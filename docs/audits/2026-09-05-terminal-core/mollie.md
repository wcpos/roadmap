## 2. POS order-authorisation gate
- `AjaxHandler::can_access_order(int $order_id): bool` accepts `manage_woocommerce`, or `edit_shop_order` for that ID, or matching POST **`order_token`**. Checkout AJAX does not require a nonce or compare the WooCommerce order key. (`includes/AjaxHandler.php:147-150`)
- Token derivation: `substr(wp_hash('mtfwc_order_' . $order_id . wp_salt('nonce')), 0, 16)`; comparison uses `hash_equals`. No timestamp, user ID or stored custom token participates. (`includes/AjaxHandler.php:149-150`, `includes/AjaxHandler.php:171`)
- `Gateway::payment_fields()` resolves `$wp->query_vars['order-pay']` on `is_checkout_pay_page()`, loads the order, and renders `data-order-id`/`data-order-token`; it does not itself validate the order key before rendering that token. (`includes/Gateway.php:223-234`, `includes/Gateway.php:254`)
- Coverage: start/poll/cancel use `with_order`; terminal list calls `can_access_order` directly. Pairing instead requires capability plus admin nonce; webhook uses remote payment retrieval and reconciliation; WooCommerce payment/refund methods do not use this custom gate. (`includes/AjaxHandler.php:19-44`, `includes/AjaxHandler.php:109-124`, `includes/WebhookHandler.php:22-30`, `includes/Gateway.php:407-434`)
- POS detection is `function_exists('woocommerce_pos_request') && woocommerce_pos_request()`; server emits `data-pos`, and fetch requests add **`X-WCPOS: 1`**. There is no plugin-owned POS query-variable detector. (`includes/Gateway.php:251-254`, `includes/AjaxHandler.php:99-106`, `assets/js/payment.js:231-238`)

## 4. Payment lifecycle on the server
- **Attempt storage:** `PaymentAttempt::record_new($order,array $payment,string $terminal_id,string $mode,string $method='pointofsale'): array` appends an attempt and saves the order. (`includes/PaymentAttempt.php:27-50`)

| Order meta key | Value shape | Evidence |

| `_mtfwc_current_payment_method` | `pointofsale`, `ideal`, or `bancontact` string | `includes/PaymentAttempt.php:8`, `includes/PaymentAttempt.php:43`, `includes/PaymentAttempt.php:162`, `includes/Services/MolliePaymentService.php:27` |

- **Start:** `MolliePaymentService::start_payment_for_order($order,$terminal_id='')` resolves the default, validates the terminal and builds a `pointofsale` payment; `start_qr_payment_for_order($order,$method)` builds QR payment metadata and requests `details.qrCode`. Both enter `start_attempt`. (`includes/Services/MolliePaymentService.php:25-57`)
- `start_attempt` returns immediately if paid; otherwise fetches/reconciles the current remote payment before creating. Open/pending/authorized/paid and other non-final outcomes are reused; only final-unpaid outcomes proceed to a new POST and `record_new`. No provider idempotency header is sent. (`includes/Services/MolliePaymentService.php:58-85`, `includes/Services/MollieApiClient.php:36-42`)
- **Locks:** `PaymentLock::{acquire,release,with_lock}` uses **`mtfwc_lock_order_<order_id>_<sanitize_key(operation)>`**, with `{operation,created_at:<epoch>,token}` and default TTL **30 seconds**. Acquisition is `get_transient` then `set_transient`, not an atomic primitive; release deletes the key in `finally`. (`includes/PaymentLock.php:7-32`)
- Lock operations are separately scoped: `create_payment`, `cancel_payment`, `cancel_abandoned`, `refund`; poll and webhook reconciliation take no `PaymentLock`. (`includes/Services/MolliePaymentService.php:57`, `includes/Services/MolliePaymentService.php:128`, `includes/Services/MolliePaymentService.php:179`, `includes/RefundReconciler.php:17`, `includes/Services/MolliePaymentService.php:103-124`, `includes/WebhookHandler.php:30`)
- **Poll:** `poll_order($order): array` retrieves/reconciles remote state only for local non-final statuses (`open`, `pending`, `authorized`, `''`); otherwise returns cached status. An open/pending attempt older than 60 seconds gets a waiting message. (`includes/Services/MolliePaymentService.php:103-124`, `includes/PaymentAttempt.php:159-161`)
- **Cancel:** `cancel_order_payment($order): array` fetches remote state, reconciles if final, otherwise DELETEs if `isCancelable` is absent/truthy, then re-fetches even after a caught cancellation exception. If still non-final, it abandons locally, adds a note and returns `abandoned`. (`includes/Services/MolliePaymentService.php:127-162`)
- Abandonment changes matching non-final history to `abandoned`, parks still-open IDs, deletes all six current-pointer meta keys, and saves. `cancel_abandoned_payments` later returns a `payment_id => outcome` map; unresolved IDs remain for another sweep. (`includes/PaymentAttempt.php:85-115`, `includes/Services/MolliePaymentService.php:176-212`)
- **Webhook:** `WebhookHandler::handle()` fetches the payment using the configured API key; order lookup first uses remote `metadata.order_id`, then `_mtfwc_current_payment_id`. It calls `PaymentReconciler::reconcile(...,'webhook')`; no signature/secret verification is performed. (`includes/WebhookHandler.php:15-42`)
- **Reconciliation:** `PaymentReconciler::reconcile($order,array $payment,string $source): array` verifies known attempt/payment-method association, supplied amount/currency/mode and ID/metadata association. It writes attempt status and removes final abandoned IDs **before branching on verification validity**. Invalid verification adds a note; final unpaid states add notes, not explicit failed/cancelled WooCommerce transitions. (`includes/PaymentReconciler.php:10-58`)
- **Paid:** same transaction on an already-paid order returns `paid,idempotent:true`; another transaction adds a conflict note and returns `conflict`. Otherwise it sets transaction ID, calls `payment_complete($payment_id)`, adds a completion-source note and saves. (`includes/PaymentReconciler.php:76-88`)
- **Status-change cleanup:** `PaymentCleanup::maybe_cancel_abandoned_payment`, on `woocommerce_order_status_changed` priority 20/four arguments, cancels a current non-final attempt when the target status is processing/completed/cancelled/failed; uses an 8-second client timeout and records the outcome in an order note. (`includes/PaymentCleanup.php:22-57`)
- **Sweeper:** WP-Cron hook **`mtfwc_sweep_stale_payments`**, schedule **`mtfwc_ten_minutes`** (600 seconds), first scheduled at now+60 on `init`; deactivation unschedules it. Stale threshold filter **`mtfwc_stale_payment_seconds`**, default 600; batch filter **`mtfwc_stale_payment_batch`**, default 25 per query. (`includes/PaymentSweeper.php:21-65`, `mollie-terminal-for-woocommerce.php:56-59`)
- Sweep queries oldest orders: pending/failed with current-payment meta, plus any status with abandoned-ID meta. Abandoned payments are resolved first; unpaid current non-final attempts past threshold are canceled/abandoned with notes. The two query result sets are deduplicated by order ID; service timeout is 8 seconds. (`includes/PaymentSweeper.php:67-101`, `includes/PaymentSweeper.php:109-155`)
- **Resume:** server renders resume flags for unpaid orders with current non-final attempts; frontend resumes polling rather than creating another payment. (`includes/Gateway.php:236-254`, `assets/js/payment.js:943-950`)
- **Refund:** `Gateway::process_refund` delegates to `RefundHandler::process_refund($order,$amount,$reason)`, which first calls `wc_create_refund`, then `RefundReconciler::refund`; returns the reconciler’s array or `WP_Error`, including `mtfwc_invalid_order`/`mtfwc_refund_failed`. (`includes/Gateway.php:434`, `includes/RefundHandler.php:10-15`)
- Refund reconciliation uses transaction ID/current-payment fallback, fetches payment and refunds, reuses a stored refund ID or a remote match on metadata `{order_id,woo_refund_id,refund_attempt_id}`, otherwise POSTs amount/description/metadata. Remaining refundable value is reduced by all listed refund amounts; subtraction rejects a negative result. (`includes/RefundReconciler.php:16-45`, `includes/Utils/Money.php:21-27`)
- Refund-object meta: **`_mtfwc_refund_attempt_id`** UUID/fallback ID, **`_mtfwc_mollie_refund_id`** string, **`_mtfwc_refund_status`** string/default `queued`, **`_mtfwc_refund_amount`** supplied amount string. `store_refund` saves and returns `{status:'refunded',refund_id}`; no separate refund poll/webhook/cleanup registration exists. (`includes/RefundReconciler.php:9-12`, `includes/RefundReconciler.php:25-37`, `includes/RefundReconciler.php:47-52`, `includes/WebhookHandler.php:24-30`)

## 5. Checkout front end (assets/js)
- Files: **`assets/js/payment.js` — 981 lines**, vanilla-JS IIFE; **`assets/js/admin.js` — 1 line**, empty strict-mode IIFE. Payment assets are enqueued via `wp_enqueue_scripts` without a page check in the enqueue method. (`assets/js/payment.js:1-981`, `assets/js/admin.js:1`, `includes/Gateway.php:22`, `includes/Gateway.php:355-365`)
- **State shape:** DOM/root properties rather than a state-machine class: `data-mtfwc-request-pending`, `mtfwcPoll={deadline,timer,id}`, `mtfwcPollSeq`, `mtfwcCompleted`, busy attribute, and primary-button start/cancel mode. (`assets/js/payment.js:294-324`, `assets/js/payment.js:450-462`, `assets/js/payment.js:610-628`)
- **Idle → sending → waiting:** Start blocks duplicate requests/missing terminal, freezes controls, posts terminal ID or `{channel:'qr',qr_method}`; failure resets controls, paid completes, otherwise channel/method syncs to the server and polling starts. (`assets/js/payment.js:610-658`)
- **Classification:** paid/already_paid/**conflict** → paid; failed/canceled/expired/verification_failed → failed; idle → idle; everything else → pending. (`assets/js/payment.js:278-290`)
- **Polling:** first tick after 2,000 ms; each response schedules the next tick at the same interval, without backoff. Deadline defaults to 300,000 ms; both values are localized through `mtfwc_poll_interval_ms`/`mtfwc_poll_timeout_ms`. Session IDs discard stopped/superseded responses. Failed/network responses with no status fall into pending and keep polling. (`includes/Gateway.php:364-365`, `assets/js/payment.js:254-256`, `assets/js/payment.js:450-543`)
- **Timeout:** checked before sending the next poll; stops polling, hides QR, disables the action button and calls cancel. A paid cancellation response completes; any other result displays timeout and resets to start. There is no fetch abort/deadline in `postAction`, so the timer is not a hard bound on an outstanding request. (`assets/js/payment.js:238-257`, `assets/js/payment.js:474-504`)
- **Manual cancel:** stops polling, waits for the AJAX response, then handles paid, abandoned, failure or canceled. It does not continue polling for remote cancellation confirmation; local abandonment is sufficient to release the UI. (`assets/js/payment.js:661-692`)
- **Method switch/leave:** switching away cancels a currently polled payment and handles a late paid response; `pagehide` sends a best-effort cancel beacon for active, incomplete polls. Reload-resume flags coexist with this leave-time cancellation behavior. (`assets/js/payment.js:706-763`, `assets/js/payment.js:855-874`, `assets/js/payment.js:943-950`)
- **Resume:** `bind` honors `data-resume="1"` and `data-resume-channel`, creates a fresh polling deadline, and does not start a new payment; handlers also bind on jQuery/native `updated_checkout`. (`assets/js/payment.js:450-456`, `assets/js/payment.js:943-979`)
- **Success → POS:** navigate to supplied `redirect_url`; fallback chain is click `#place_order`, submit `#order_review`, then `window.top.postMessage({action:'wcpos-process-payment'}, '*')`. POS return URL is `/wcpos-checkout/order-received/<id>?key=<order-key>`; other requests use WooCommerce’s received URL. (`assets/js/payment.js:563-596`, `includes/AjaxHandler.php:99-106`)
- **Request parameters:** multipart POST `action`, `order_id`, `order_token`, plus action-specific fields; same-origin credentials; POS fetches add `X-WCPOS: 1`. The leave beacon sends the three fields but no custom header. (`assets/js/payment.js:207-238`, `assets/js/payment.js:867-872`)

Fetch failure logs a warning and re-enables existing options. Selection helper still falls back to configured default when the select value is empty. (`assets/js/payment.js:176-186`, `assets/js/payment.js:768-825`)

## 7. Terminal discovery and curation
- `TerminalService::list_terminals(int $timeout=0): array` calls account-wide `GET /terminals?limit=250`, ignoring stored profile ID; extracts `_embedded.terminals`, then `items`, else `[]`. No pagination traversal or service-level cache is implemented. (`includes/Services/TerminalService.php:11-16`, `includes/Services/MollieApiClient.php:19`)
- Checkout list is fetched directly; `normalize_terminals` returns `{id,label,status,mode}`, dropping invalid/missing-ID entries; label preference description→brand→ID. `selectable_terminals` drops lowercase inactive/disabled and applies the allowlist. (`includes/AjaxHandler.php:47-50`, `includes/AjaxHandler.php:59-89`)
- Settings-screen choices use request memoization and transient **`mtfwc_terminal_choices_test|live`**, TTL **5 minutes**, with an 8-second API timeout. Fetching is restricted to non-AJAX admin requests with matching `section` and a key. (`includes/Gateway.php:142-171`)
- Settings save deletes both current cache keys plus legacy **`mtfwc_terminal_options_test|live`**. (`includes/Gateway.php:19-20`, `includes/Gateway.php:346-351`)

## 11. Plugin-specific (must stay local)
`Services\MollieApiClient` is a local WordPress HTTP wrapper, not a provider SDK: Bearer API key, JSON, `https://api.mollie.com/v2`, default 30-second timeout, associative-array responses and `RuntimeException` errors. It exposes profile/terminal/pairing/payment/cancel/refund methods; authentication can reuse the official Mollie plugin’s mode-specific key. Terminal payments use `method=pointofsale`, `terminalId`, amount, redirect/webhook URLs and order metadata; QR uses `ideal`/`bancontact` plus `include=details.qrCode`, returning image `{src,width,height}` only while open and only for `data:image/` or HTTPS sources. Webhook authentication is remote retrieval of the supplied payment ID followed by local attempt/money/method/environment checks, not signature verification. Provider models are arrays containing `id`, `status`, `amount`, `method`, `mode`, `metadata`, `isCancelable`, `details.qrCode`, and `_embedded` collections. (`includes/Services/MollieApiClient.php:7-57`, `includes/Settings.php:28-40`, `includes/Services/MolliePaymentService.php:25-53`, `includes/Services/MolliePaymentService.php:89-94`, `includes/Services/MolliePaymentService.php:135-146`, `includes/WebhookHandler.php:15-30`, `includes/PaymentReconciler.php:35-58`, `includes/RefundReconciler.php:41`)

## 12. Notable hardening and comments
1. Enabled-state regression: “the 0.5.1 guard only looked at that one and locked every such POS out”; start/list accept either web or POS enablement. (`includes/AjaxHandler.php:153-163`)
2. Settlement after disabling: “a payment already in flight must still settle”; poll/cancel/webhook are deliberately not enabled-gated. (`includes/AjaxHandler.php:161-163`)
3. Lost allowlist prevention: field is “Omitted entirely when the terminal list cannot be fetched” so temporary API failure does not wipe settings. (`includes/Gateway.php:114-117`)
4. Admin outage behavior: “use a short timeout” rather than “hanging admin”; terminal choices use cache and text fallback. (`includes/Gateway.php:152-154`)
5. Removed profile setting: old value is “intentionally ignored” so upgraded sites are not stuck on an uneditable profile. (`includes/Services/TerminalService.php:12-14`)
6. Lock/default interaction: excluding the default “would brick checkout when the terminal selection is locked”. (`includes/Settings.php:78-83`)
7. Order-pay completion: re-submission would hit WooCommerce’s **“already paid”** guard; server supplies direct thank-you navigation. (`includes/AjaxHandler.php:134-137`)
8. Unresponsive terminal: “Detach the attempt locally so the cashier regains control”; webhook/sweeper reconcile lingering payment. (`includes/Services/MolliePaymentService.php:152-156`)
9. Sweep visibility: deleting current pointer “would hide it from the stale-payment sweep”; abandoned IDs have separate meta. (`includes/PaymentAttempt.php:98-100`)
10. Attempt ownership: abandoned-payment reconciliation “must not stamp its status onto whatever attempt the cashier is running now”. (`includes/PaymentAttempt.php:56-58`)
11. Shared-profile collision: unknown payment cannot pay an order “even when its metadata order_id collides”. (`includes/PaymentReconciler.php:46-49`)
12. Cleanup recursion: reconciler records final attempt status before `payment_complete()` fires status changes, so own paid attempt is no longer non-final. (`includes/PaymentCleanup.php:15-17`)
13. Browser failure backstop: browser kill/network drop/tab discard can defeat timeout cancellation and leave beacon; WP-Cron handles lingering payments. (`includes/PaymentSweeper.php:9-18`)
14. Method-switch race: dropping a cancel response that says paid “would strand a paid order on another payment method”. (`assets/js/payment.js:728-731`)
15. Terminal placeholder: missing saved default must not silently choose “the first terminal, which could be the wrong physical device”. (`assets/js/payment.js:808-810`)

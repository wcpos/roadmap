## 2. POS order-authorisation gate
- `PaymentRequestToken::create(order_id, order_key, expires?)` returns `{token,expires}`, defaulting to one hour. Token is HMAC-SHA256 of `stripe_terminal_payment|<order_id>|<order_key>|<expires>`, signed with `wp_salt('auth')`, or `__FILE__` if that function is unavailable. Validation checks expiry/nonempty values and `hash_equals`. No token storage. (`includes/PaymentRequestToken.php:22-74`)
- `Gateway` creates the token for the order-pay order and localizes `paymentToken`, `paymentTokenExpires`, `orderId`, `orderKey`, and a `stripe_terminal_nonce` nonce. (`includes/Gateway.php:684-710`, `includes/Gateway.php:749-789`)
- `AjaxHandler::verify_order_ajax_request(order)` accepts a matching posted `order_key` **without nonce when no token is supplied**; otherwise falls back to nonce verification. When a token is supplied, it must validate against the posted key, and that key must match the order. (`includes/AjaxHandler.php:1028-1063`)
- Covered order handlers then also call `can_access_order()`: nonempty matching POST `order_key` **and** `$order->needs_payment()`. No capability check is added; nonce alone therefore does not satisfy the combined gate. (`includes/AjaxHandler.php:1070-1079`)
- Covered: create, confirm, cancel, order-specific reader status, reader display/warm, poll, manual Stripe check, simulate, retry, force-clear. Reader status without `order_id` uses nonce only. `validate_service` and `get_readers` have no nonce/order gate. REST handlers do not use this gate. (`includes/AjaxHandler.php:115-121`, `includes/AjaxHandler.php:245-251`, `includes/AjaxHandler.php:307-313`, `includes/AjaxHandler.php:368-386`, `includes/AjaxHandler.php:408-472`, `includes/AjaxHandler.php:500-505`, `includes/AjaxHandler.php:547-552`, `includes/AjaxHandler.php:651-657`, `includes/AjaxHandler.php:735-741`, `includes/AjaxHandler.php:808-813`, `includes/AjaxHandler.php:887-892`, `includes/API.php:49-123`)
- POS detection uses `woocommerce_pos_request()` and, for POS return URLs/recovery, `order-pay` query vars. Nonce creation temporarily switches to order meta `_pos_user`, then restores the original WP user. Warming separately recognizes `created_via=woocommerce-pos`, `_pos=1`, and REST prefix `/wcpos/`. (`includes/Gateway.php:165-175`, `includes/Gateway.php:771-789`, `includes/Gateway.php:913-925`, `includes/ReaderWarmer.php:86-88`, `includes/ReaderWarmer.php:183-202`)

## 4. Payment lifecycle on the server
- **Start:** AJAX takes `order_id`, `reader_id`, optional MOTO; amount is recomputed from the WC order, not trusted from JS. Service creates a fresh PaymentIntent with amount, currency, description, and Stripe `metadata.order_id`; no creation idempotency key or persisted Attempt/Lock object. (`includes/AjaxHandler.php:95-137`, `includes/StripeTerminalService.php:164-235`)
- Start persists `_stripe_terminal_payment_intent_id` → `pi_...`; `_stripe_terminal_moto` → `'yes'` or deletes it; adds creation/dispatch notes. Options `stwc_last_reader_id` → reader ID and `stwc_payment_dispatch_at` → epoch seconds support warming. Then dispatches `processPaymentIntent` with customer cancellation enabled. (`includes/AjaxHandler.php:150-204`, `includes/StripeTerminalService.php:252-257`, `includes/StripeTerminalService.php:313-330`)
- **Poll:** `check_payment_status()` reads WC paid/status/transaction and terminal metadata; retrieves the recorded intent directly from Stripe, reports decline detail, and allows a non-succeeded Stripe status to override local success metadata for an unpaid order. It does not save metadata or complete payment. (`includes/AjaxHandler.php:556-621`)
- **Manual reconciliation/resume:** service lookup tries transaction ID as intent or charge, then `_stripe_terminal_payment_intent_id`, then the first matching `metadata.order_id` among 100 listed intents; fetches latest charge. Paid charge + succeeded intent + unpaid order causes terminal metadata persistence and a recovery note, not immediate completion. (`includes/StripeTerminalService.php:827-935`)
- That metadata is `_stripe_terminal_payment_intent_id`, `_stripe_terminal_charge_id`, `_stripe_terminal_payment_status='succeeded'`, `_stripe_terminal_payment_amount` integer minor units, `_stripe_terminal_payment_currency` provider currency string, `_stripe_terminal_payment_method='card'|'card_present'`, and `_stripe_terminal_moto='yes'` or deletion. (`includes/StripeTerminalService.php:908-921`)
- **Confirm:** `confirm_payment_intent(id,order)` retrieves rather than captures/confirms at Stripe; on succeeded status calls `update_order_from_payment_intent()`. With expanded charge data, stores `_transaction_id`, `_stripe_currency` uppercase, `_stripe_charge_captured='yes'|'no'`, `_stripe_intent_id`, `_stripe_terminal_livemode='yes'|'no'`, `_stripe_card_type`; saves without completing payment. (`includes/StripeTerminalService.php:456-474`, `includes/StripeTerminalService.php:640-659`)
- **Cancel:** AJAX first cancels reader action, then calls `cancel_payment_intent(id,order)`. The latter cancels only `requires_payment_method` or `requires_confirmation`; neither method clears order payment metadata. Reader cancellation translates provider busy/missing-action into `{status:'busy'|'idle'}`. (`includes/AjaxHandler.php:325-343`, `includes/StripeTerminalService.php:488-549`)
- **Stale/abandoned actions:** dispatch conflict invokes `clear_stale_reader_action()`: clears failed or non-in-progress foreign actions, refuses an in-progress foreign intent, and retries dispatch once. Timeout recovery also cancels/retries once. Force-clear rechecks the expected foreign intent and `in_progress` state before cancellation. No payment sweeper/expiry cleanup is registered; cron here is reader warming, not reconciliation. (`includes/StripeTerminalService.php:259-301`, `includes/StripeTerminalService.php:349-421`, `includes/AjaxHandler.php:901-931`, `includes/ReaderWarmer.php:63-67`, `includes/ReaderWarmer.php:99`, `includes/ReaderWarmer.php:202`)
- **Registered webhook:** `API::handle_webhook()` handles intent success, charge success, and intent failure. Intent success writes terminal ID/status/amount/currency/livemode/method/MOTO, reconciles tip, saves, and notes; it does not call `payment_complete()`. Failure stores `_stripe_terminal_payment_status='failed'` and `_stripe_terminal_payment_error` after ignoring already-paid/succeeded orders; WC status is unchanged. No event-ID deduplication or webhook lock. (`includes/API.php:398-447`, `includes/API.php:477-524`, `includes/API.php:606-646`)
- Charge-success updater contains a call to `Settings::get_secret_key()`, but `Settings` defines only the three accessors listed above; its subsequent charge-meta write path is therefore not established as executable. This is an **Observed source mismatch**, not runtime-tested. Auto-created webhooks subscribe only to intent success/failure. (`includes/API.php:541-581`, `includes/Settings.php:13-44`, `includes/Gateway.php:871-875`)
- A second, separately defined service webhook implementation is **not the registered REST callback**: its succeeded-intent handler directly calls `payment_complete(intent_id)`, while its failed handler sets WC status `failed`. (`includes/API.php:114-120`, `includes/StripeTerminalService.php:766-802`, `includes/StripeTerminalService.php:985-1015`, `includes/StripeTerminalService.php:1114-1141`)
- **Paid transition:** `Gateway::process_payment()` returns success for already-paid orders; otherwise successful terminal intent+charge metadata, or successful direct Stripe recovery, triggers transaction assignment, `payment_complete(charge_id)`, an order note, and return URL. Unpaid main checkout redirects to order-pay; unpaid order-pay form submission returns failure. (`includes/Gateway.php:324-422`)
- **Tip reconciliation:** `Utils\TipReconciler::maybe_add_tip_to_order(order,intent)` adds a non-taxable `Tip` fee from `amount_details.tip.amount`; stores `_stripe_terminal_tip_amount` in major units and `_stripe_terminal_tip_payment_intent_id`; recalculates totals without tax. Same-intent meta check is the deduplication mechanism, not a lock. No general Reconciler/Attempt/Lock class is used in the payment path. (`includes/Utils/TipReconciler.php:15-52`, `includes/AjaxHandler.php:135-179`)
- **Refund:** `Gateway::process_refund(order_id,amount?,reason)` chooses original test/live mode using `_stripe_terminal_livemode`; resolves `_transaction_id`, `_stripe_terminal_charge_id`, `_stripe_intent_id`, then terminal intent ID. Service calls Stripe refunds API; idempotency key is `stwc_refund_<order>_<minor-amount|full>_<refund-count>`. Adds a note and returns true except failed/canceled/provider errors; pending is accepted. No custom refund meta/cron. (`includes/Gateway.php:434-546`, `includes/StripeTerminalService.php:92-113`)

## 12. Notable hardening and comments
1. Duplicate submission: “WooCommerce then skips the gateway” and shows an already-paid error; recovery redirects only matching paid Terminal POSTs with the order key. (`includes/Gateway.php:158-201`)
2. POS nonce identity: “switching the current WordPress user to the order customer”; nonce is created for `_pos_user` cashier instead. (`includes/Gateway.php:760-789`)
3. JWT/cookie distinction: signed token avoids “coupling payment actions to a specific WordPress auth layer.” (`includes/AjaxHandler.php:1021-1024`)
4. Reader freshness: “Do not block dispatch solely because it is old”; `processPaymentIntent` is the authoritative liveness check. (`includes/StripeTerminalService.php:357-362`)
5. Pickup verification: cancelling on unchanged timestamps “can abort a valid payment”; continue polling Stripe. (`packages/payment-frontend/src/payment.js:573-580`)
6. Conflict retry: “Return the single retry directly so recovery paths cannot stack.” (`includes/StripeTerminalService.php:273-274`)
7. Mid-authorization cancellation: reader busy is explicitly represented rather than treated as successful cancellation of the hardware action. (`includes/StripeTerminalService.php:534-543`)
8. Keep-warm: display commands can “REPLACE[] the payment action, killing collection”; setting defaults off because guards cannot close the race. (`includes/ReaderWarmer.php:42-46`, `includes/ReaderWarmer.php:124-129`)
9. POS new-order warming: “POS orders are created as open orders before a gateway is chosen”; provenance, not only gateway ID, selects them. (`includes/ReaderWarmer.php:73-88`)
10. Currency-cache refresh: stale cached country must not block valid payment after “rotated key, account moved.” (`includes/StripeTerminalService.php:1168-1195`)
11. Capture endpoint: “Never store client-supplied payment data”; retrieve with store key because refunds later act on this metadata. (`includes/API.php:315-340`)
12. Completion ownership: “Don't change the order status to processing”; gateway owns the completion lifecycle. (`includes/API.php:345-349`)
13. Failed webhook ordering: “Guard against stale failed events arriving after a successful payment.” (`includes/API.php:619-623`)
14. Pending refunds: erroring would make WooCommerce discard its record “while Stripe still completes the refund.” (`includes/Gateway.php:530-534`)
15. Blocks compatibility: missing automatic JSX runtime on older WP installs must not break checkout; integration stays inactive. (`includes/Blocks/StripeTerminalBlocksSupport.php:43-62`)

**Behavior changes / regressions:** No changes made; no before/after execution, so regressions were not evaluated. Source mismatches affecting interpretation are identified in sections 4–6.

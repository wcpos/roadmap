## 2. POS order-authorisation gate
- No custom POS token: server renders the existing WooCommerce order key as `data-order-key`, using `order-pay` query-var order ID; ordinary checkout gets no order ID/key here. JS passes that key with payment requests. (`includes/Gateway.php:298-310`, `assets/js/payment.js:157-185`)
- `ajax_create_checkout()` requires AJAX, reader ID, order ID, existing order and nonempty `order_key`, compared using `hash_equals($order->get_order_key(), $order_key)`. No payment nonce/capability check. (`includes/AjaxHandler.php:124-153`)
- `ajax_cancel_checkout()` additionally compares posted `reader_id` against order meta `_sumup_reader_id`; status lookup authorizes the key and derives the reader from order meta rather than posted reader input. (`includes/AjaxHandler.php:225-250`, `includes/AjaxHandler.php:275-302`, `includes/AjaxHandler.php:353-359`)
- **POS detection ABSENT.** The payment handlers universally skip nonce validation under POS-context comments; they test `wp_doing_ajax()`, not a POS header/function/query flag. Rendering sets compatibility nonce string `pos_environment` unconditionally. (`includes/AjaxHandler.php:125-135`, `includes/AjaxHandler.php:226-236`, `includes/AjaxHandler.php:276-288`, `includes/Gateway.php:363-367`)
- Outside the order-key gate: pair/unpair use nonce `sumup_admin_actions` plus `manage_woocommerce`; webhook uses its own order-specific token; `Gateway::process_payment($order_id)` itself only checks transaction ID/already-paid state. (`includes/AjaxHandler.php:45-54`, `includes/AjaxHandler.php:89-98`, `includes/AjaxHandler.php:453-462`, `includes/Gateway.php:236-255`)
- Webhook token derivation, duplicated in reader service and handler: `substr(wp_hash('sumup_webhook_' . $order_id . wp_salt('nonce')), 0, 10)`; passed as URL parameter `nonce`, with no expiry check. (`includes/Services/ReaderService.php:122-132`, `includes/Services/ReaderService.php:156-162`, `includes/AjaxHandler.php:670-676`)

## 4. Payment lifecycle on the server
- **Start:** `ajax_create_checkout()` rejects paid/no-longer-payable orders and existing nonterminal meta states; retryable states are `FAILED,CANCELLED,TIMEOUT,EXPIRED`. It clears prior checkout/transaction statuses and timestamps, `_sumup_transaction_checked_at`, and WooCommerce transaction ID. (`includes/AjaxHandler.php:155-178`)
- Before provider call it saves `_sumup_checkout_status='CREATING'`, `_sumup_reader_id=<string>`, `_sumup_attempt_started=<Unix seconds>`. `ReaderService::create_checkout_for_order(WC_Order,reader_id)` constructs amount/description/callback and returns provider array or false. (`includes/AjaxHandler.php:179-185`, `includes/Services/ReaderService.php:95-145`)
- Successful start stores `data.client_transaction_id` through `set_transaction_id()` in both service and handler, then saves `_sumup_checkout_status='PENDING'`. False/exception deletes checkout status and reader ID but leaves attempt-start time. (`includes/Services/ReaderService.php:136-142`, `includes/AjaxHandler.php:187-218`)
- **Poll/reconciliation:** `ajax_check_payment_status()` reads saved states/transaction ID. With an ID, non-PAID checkout and nonfinal transaction state, it queries when five seconds have elapsed, `force_transaction_check` is true, or checkout state is final. `_sumup_transaction_checked_at=<Unix seconds>` is saved before querying. (`includes/AjaxHandler.php:304-327`)
- `TransactionService::get_by_client_transaction_id(string)` GETs `/v2.1/merchants/{merchant_code}/transactions?client_transaction_id=...`, returning array/false. Only matching response client ID and `SUCCESSFUL|FAILED|CANCELLED` are persisted as `_sumup_transaction_status`; `_sumup_transaction_updated=gmdate('c')`; reader meta is removed. (`includes/Services/TransactionService.php:28-61`, `includes/AjaxHandler.php:328-340`)
- Effective response maps `SUCCESSFUL→PAID`; failed/cancelled transaction overrides checkout unless checkout already says PAID. Active nonfinal attempts also query reader status. Poll does not call `payment_complete()` or persist its effective checkout-state mapping. (`includes/AjaxHandler.php:347-423`)
- **Cancel:** `ajax_cancel_checkout()` calls `ReaderService::cancel_checkout(reader_id)` → provider terminate. It stores no cancellation meta and returns only acceptance; final state comes through subsequent webhook/status reconciliation. (`includes/AjaxHandler.php:252-269`, `includes/Services/ReaderService.php:59-61`, `includes/Services/WordPressHttpReaderApiClient.php:115-143`)
- **Webhook:** `process_webhook()` ignores parseable timestamps earlier than `_sumup_attempt_started`. Routes `checkout.status.updated` and `solo.transaction.updated`; saves `_sumup_last_webhook={event_type,payload,timestamp,processed}`, with ISO-style default/current timestamps. (`includes/AjaxHandler.php:507-544`)
- Checkout event saves `_sumup_checkout_status=<payload status>` and `_sumup_checkout_updated=<event timestamp>`; transaction event saves `_sumup_transaction_status` and `_sumup_transaction_updated`. Final states remove `_sumup_reader_id`; each handler adds a status order note, with transaction ID included in transaction-event notes. (`includes/AjaxHandler.php:554-592`, `includes/AjaxHandler.php:602-631`)
- Attempt correlation rejects events while `CREATING`; otherwise matches current transaction ID against payload `client_transaction_id`, then `reference`, then `transaction_id`. With no current transaction ID, matcher returns true. No event-ID deduplication or atomic lock appears in these checks. (`includes/AjaxHandler.php:642-659`)
- **Lock / Attempt / Reconciler classes ABSENT.** Guarding and reconciliation live directly in `AjaxHandler`, using ordinary order-meta reads/saves; no lock key, idempotency header or checkout request idempotency key is constructed. (`includes/AjaxHandler.php:155-185`, `includes/AjaxHandler.php:304-340`, `includes/Services/ReaderService.php:107-134`)
- **Cron/sweeper/payment TTL ABSENT.** Cleanup is synchronous failure/retry/final-status meta deletion; browser timeout requests termination. Abandoned attempts have no server-scheduled cleanup in the initialization/lifecycle shown. (`sumup-terminal-for-woocommerce.php:92-99`, `includes/AjaxHandler.php:172-218`, `includes/AjaxHandler.php:337-340`, `assets/js/payment.js:433-444`)
- **Resume:** stored transaction/meta allow later manual status checks, but there is no resume-specific response or bootstrap-restored active poll. (`includes/AjaxHandler.php:304-312`, `assets/js/payment.js:19-25`, `assets/js/payment.js:209-243`)
- **Mark paid:** JS submits WooCommerce checkout after PAID; `Gateway::process_payment()` requires any recorded transaction ID, calls `payment_complete()` only if not already paid, returns `{result:'success',redirect:get_return_url(order)}`. It does not itself inspect SumUp status; webhook/poll only update/report provider state. (`assets/js/payment.js:460-466`, `assets/js/payment.js:490-512`, `includes/Gateway.php:236-255`)
- **Refund ABSENT.** No plugin refund handler/support declaration; implemented gateway processing is the payment path above, and server endpoint registration contains no refund action. (`includes/Gateway.php:43-70`, `includes/Gateway.php:236-257`, `includes/AjaxHandler.php:22-39`)

## 5. Checkout front end (assets/js)
- Files: `payment.js` **602 lines**; `admin.js` **156 physical lines / 155 newline-terminated lines**. Payment object is CommonJS-exportable for tests; admin exposes `window.sumupAdmin` plus legacy globals. (`assets/js/payment.js:1-602`, `assets/js/admin.js:1-156`)
- State is an in-memory `activePolls[readerId]` registry, with flags `active`, `requestPending`, `cancelRequested`, `cancellationPending`, `timeoutPending`, `timeoutFinalCheckRunning`, `manualOnly/manualCheck`; no persisted payment-state object. (`assets/js/payment.js:10-14`, `assets/js/payment.js:209-243`, `assets/js/payment.js:278-285`, `assets/js/payment.js:340-430`)
- Idle → starting disables all Start/Check Status buttons; accepted start enables that reader’s Check Status/Cancel and enters polling; start error resets controls. (`assets/js/payment.js:169-205`, `assets/js/payment.js:530-542`)
- Poll every **2,000 ms**, no backoff; `maxPolls=150`, expiry on tick **151** (nominally ~302 seconds, plus outstanding/final request time). Tick count increments even while request overlap is suppressed; no explicit browser AJAX timeout. (`assets/js/payment.js:350-353`, `assets/js/payment.js:368-430`)
- Timeout waits for any in-flight status request, then performs a fresh `force_transaction_check=true` request before cancellation. If still active, requests cancellation; accepted cancellation resets the counter and continues polling. (`assets/js/payment.js:299-312`, `assets/js/payment.js:375-443`)
- User cancel asks for confirmation and does **not** equate accepted terminate with final cancellation. Terminal response stops polling and resets controls, except PAID submits checkout. Cancellation failure resumes polling if stopped; a subsequent cancellation-pending timeout stops polling, leaves Start disabled and directs cashier to Check Status. Repeated cancellation failures therefore have no fixed total elapsed-time ceiling. (`assets/js/payment.js:273-335`, `assets/js/payment.js:433-470`)
- Reader display maps `IDLE`, `SELECTING_TIP`, `WAITING_FOR_CARD`, `WAITING_FOR_PIN`, `WAITING_FOR_SIGNATURE`, `UPDATING_FIRMWARE`, plus `OFFLINE`; these are display states, not payment finality. (`assets/js/payment.js:448-485`)
- **Automatic resume-on-reload ABSENT.** Initialization restores logs/readers only; manual Check Status creates a one-shot poll context. Reader cards initially show Start/Check Status and hidden Cancel regardless of saved attempt state. (`assets/js/payment.js:19-25`, `assets/js/payment.js:219-243`, `includes/Gateway.php:330-339`)
- **POS postMessage ABSENT.** Success clicks `#place_order`, otherwise submits `#order_review`, otherwise `form.checkout/form[name="checkout"]`; absent forms, displays success. Redirect comes from gateway `get_return_url(order)`, not a JS POS URL. (`assets/js/payment.js:490-512`, `includes/Gateway.php:252-255`)
- No POS-specific headers/flags added. Start/cancel POST `action,nonce,reader_id,order_id,order_key`; poll POSTs `action,order_id,order_key,force_transaction_check`. (`assets/js/payment.js:177-186`, `assets/js/payment.js:289-298`, `assets/js/payment.js:393-401`)
- Selection uses server-rendered reader cards, not a dropdown/list AJAX endpoint. On gateway selection/`updated_checkout`, empty panels reload the current-page fragment; existing cards are preserved, concurrent refreshes queue another load. (`includes/Gateway.php:287-342`, `assets/js/payment.js:24`, `assets/js/payment.js:50-111`)
- Errors appear as text-built `.sumup-status-error` blocks in per-reader ARIA live regions; polling errors normally log warnings, with visible errors on manual checks. (`includes/Gateway.php:341`, `assets/js/payment.js:402-414`, `assets/js/payment.js:557-584`)
- Unit tests: six Node tests stub jQuery/DOM/AJAX around timeout final-check ordering and five reader-loading cases. PHP source-contract tests inspect log controls, order-key wiring, safe rendering, targeted form submission and continued polling after cancellation—not full browser lifecycle execution. (`tests/payment-timeout-polling.test.js:1-219`, `tests/regression/payment-interface-contract.php:12-68`)

## 12. Notable hardening and comments
1. “Skip nonce validation for POS environment due to user context switching”; implemented across all three payment handlers, with order-key checks instead. (`includes/AjaxHandler.php:125-153`, `includes/AjaxHandler.php:226-249`, `includes/AjaxHandler.php:276-301`)
2. “We can't use wp_verify_nonce() because webhooks come from external servers … with no WordPress user session”; motivates the deterministic order-specific webhook token. (`includes/AjaxHandler.php:453-457`)
3. “Remove final state from a previous attempt before starting a retry”; clears checkout/transaction status, timestamps and previous transaction ID before saving `CREATING`. (`includes/AjaxHandler.php:172-182`)
4. “Reconcile pending webhook state against SumUp's authoritative transaction record”; implements throttled transaction lookup and identity matching rather than relying exclusively on callbacks. (`includes/AjaxHandler.php:304-340`)
5. “This is an asynchronous operation. The API only confirms the terminate request was accepted”; cancellation completion is expected later by webhook, not inferred from HTTP acceptance. (`includes/Services/WordPressHttpReaderApiClient.php:115-143`)
6. “Opening a gateway only reveals its existing markup. Re-fetch the box so an empty initial render gets another chance to load the paired readers.” (`assets/js/payment.js:88-93`)
7. “This runtime guard must happen before requiring the SDK autoloader”; SDK loading is guarded so older PHP never loads its newer syntax. (`sumup-terminal-for-woocommerce.php:37-41`, `vendor_prefixed/sumup-sdk-autoload.php:3-8`)
8. “We no longer fetch merchant_code here to avoid unnecessary API calls”; service initialization defers merchant retrieval to cached profile access. (`includes/Gateway.php:528-536`, `includes/AjaxHandler.php:701-706`)
9. “Cache the result (even if false, to avoid repeated failed calls)”; failures are cached within the request, while only successful profiles enter the five-minute transient. (`includes/Services/ProfileService.php:55-61`)

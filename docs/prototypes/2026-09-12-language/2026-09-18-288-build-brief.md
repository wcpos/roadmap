# Settings, connect, receipt, products and the token sheet: the build brief (roadmap#288, 2026-09-18)

The ticket: does the language decided on the register and orders hold on four other kinds of
screen, and what are the concrete token values that make all six cohesive. This brief is the
input to the build. The output is the drawing, the captures, and a README per folder whose
numbered decisions Paul rules on. The register is signed off (README, "Decisions for Paul",
2026-09-18); nothing there is reopened.

## 0. Read first, in this order

1. `README.md` in this folder: the decided language, the token table, every ruling.
2. `../../design/2026-09-12-direction.md` and `../../design/ui-design-guidelines.md`.
3. `pos-register/index.html`, the whole file. It is the design: the token block at the top,
   the strip (`renderStrip`, `seg`), `S` and `Q`, `render()`, the `RP` (Reports) and `OP`
   (Orders) page modules with their own `SCENES`, `render`, `click`, `jump`, `keydown`. New
   pages copy that shape. Reuse its primitives: `.bar`, `.rail`, `.panel`, `.sheet`, `.pop`,
   `.toast`, `.lr`, `.opt`, `.sw`, `.btn`, `.ibtn`, `.chip`/`.pill`, `.in`, `.segt`, `.tr`,
   `.empty`, `.paidwrap`, the icon map `I`. Add classes only for what has no primitive.
4. The four `INVENTORY.md` files (`settings/`, `connect/`, `receipt/`, `products/`): the
   feature floor. Read §1, §2, §3, §5, §6 of each; dip into §4 only for a string you need.
   Guideline 10: a drawing that invents a simplified screen evaluates a straw man. Rehost every
   control, every state, every learned behaviour that is visible; where the brief below says
   to change something, that is a deliberate decision that goes to Paul, listed in the README.

Rules that bind every line: everything reads tokens (no new hex, no new px that is not a token
expression); `max(var(--ctl),var(--floor))` on every control; sentence case in every string
("Store name", not "Store Name": the app's strings are title case, the language is not); status
is a dot plus a word; confirmation only for destruction; no toast on a happy path; a completion
is one quiet beat; one line of copy, never a paragraph; the theme tints controls and the rail
only; Tabler/Hugeicons/Phosphor by theme as the file already does.

## 1. Shape

- **Settings and Connect are pages of the register**, like Orders and Reports: `?screen=settings`
  (module `SP`) and `?screen=connect` (module `CP`). The rail's gear opens Settings; the phone
  menu sheet lists it. Connect has no rail (it is before login): the cashier sheet's "Switch
  store" and the strip's State reach it. Each page keeps its own State group in the strip;
  Width, Theme and Scale are shared as today.
- **The token sheet is a page**: `?screen=tokens` (module `TK`), computed from the live frame.
- **Receipt and products are states of the register** (`screen=register`), extending
  `renderCart`/the paid stage and `renderProducts`.
- **Folders**: `settings/`, `connect/`, `receipt/`, `products/`, `tokens/` each get an
  `index.html` that redirects like `reports/index.html`, a `README.md` (§8), captures under
  `screens/`, and a `shoot.js` (§7). The register's own `shoot.js` gains the new register states.
- Edit `pos-register/index.html` in place, additions only: do not reformat, reorder, rename or
  delete anything that exists. The one permitted change to existing code is lifting the five
  categorical colours `--c1..--c5` from the reports block into the shared token block (§6).

## 2. Settings (`SP`)

Structure. Tablet and desktop: a page with a left list of the six sections (General, Tax,
Printing, Customer display, Barcode scanning, Theme) and the section's content as labelled rows
on the right, `max-width` about 720. Phone: the index list, then a sub-page with a back bar
(the app's own rule, `navigation-area/LEDGER.md` #1–#3: wide gets a rail, narrow gets an index
and a back bar). A row is label left, control right on tablet and desktop, stacked on the phone;
no divider between rows; a hairline and an uppercase small title between sections. This is
today's quiet layout (commit `69a36ee74c`) in the new tokens.

- **Saved.** Settings has no Save button; every change writes on the spot (INVENTORY §7.1 is the
  open question). Draw it: a check and the word "Saved" fade in beside the control for 1.2 s
  (opacity only), and the page header carries one line, "Changes save as you make them."
  Switch `saved`: `row` (drawn) / `header` (a "Saved · just now" line in the header instead) /
  `none` (today).
- **General**: the 15 controls of INVENTORY §2 in three sections (Store, Localisation, Currency
  and numbers). The four address rows (country, state, city, postcode) are drawn as mirrored
  value rows with "Set in WooCommerce, mirrored here." and "Open WooCommerce settings", the Tax
  page's treatment, not disabled inputs with no reason. "Restore server settings" stays at the
  foot as an outline destructive button; pressed, it opens a confirm sheet (it overwrites local
  changes; confirmation is for destruction), then a row-level "Restored" beat; its failure is one
  red line, "Couldn't reach the store · Try again".
- **Tax**: the four mirrored rows, the five editable ones, the docs link, "View all tax rates".
- **Printing**: printer rows (name, connection line, status dot + word: Ready / Not reachable /
  Built in), per row Test print (spinner, then a row line "Printed on Epson TM-m30" or "Sent to…"
  for 3 s; no toast), Edit, and a ⋯ with Copy setup report / Set default / Delete. Delete gets a
  confirm sheet (Forget display has one; parity). The empty state is the dashed card with the
  inventory's copy. Add printer opens the setup wizard as a slide-out panel from the right (the
  register's `.panel`; a full page on the phone): draw the `results` phase (found-printer cards
  with the pills Ready / Test needed / Office printer / No connection) and the `saved` phase.
  Edit opens the same panel with the form rows (name, connection segmented, network fields,
  Advanced disclosure closed). The Templates section: one select per template with the
  "Auto — Epson TM-m30" option.
- **Theme**: the prototype's nine themes as tiles with a live mini-preview each (a card, a
  primary button, a row of text in that theme's tokens), "System" first; then a **Scale** row: a
  segmented Compact / Regular / Spacious with an "Auto" option, one line under it, "Auto picks by
  device: phones compact, counters regular, large screens spacious." This makes the map's fog
  ("where the scale override lives in Settings") a concrete question; the mechanism is #289's.
- **Customer display** and **Barcode scanning**: at row level with their real rows and states

  word, "Play a sound on scan" revealing its block, the register-scanner mid-flow replacing the
  list, the test panel's four verdicts as one state each is too many: draw `detected` only).
- **Loading**: the section shell with no rows; skeleton treatment is #308's, do not invent one.

SCENES (strip State): `index` (phone only), `general`, `general-saved`, `general-restore`,

## 3. Connect (`CP`)

field and two buttons. No welcome paragraph.

- **First run**: label "Your store's address", placeholder `mystore.com`, Connect (primary,
  disabled until typed), and "Try the demo store" as a quiet button at the foot.
- **Discovering**: the button spins and one line under the field says what is happening, in
  order: "Finding your store…", "Checking WordPress…", "Checking WooCommerce POS…", "Saving…".
  The hooks already name these stages (INVENTORY §3); the screen never showed them. Anticipation.
- **Errors**: one red line and a docs link, verbatim from INVENTORY §3, one state each for: not a
  WordPress site, timed out, hosting block (HOST121), WooCommerce missing (AUTH321), update the

  Needs sign-in / Checking…), a "Sign in with WordPress" row, the stores as radio cards ("Store"
  when one, "Choose a store" when several, the empty line "No stores found for this user. Ensure

- **Several sites**: an accordion, one open, the chevron on the left, a user-count badge.

## 6. The token sheet (`TK`)

`?screen=tokens`: one long page, **computed from the live frame** (a probe element under each
`data-theme` × `data-scale`, `getComputedStyle`), never hand-typed, so it can never drift from
the file. Sections:

- **Colour**: rows are the tokens (`bg fg card muted muted-fg border primary primary-fg ring rail
  rail-fg rail-border destructive destructive-fg scrim ok ok-bg warn warn-bg bad bad-bg info
  neutral c1 c2 c3 c4 c5`), columns the nine themes; each cell a swatch and its oklch string.
  Contrast ratios computed (WCAG, from the resolved sRGB) for fg/bg, muted-fg/bg,
  primary-fg/primary, rail-fg/rail, fg/card, with a red mark under 4.5 (text) or 3 (UI).
- **Status set**: the five, with a computed line "identical in N of 9 themes".
- **Scale steps**: the README's seven numbers × three steps read from CSS, and the floor rule.
- **Type**: the ramp the file actually uses (grep it: the `var(--fs)*` multipliers and `--amt`)
  as a rendered specimen per step; the per-theme display and mono faces as specimens.
- **Motion**: `--t`, `--ease`, and every named beat in the file with its duration (the roll 420,
  the tear 320, the stamp, the tick 450, the panel), each with a play button.
- **Icons**: the rule by theme (decision 45) with six glyphs per set.
- Radius, hairline, the pop shadow.
- **Lift `--c1..--c5`** from the reports block into the shared token block (the same five on every
  theme; the reports block then reads them). This is the one edit to existing code.

Strip on this page: Theme highlights that column; Scale picks the step for the specimens.

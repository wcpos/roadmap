| Refunds | keep, row | refunds are separate WooCommerce records with date, reason, actor; the shipped Sales sum only follows refunds attached to the period's orders, so the real report is still to build |
| Discounts | **fold into Orders** | an order field (coupon and quick-discount totals) |
| "Voided" | **drop** | no such aggregate exists; payment voids, movement reversals and cancellations are three different things |
| Cash movements (row) | **fold into Closures** | see above |
| Deposits | **drop** | nothing in either repo: no endpoint, no field, no line type, no template, no plugin integration. It was the 2026-09-14 example of a plugin-registered report (#333) and should return only when such a plugin registers one |
| Registers | keep, row, only under All registers | redundant for one register |
| In store · Online | keep, row (flagged) | channel is order data (`created_via`); worth showing while the store sells online too; not in the audit table because the panels had dropped it |
| Hero companions | keep | current-period figures are backed; the comparison-period calculation does not exist yet |
| Print, Sales summary | keep | today a hard-coded local document; the plugin's generic `report` template is the intended home |

Template homes: `closure` (closure and X-report, which is a document variant of it, not a type)
carries payments, taxes, cash movements, corrections; `report` (tabular, groups, subtotals)
is the home for every Sales-side document once a producer feeds it; `receipt` is per order
and per refund; there is no `x-report`, `deposits`, `payments` or `taxes` template type.

Not yet built anywhere, so the prototype is ahead of the code: the comparison period, ranked
products, category sales, payment shares and counts, tax per rate on the Sales side, and
merchant templates in the Sales panels.

### Refunds, discounts and voids: important distinctions

**Refunds are separate records**, not merely an order status: the receipt builder explicitly iterates `WC_Order_Refund` objects and exposes dates, amounts, reasons, actors and returned lines (`P/Services/Receipt_Data_Builder.php:1513`, `:1544`). Refund proxy behavior exists, but its literal collection route is supplied by a registry absent from these exports; that route is **Unverified** (`P/API/V2/Proxy/Refunds_Proxy_Behavior.php:18`, `P/API/V2/Catalog_Proxy_Controller.php:109`).

The shipped Sales calculation only sums refund references attached to the selected original orders. It does not filter refund events by their own date, and it does not subtract refunds from `total` (`R/report/utils.ts:29`). Thus it is not an implemented “refunds occurring in this period” report.

**Discounts are order data:** coupon items, coupon discount/tax amounts and order discount totals (`P/Services/Receipt_Data_Builder.php:470`, `:500`). Quick discounts also use a coupon mechanism (`P/Services/Quick_Discount.php:3`).

**“Voided” is not an established order-report status here.** Order statuses come from WooCommerce (`P/API/V1/Data_Order_Statuses_Controller.php:50`). Payment rows can be `voided`; cash movements can be reversed; cancellation is separately recorded (`S/customer-display/ledger.ts:102`, `P/API/V2/Sessions_Controller.php:306`, `P/Services/Fiscal_Record_Writers.php:31`). An aggregate combining these meanings is **not found in either export**.

**Cash movements are not invented.** Supported types are `paid_in`, `paid_out`, `no_sale`, `void`; “To bank” is not a distinct type, but could be a paid-out reason (`P/API/V2/Sessions_Controller.php:280`, `:327`).

## 2. Deposits — direct answer

There is **no separate deposits report**, deposits endpoint, deposit-specific order field/line type, or named deposits-plugin integration **found in either export**. The only meaningful “deposit” text is an invoice preview’s customer note, “Invoice for catering deposit”—not a data model (`T/gallery/preview-data/invoice.json:10`). Order-linked payment rows and paid totals do exist (`P/API/V2/Payments_Controller.php:85`, `P/Services/Receipt_Data_Builder.php:614`). **Inferred:** a deposit represented as an order payment, ordinary line or plugin metadata would belong to Orders/payment data unless an integration supplied a distinct reporting contract. These exports do not establish any such integration, nor justify “comes from the server” or disabling Deposits offline.

### Sessions, closures and X-report endpoints

- **Sessions_Controller:** `GET/POST /wcpos/v2/sessions`; `GET /sessions/{id}`; `POST /sessions/{id}/status`; `POST /sessions/{id}/approve`; movement routes above (`P/API/V2/Sessions_Controller.php:35`). Detail returns movements and sales count, plus expected totals only with report permission (`:122`).
- **Closures_Controller:** `GET/POST /wcpos/v2/closures`; `GET /closures/last`; `GET /closures/{id}`; `POST /closures/{id}/print`; `POST /closures/{id}/recount` (`P/API/V2/Closures_Controller.php:31`). Detail adds corrections (`:156`); `/print` records printing rather than serving a standalone HTML template (`:139`).
- **X-report is server-backed as well as client-renderable.** `Receipts_Controller` supports `GET /wcpos/v2/receipts/{order_id}?document=xreport:{session_uuid}` and its `/pdf` counterpart. Resolution reads an open/counting session and builds a live document (`P/API/V1/Receipts_Controller.php:63`, `:99`; `P/Services/Fiscal_Record_Store.php:239`). V2 inherits those routes (`P/API/V2/Receipts_Controller.php:14`).
- A separate `/x-report` endpoint is **not found in either export**. The client also builds local closure/X-report documents and requests template type `closure` (`S/register-session/use-session-report.ts:36`, `:61`).

## 4. Backed but not shown

“Not shown” here means absent from the supplied panel/row descriptions; some information remains available inside the full closure document.

- **Shipping totals by method:** already calculated and printed by the old Sales summary, absent from the prototype’s listed sections (`R/report/utils.ts:95`, `R/report/generate-html.ts:170`).
- **Explicit gross versus tax-exclusive Sales totals:** old summary prints both; current “net sales” is `total - totalTax`, not a refunds-net measure (`R/report/index.tsx:105`).
- **Actual payment amounts, paid total, tendered/change and transaction references:** receipt data supports these; the Sales payment grouping uses whole order totals instead (`P/Services/Receipt_Data_Builder.php:631`, `R/report/utils.ts:66`).
- **Refund reason, refund date, refunding person, destination/gateway, returned lines, refunded fees/shipping:** available in receipt data, absent from the prototype’s simple refunds/discounts/voided table (`P/Services/Receipt_Data_Builder.php:1544`).
- **Fees, coupon detail and sale-price savings:** receipt data/templates have these distinctions beyond one discount total (`P/Services/Receipt_Data_Builder.php:456`, `:470`, `:578`; `T/gallery/detailed-receipt.html:153`).
- **Opening-float discrepancy, non-cash tender variances, perpetual sales/refund totals and unsynced monetary amount:** closure template details, beyond the summary drawer result (`T/gallery/closure-default.html:13`, `:17`, `:48`).
- **Report completeness warning and grouped subtotals:** generic report template capabilities not represented in the prototype inventory (`T/gallery/report-default.html:6`, `:10`).
- Dedicated **tips** data/reporting is **not found in either export**. Tax-per-rate, cash movements and corrections are already represented in the supplied page specification; they are not wholly missing topics.

## 5. Shown but not backed

- **Deposits amount, count, statuses and server-only/offline restriction:** implementation **not found in either export**.
- **An undifferentiated “voided” Sales total:** **not found in either export**; payment voids, movement reversals and order cancellation are distinct.
- **Comparison deltas/ghost comparison series:** comparison-period producer **not found in either export**; current order metrics are backed.
- **Top-products ranking and category sales tables:** aggregate producers **not found in either export**; raw product/order ingredients are not the same as an implemented report.
- **Payment shares/order counts and cashier average/share:** not produced by existing Sales `calculateTotals`; its payment grouping has amount only, cashier grouping count/amount (`R/report/utils.ts:142`, `:160`).
- **Sales tax “on £net” and rate net/tax/gross table:** absent from the Sales calculator, although equivalent fields exist in closure production/templates (`R/report/utils.ts:148`, `S/register-session/session-store.ts:269`).
- **Merchant-template-powered printing in every Sales detail panel:** generic renderer exists; live panel producers/integration are **not found in either export**.
- These are implementation gaps, not evidence that all underlying concepts lack data. The README explicitly describes fixture-based and synthetic behavior (`reports-README.md:153`, `:159`).

## Release notes (B2; B1 is empty — no app change ships)

Short form (`readme.txt` entry, free GitHub body via `release.yml`, Pro `CHANGELOG.md`):

- **Removing a coupon from a cart that had already been saved no longer makes Checkout fail.** Until now the next Checkout or Save was refused with "Coupon code is required" and the sale could not be completed until the coupon was put back or the cart rebuilt. This has been the case since coupons arrived in 1.9.0.

Long form (for the free GitHub body after Paul publishes, if wanted) adds the mechanism: the till marks a saved coupon line for removal the same way it marks a removed product, fee or shipping line, but WooCommerce handles coupon lines by code rather than by id, so the marker reached it as a coupon line with no code (HTTP 400). Both order lanes now read the marker as a removal; a marker for a coupon already gone is ignored. (#2153)

## Behavior changes carried into production

- Free #2153: a full-document order update whose `coupon_lines` carries `{ id: <stored coupon line id>, code: null }` now removes that coupon (both `wcpos/v2` push and `wcpos/v1`) instead of failing with 400 "Coupon code is required". Marker ids must be canonical positive integers; the v1 override honours markers only on an existing order. No other payload shape changes behaviour. If a couponed sale misbehaves at Checkout on 1.10.24, look here first; the client-side couponed-order hold (money-string compare, see the plugin memory `couponed-order-stuck-open-is-client-hold-deadlock`) is untouched by this train.

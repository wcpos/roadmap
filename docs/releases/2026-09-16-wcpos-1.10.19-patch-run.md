## What rides

Monorepo `v1.10.18...main` (release SHA `00b3763a`, merge of #2097 on top of #2094's merge `b28deafb`):

- [#2092](https://github.com/wcpos/monorepo/pull/2092) — products and variations refuse the FlexSearch index and answer catalogue search from a folded-text blob in the query package (one blob per collection instance, `indexOf` per term, set intersection for AND, kept fresh from `collection.$`); the persisted `*_flexsearch` collections for those two are swept on the next open. 143 MiB renderer heap / ~8 s index build at 20k products → +2 MB / 0.8 ms.
- [#2093](https://github.com/wcpos/monorepo/pull/2093) — docs only: CLAUDE.md records the 1.10.18 store builds' per-platform runtime versions (Android `050c0144…`, iOS `612a275d…`).
- [#2094](https://github.com/wcpos/monorepo/pull/2094) — `FocusedSkiaWeb` mounts a Skia canvas only while its screen is focused (Reports chart, Health trend lines); react-native-skia 2.6.2's web view re-arms `requestAnimationFrame` every frame while mounted, and the drawer keeps visited screens mounted, so an idle POS tab sat at 30-50% CPU. Paul rewrote it from a pnpm patch of Skia to this app-level gate because patching inside the installed Skia directory moved the native fingerprint (`rncoreAutolinking` hashes the whole package) and would have cut the 1.10.18 cohort off from OTA.

## Release notes (app v1.10.19)

- **Product search on large catalogues uses far less memory and no longer builds a search index at startup.** Product and variation search now answers from a compact text table instead of a full-text index that held about 143 MB of memory at 20,000 products and took about 8 seconds to build after each sync; the old index is removed from storage the next time the till opens. Search results are unchanged: every word you type still has to appear in the product name, SKU or barcode.
- **Leaving the Reports or Health screens no longer keeps the web app busy in the background.** On web and desktop, the charts on those screens kept a 120 Hz frame loop running after you navigated away, holding an idle POS tab at 30-50% CPU. Charts now exist only while their screen is on view.

Phone and tablet apps on the 1.10.18 store build receive this version as an over-the-air update: it downloads in the background and applies on the next cold start after that, with no store update needed. Older store versions must first update to 1.10.18 from the App Store or Google Play.

## Follow-up: `search-heap.spec.ts` is marginal since #2092

The tail-over-plateau gate (`MAX_TAIL_OVER_PLATEAU = 1.25`) has tripped on first attempt in three of the four `main` Deploy runs since #2092 merged (`eb2fc62b` pro 1.33 → retry pass; `dedbba9b` free 1.51 / 1.29 / 1.27, all three attempts, run red; `00b3763a` free 1.36 → retry pass). Before #2092 (`e962c8b6`) both projects passed first try (0.68, 1.12). The leak gate itself — retained-after-GC over the collected baseline — reads the same before and after (~55 MB after GC vs ~48 MB baseline, ratio ~1.15) in every run, and DOM nodes return to 634, so this reads as a changed GC oscillation under the blob (plateau window sampling a freshly swept heap at 84–116 MB, tail sampling before a sweep at 109–154 MB) rather than retention per committed search. It needs either a longer plateau window / more cycles or a look at whether the blob's `find().exec()` warm-up shifts the sweep cadence. Not a release blocker (the gate is green by its own retry rule and the after-GC gate is flat), but a red `main` Deploy on a docs-only merge is a false alarm waiting to burn a train's bundle gate.

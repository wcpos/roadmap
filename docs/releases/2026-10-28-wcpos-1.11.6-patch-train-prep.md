## Verdict

**Worth running; one item is a money defect.** Three reasons to run it, in order of weight:

1. **monorepo #2883** — the pay page's fallback poll counted an order with a blank or missing status as *paid*: a paid toast, the receipt, and the order's completion on an unpaid sale. A plugin filter that strips `status`, or a host's HTML 200 page, is enough to trigger it. Web and desktop (the pay page is the legacy order-pay flow; the native app uses the same component). Found by review, not yet matched to a Sentry row.
2. **free #2432** — on HPOS stores, the first POS read of any web or admin order *saved* it: the order was attributed to the cashier who opened it (`_pos_user_created`, never rewritten), its revision moved, and the till's next change to it answered 409 stale. Every save listener and webhook fired on a GET. Pro merchants already have this (Pro 1.11.7 bundled free's `main` tip); free merchants do not.
3. **free #2471** — a line added under a saved coupon left the coupon's discount at its old value, so receipts and the till showed a coupon amount that did not match the order totals (demo-site report, 2026-10-27; on `next` this is the CHECKOUT401 class).

Riding along: unpaid receipts no longer print a PAID row (app #2937 + free #2461, two halves of one fix), the splash bar in dark mode (#2985), the WooCommerce 11.3 variation read (#2472), Electron 43.8.1 (a security advisory, eMudhra certificates). Every monorepo change is `door:two-way`; the free changes are server-side behaviour fixes with no route, field, header or option change. Nothing is large: 8 production files on the monorepo side, 7 on free.

**Mobile gets a leg this time.** The 1.11.5 train skipped it (the scanner fix was web-only), so native is on the 1.11.4 OTA; #2883 and #2937 are platform-free and A4 says OTA.

- **monorepo #2937** — the local receipt derives `needs_payment`/`payments` from the order's own status against a named list (`pending`, `failed`, `pos-open`, `pos-partial`); those statuses exist on every 1.11.x plugin. - **monorepo #2985** — two className overrides on one screen.

Every 1.11.x app renders the server's receipt data through the same Mustache templates, which already branch on `{{#payments.0}}`, so an empty list is a shape every app accepts (it is what a template with no payments has always rendered). The Detailed Receipt's gallery `version` bump uses the gallery update offer that exists since 1.11.0.
- **free #2471** — server-side `recalculate_coupons()` after a line write; the response shape is unchanged, the coupon line ids survive (matched by code). Every app reads the same coupon lines, now with a discount that matches the totals.
- **free #2472** — the include lane's internal query clone clears `on_sale`; the dispatched request and response are unchanged.

## Risk read (each verified against the PR's diff and body, not carried from memory)

- **#2883 (pay page).** Four production lines; a predicate that now refuses blanks. The one way it can bite is a gateway whose success path hands the poll an order with no status, which is the case it exists to refuse. Low.
- **#2937 + #2461 (unpaid receipts).** Two deliberate behaviour changes, both in the safe direction — see the next section. Templates unchanged except the bundled Detailed Receipt's PAID heading moving inside the payments loop. Low.
- **#2432 (HPOS read saves).** Touches the uuid mint on the hot read path of every order on HPOS stores. The PR's HPOS test asserts the v1 mint before the v2 read. Risk is a uuid that fails to persist on some store type; the fallback is the same mint on the next read. Low–medium, and it has had two days in Pro 1.11.7's zip with no Sentry row against `wcpos-php@1.11.7` (none exist yet in the 7-day window at all; Pro's volume is small).
- **#2471 (coupon re-apply).** Runs WooCommerce's `recalculate_coupons()` on every line write to an order that has coupons and still needs payment. A paid order is never re-priced. Quick-discount coupons keep their intent through the existing hook. Risk is a third-party coupon plugin whose `recalculate_coupons()` behaves unlike core. Low–medium; the fix is what the 2.0 writer already does (#2470).
- **#2472 (WC 11.3 variations).** Clears one query arg inside the plugin's own query clone. Low.
- **#2985 (splash).** CSS. Low.
- **Electron 43.8.1.** A minor-line Electron update (43.5 → 43.8) inside the stable major; the desktop E2E lane covers launch. Low.
- **Train shape.** The full shape (bundle, app, free, Pro, desktop, OTA), last run on 2026-10-21 (1.11.4) end to end in ~65 min with jsDelivr 503s that resolved on re-probe. Nothing new in the mechanics.

## Behaviour changes / regressions (deliberate, from the PR bodies)

- **A receipt opened right after an online checkout, while the local order is still `pos-open` and the store's receipt data has not landed (the "Syncing" badge is up, Print is disabled), shows "Amount due" instead of PAID for those seconds, then upgrades to the store's PAID row.** This is the status the preview always had; only the payment block now agrees with it (#2937).
- **A `pos-partial` order (legacy partial-payment fee line) shows no payment row** where it used to show the remaining balance as a paid row. Both are wrong; this is the safe direction. Ledger-driven rows are `next` work (#2461, #2937).
- **An HPOS order read no longer fires `woocommerce_update_order` or the `order.updated` webhook** (#2432). Any integration that relied on a POS read to trigger those was depending on the defect.

## B1 — app notes (app 1.11.6 release body; desktop body = these lines + the desktop line + footer)

- **A sale is no longer marked paid when the store's payment check answers with an order that has no status.** The pay page's fallback check now waits for a real order status; an empty or blank one (a plugin filter, a host's error page) could mark the sale paid, open the receipt and complete the order before it was paid. (#2883)
- **A receipt opened from the device's own data for an order that still needs payment no longer prints a "PAID" row.** Offline, or in the moment before the store's receipt data arrives, a pending or open order printed "PAID <method> <total>" and the Invoice template hid its "Amount due". (#2937)
- **The loading screen's progress bar is readable on a device in dark mode.** It drew in the dark palette on the light loading screen (reported on Android Chrome); the custom themes are fixed there too. (#2985)

Desktop-only line (electron body): **Desktop: the app runtime is updated to Electron 43.8.1**, which carries Electron's mitigation for compromised eMudhra intermediate certificates (GHSA-jr5w-w6x2-84p9). (electron #554)

Footer: "Desktop build of WCPOS app **1.11.6**. Available for macOS (Intel + Apple Silicon), Windows, and Linux (`.deb` / `.rpm`)."

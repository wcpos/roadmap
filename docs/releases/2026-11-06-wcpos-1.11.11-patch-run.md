## B1 — app notes (app v1.11.11 release body; desktop body = the same lines + footer)

- **A sale with two coupons on a line whose price includes tax now totals exactly as WooCommerce does.** The till took the tax out of each coupon's discount separately, so a line could end a millionth off WooCommerce's figure; the discounts are now added up across the coupons and the tax taken out once. (#3294)
- **Reloading the POS no longer raises an "unknown tax rate" warning before the store's tax rates have been read.** On reload the saved order could arrive before the rates, and the warning and its log entry stayed after the rates arrived a moment later. The check now waits for the first real read of the rates. (#3265)
- **A store that is slow to answer when connecting is no longer reported as blocking WCPOS.** A connection probe that ran out of time was counted as proof of a host block; a timeout now says the site took too long to respond and the connection can be tried again. (#3297)
- **A 1.11 till that meets a store already on WCPOS 2.0 is told to sync before updating, with a link to the upgrade guide.** The update-required card now reads "Sync this till before updating; 2.0 does not carry over unsent sales." and links to "Upgrading to 2.0". (#3314)
- Developers: the app's translations come from the 2026.11.1-card tag (the 2026.11.1 set plus the card's two strings in 50 languages, #3314); comment cleanup in the image resolver (#3305).

Plugin update 1.11.10 (free, and Pro 1.11.12) ships alongside: a store running a plugin that returns nothing from WordPress's REST dispatch filter syncs its whole catalogue again, and PDF receipts cap images at 128 MB on every host.

Desktop footer: "Desktop build of WCPOS app **1.11.11**. Available for macOS (Intel + Apple Silicon), Windows, and Linux (`.deb` / `.rpm`)."

- **Both lanes publish to web-bundle `main`, and the retention is not lane-aware.** A 2.0 publish less than 24 h before a 1.11 one leaves `sqlite.worker.js` and `sqlite3.wasm` on the 1.11 bundle, and the lane tag script refuses it. Until #3330 is on `1.11.x`, a hand-trimmed commit with the build-commit first line is the workaround (the script parses only the first line: `chore(release): build web bundle (@main from monorepo <sha>, ref <sha>)`).
- **Chunk names are not content hashes across patch tags.** The Sentry release banner is stamped after Expo hashes the chunk, so every lazily loaded chunk keeps its name and changes one byte per patch. jsDelivr caches by path, and the previous train's verification seeds the edge, so a 1.11 lane's second patch after a verification is the first to trip. Until #3331 lands, the recipe is: `join` the two tags' trees by path, purge every path whose blob differs (`https://purge.jsdelivr.net/gh/wcpos/web-bundle@<lane>/<path>`, 72 paths took a minute, none throttled), then re-run the tag script once.
- **Codex reviews a PR again when it is readied**, and the merge hook waits for that second pass; readying the three draft bumps at D4 cost ~5 min each before their admin merges went through. Ready them as soon as the bundle tag exists.
- **The merge hook reads the first `repos/<owner>/<repo>` in the whole command.** A compound command that queried free's API before the Pro admin merge was walked as woocommerce-pos#777 (four unrelated CodeRabbit threads). Merge with a single-purpose command. The same hook also reads a heredoc's text, so a run record that quotes a merge command cannot be written through a Bash heredoc.
- **Forge can create two drafts for one tag** when its platform jobs finish within the same second; publish-linux got its own. Check `releases?draft=true` for the tag before touching the body, move the assets onto the draft that has the notes, and delete the other.
- **Publish a Forge draft through the API with `tag_name` in the same PATCH.** The `gh release edit` form does not find a draft by tag, and a `PATCH draft=false` alone published it as `untagged-…` for a minute. The PATCH that publishes must carry `tag_name`, `target_commitish` and `make_latest` together.
- **jsDelivr curl 56 resets** on the first verification pass were transient (a direct probe answered 200 a minute later); the script's "wait, then re-run once" was the right reading.

# 2026-09-28 — the `next` lane renumbered from 1.11.0 to 2.0.0

Not a release. The run record of the day the in-development release changed its number, so the
next person who meets a `1.11.0` in a PR title, a migration name or a run record knows what it means.

## Why

Paul, 2026-09-22: *"although it is v1.11.0 now I will be releasing it as version 2 to signify to
users that this is a major update."* The ruling on wcpos/roadmap#363 (2026-09-23) made that one
name everywhere and held the mechanical PRs for his yes. Paul, 2026-09-28: *"go ahead with the
version 2 change. Wherever you see 1.11.0 we're now changing that to 2.0.0."*

The reasons the ruling gives, in short: a release called version 2 but stamped 1.11 needs
translating forever in support; the release is semver-major on its own merits (WooCommerce minimum
5.3 → 9.0, app and plugin must match, the magnetic card reader removed, the register UI rebuilt);
the docs tree was already `2.x`; the update server's compatible-family rule is the first two
numbers, so `2.0` is a clean new family.

## Deliberately not changed

- **ADRs, retrospectives, run records, PR titles** keep `1.11.0`: dated records keep the name they
  were written under (vocabulary §3 in `CONTEXT.md`).
- **Two test assertions** that check `1.11.0` is below the new floor (`use-app-info.test.ts`,
  `exact-sku-leg.test.ts`), and the unrelated `uniwind@1.11.0` dependency pin.
- **Milestone objects** (`v1.11.0` in every repo): the sync owns them; drift expected.
- **#195's due date** (2026-09-18, passed): the date follows the work; Paul's to set.

## Knock-ons

- A released plugin loads the web bundle at `@2.0`, so the release train cuts `v2.0.x` web-bundle
  tags. dev-next is pinned to `@next` and is unaffected.
- Anything still saying `1.11` in merchant-facing prose from here on is a bug, not a lane name.

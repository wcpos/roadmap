## Headline content

**The stuck-cart class:** after a gateway payment the WooCommerce order completes on the server but
stays a `pos-open` cart on the till. Field reports correlated with non-HPOS (legacy CPT order
storage) stores. Fixed from both sides:

- App (monorepo #1752, #1759): the payment-received page's full order payload is now adopted into
  the local store through the same guard chain as the pull lane, instead of being discarded; the
  fallback server-truth poll heals the local doc too; and "paid" is a blocklist of unpaid statuses
  (`pos-open`, `pos-partial`, `pending`, `failed`, `cancelled`) so on-hold (cheque/BACS) and custom
  gateway statuses complete the sale.
- Free plugin (#1828): the received-page emission gate reads the order's real status rather than the
  gateway's configured status setting; a failed internal REST dispatch no longer becomes the
  payload; and `Sync\Order_Modified_Date::touch()` bumps `post_modified(_gmt)` on CPT meta-only
  saves so date-cursored sync can see them (HPOS already does this; the coupon equivalent already
  existed).
- Also in the app: SYNC181 / CLIENT144 error codes so "Storage call has not returned" and failed
  search rebuilds render as readable Logs entries (#1751).

Electron carries no desktop-specific change — its release exists to embed app 1.10.6 (desktop does
not follow the bundle).

## The one wrinkle: a docs merge superseded the release SHA on `main`

Monorepo #1753 (docs-only, `CONTEXT.md`) was merged to `main` 13 minutes after the release merge
`3f2459b8`, while `3f2459b8`'s push Deploy run was still building. Two things made this a non-event:

- `deploy.yml`'s concurrency group on `main` is per-run (`deploy-main-run-{run_id}`,
  `cancel-in-progress: false`), so a newer main push does **not** cancel the older run any more —
  the "superseded by a newer main push" failure from the 1.10.3-era gate no longer happens.
- `require-green-main` checks the push Deploy run **for the SHA you pass** (`monorepo_ref`), not
  the tip of `main`. So dispatch the bundle with the release merge SHA, never with `main`.

Paul: *"what are we waiting for??"* — the wait was `3f2459b8`'s E2E, which cannot change the
artifact (app content identical to the already-green `94cdb064` plus a version string and two
submodule pointers). Dispatched with `override_release_gate="I accept a red main"` and
`monorepo_ref=3f2459b8…`, same justification as the 1.10.6 run.

### Small findings worth keeping

- **Pass the release merge SHA as `monorepo_ref`, never `main`.** The gate checks the push Deploy
  run for the SHA you pass; `main` can move under you (a docs merge did, 13 min after the release
  merge) and its run will not be the one you want.
- **`deploy.yml` main runs no longer cancel each other** (per-run concurrency group,
  `cancel-in-progress: false`). The "superseded by a newer main push" failure mode recorded from the
  1.10.3 run is gone; a mid-release push to `main` now costs nothing at the gate.
- **The local `apps/electron` submodule is uninitialised** in `~/Projects/monorepo-v2` (its git dir
  resolves to the parent). A fresh `git clone --depth 50` into `monorepo-v2-worktrees/` is the
  cheapest electron release checkout and sidesteps the `core.worktree` trap entirely.
- **`gh pr merge` on electron is hook-gated on every review thread having a reply**
  (`merge-thread-walk.js`); resolving the thread alone is not enough. Codex flagged the same-tag
  release-notes trap on #398 — replied with the standing disposition.
- `cleanup-worktrees.sh` did not remove the three merged release worktrees (kept 1 / unmerged 1
  from its own cwd only); removed them by hand.

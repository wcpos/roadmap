## New Lessons (runbook corrections)

### Plugin repos now auto-release AND auto-deploy on push to `main`

This is the biggest process change since 1.9.3. Both `wcpos/woocommerce-pos` and
`wcpos/woocommerce-pos-pro` now have a `release.yml` that triggers on push to `main`:

- Merging a version-bump PR is **sufficient** — `release.yml` creates and **publishes**
  the GitHub release (non-draft) and builds/uploads the plugin zip.
- For the free plugin, publishing the release fires `wporg-deploy.yml`
  (`on: release: released`), so the **WordPress.org deploy happens automatically** with
  no manual publish step.

Consequences for the runbook:

- **Do NOT dispatch the `manual-release.yml` workflow** for the plugins anymore. Doing so
  races `release.yml` and creates a **stale duplicate draft** release (drafts can share a
  tag name). One was created and deleted during this run.
- The auto-created release body is generic (free: empty; pro: GitHub's auto "What's
  Changed" PR list). **Curate the release notes after merge** by editing the published
  release.
- Merge the **free** PR first and let WP.org deploy, then merge **pro** (pro's build pulls
  the free plugin via Composer, so free must be tagged first).

### Windows publish broke on a Visual Studio 18 runner image

The `windows-latest` runner image rolled to **Visual Studio 18**
(`18.6.11822.322`). The `@electron/node-gyp` bundled in electron-forge's rebuild cannot
classify major version 18 (`- unsupported version: 18`, `invalid versionYear: undefined`),
so it reports "Could not find any Visual Studio installation to use" and the native rebuild
of `@serialport/bindings-cpp` (new in 1.9.5) fails. macOS and Linux jobs were unaffected.

- Fix: pin `publish-windows` to `runs-on: windows-2022` (VS 2022 / v17, the known-good
  toolchain used through v1.9.4) — [electron#272](https://github.com/wcpos/electron/pull/272).
- A secondary symptom in the same failure: node-gyp's VS detection hit
  `ERR_CHILD_PROCESS_STDIO_MAXBUFFER` running `Get-VSSetupInstance | ConvertTo-Json`.
- **Open follow-up:** upgrade node-gyp/electron-rebuild to a version that supports VS 18,
  then return the Windows job to `windows-latest`.

### Full-platform Electron release — Linux is back

For the first time since v1.9.1, the Electron release published **all platforms**: macOS
Intel + Apple Silicon (`.dmg` + `.zip`), Windows (`Setup.exe` + `nupkg` + `RELEASES`), and
Linux (`.deb` + `.rpm`). The Flatpak/Linux decouple from the 1.9.3 cycle held up — the
`platform=all` dispatch published `.deb`/`.rpm` cleanly. Flatpak/Flathub remains a separate,
in-progress submission.

### jsDelivr `@1.9` resolved immediately this run

After tagging `v1.9.8` and purging `@1.9`, `@1.9.8`, `@v1.9.8`, and `@main`, the production
ref `@1.9/build/metadata.json` resolved to `1.9.8` (`x-jsd-version: 1.9.8`) and served the
new bundle **immediately** — no ~15-minute resolution lag like the 1.9.3 run. The new entry
bundle served via `@1.9` was confirmed to embed `1.9.4`. (Note: the previous version's
hashed entry file still returns 200 from edge cache since only `metadata.json`/`index.html`
were purged — harmless, nothing references the old hash once `metadata.json` updates.)

### Recurring "Update POT file" workflow failure (both plugin repos)

The `update-pot.yml` workflow fails on every push to `main` in both plugin repos at the
"Install dependencies" step: `wp package install wp-cli/i18n-command` → "Could not
authenticate against github.com" → exit 1, despite the earlier token-unset mitigation
(woocommerce-pos#1147 / woocommerce-pos-pro#313). The wp-cli phar's bundled Composer still
rejects GitHub's new token format. **Non-release-blocking** (translation metadata is bumped
separately by the translations-ci bot), but it should be fixed properly in both repos.

### Follow-up: sideloadable Android APK on the monorepo release

Customers asked for raw APKs to sideload. The `production` profile builds an `.aab`
(not installable), and Play-served APKs are re-signed/split by Play App Signing, so the
store's exact APK can't be retrieved. Solution adopted ([monorepo#598](https://github.com/wcpos/monorepo/pull/598)):
a `production-apk` EAS profile (`extends: production`, `buildType: apk`,
`distribution: internal`, `autoIncrement: false`) and an `apk` input on `build.yml`
(`no`/`attach`/`only`) that builds the universal `.apk` in CI and uploads it to the
monorepo version release. Use `attach` during a release dispatch, or `only` to backfill an
existing release without rebuilding/resubmitting the store bundles. **Caveat:** the sideload
APK is signed with the EAS upload key, not Google's app-signing key — different signature,
so it cannot update over (or be updated by) a Play install. iOS has no public sideload path
(TestFlight only).

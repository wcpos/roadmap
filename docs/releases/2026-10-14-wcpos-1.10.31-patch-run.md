## Behaviour changes carried into production

- **Sync, monorepo #2526 + free #2229:**
  - The deletion check reads `''` as `'0'` only for an empty bucket; the server now sends `'0'`.
  - Journal ids that are not safe integers > 0 (the Guest, id 0) are dropped on both sides.
  - Variation search falls back to a phrase search past the word/character limits.
  - A `rest_invalid_param` push is keyed by its reason.
  - A checkout timeout carries a `WriteOutcomeTimeoutError` with an engine status snapshot.
- **Storage, #2528 / electron #512 and #2536 / electron #513** (the worker moved):
  - Targeted recovery drops a damaged row in the server-rebuilt existence manifests.
  - Boot replay walks the changelog in file order (`PATCH_VERSION` 6), so a normal update no longer rebuilds every index on reopen.
- **Search, #2530:** flexsearch cleanup no longer re-indexes the DELETE events of compacted appends, so stale text no longer wins.
- **Android checkout, #2539:** a load followed by an error for the same URL is not a load, and the error page's `loading` event is ignored. A failed pay page reaches the Retry banner.
- **Android search, #2540:** a body cut short by our own abort is reported as the abort.
- **Free plugin, #2231 (load integrity):**
  - A fallback autoloader handles a class missing mid-update.
  - A WCPOS REST request that hits one returns 503 with `Retry-After`.
  - A daily check and a Site Health test compare files against the wp.org checksums (Pro's against its own `checksums.json`).
  - Star Online 401/403/404 are terminal.

## Incident: RxDB 17.6.0 shipped on `@1.10` (10:00 UTC)

- **What broke:**
  - The bundle `v1.10.41` runs RxDB 17.6.0. Every 1.10.x plugin loads `@1.10`, but a plugin keeps its OWN vendored worker; free 1.10.27 and older carry RxDB 17.4.0.
  - `rxdb/plugins/storage-remote/remote.js` answers a `create` whose version differs from its own with `RM1` (exact string match, not major).
  - So every web POS on a plugin older than 1.10.28 failed to open its database, the demo included. Paul reported it at about 09:55 UTC.
  - The root mistake was taking #2504 (rxdb 17.6.0) onto `main` as a patch. A2 recorded "worker moved", but nobody compared the worker's RxDB version.
- **Fix (Paul's call: pull Pro, pull the bundle off jsDelivr, bump to 1.11):**
  1. Pro `v1.10.28` returned to draft; `v1.10.27` re-marked as latest.
  2. Web-bundle tag `v1.11.0` created at `a40735b1` (the 17.6.0 bundle), `v1.10.41` deleted, and `@1.10` purged.
     - It read `1.10.40` at the first probe (10:02 UTC), including the plugin's `metadata.json?v=<old worker sha256>` URL.
     - The entry served is `entry-93564f3a…` (1.10.40's). **Web on older plugins was restored at 10:02 UTC.**
  3. Free [#2243](https://github.com/wcpos/woocommerce-pos/pull/2243) `release/1.11.0` (version bump only; same code as 1.10.28), admin-merged at `1371aa1c`.
     - Draft 412571490 was verified: header and `VERSION` 1.11.0, `Stable tag` 1.11.0, worker sha256 `17a8f577…` == the `@1.11` worker.
     - Paul published it; `wporg-deploy` green (10:07 UTC). SVN trunk and `tags/1.11.0` carry 1.11.0 and the 17.6.0 worker.
  4. Pro [#650](https://github.com/wcpos/woocommerce-pos-pro/pull/650) `release/1.11.0`, merged at `f6223b14`. `manual-release.yml releaseVersion=1.11.0` green; v1.11.0 published and latest (it vendors free `main` = 1.11.0).
  5. Notes (Paul: *"pretend like 1.10.28 never happened"*):
     - Free [#2244](https://github.com/wcpos/woocommerce-pos/pull/2244) and Pro [#651](https://github.com/wcpos/woocommerce-pos-pro/pull/651) fold every note under `1.11.0` and drop the 1.10.28 entries.

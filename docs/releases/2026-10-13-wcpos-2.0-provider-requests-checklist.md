# WCPOS 2.0 — provider and platform requests checklist

Paul, 2026-10-13: *"prepare a checklist for all the terminals and gateways that need requests and I will do them all when v2 is released."* This is that list: every approval, enrollment, registration or entitlement that has to be asked of a payment provider or an app platform before 2.0's card-terminal support reaches real merchants. It is not the release train (that is `RELEASE-CHECKLIST.md`); it is the paperwork around it.

Compiled from each extension's `next` lane, the research notes of 2026-10-05/06, tickets #113 and #427, and each provider's own developer documentation (Opus 5.5 research pass, 2026-10-13). Each line says who has to act:

- **Paul** — needs the business owner's identity, legal acceptance, 2FA or money. Nobody else can do it.
- **Session** — console clicks an agent drives with Paul's credentials once he says go (ruled 2026-08-31: those clicks are never handed back to him).
- **Merchant** — self-serve on the merchant's own provider account. Nothing for WCPOS to request; it belongs in the docs (listed here so the docs pages can be checked).

Tick a box in this file when done, with the date and the case or reference number.

## The three that gate anything

- [ ] **Apple — Tap to Pay on iPhone distribution entitlement** (Paul). Reply on Case-ID 22668722 and upload through Apple's File Uploader: videos of the New User Flow, the Existing User Flow and the Checkout Flow, plus the completed *App Review Requirements Checklist* (`https://apple.box.com/v/ttpoirequirements`). Development entitlement granted 2026-10-06; until the distribution grant, Tap to Pay runs only on registered test devices. **Cannot be filed yet:** the flows Apple requires (admin-only terms acceptance, the "How to Tap" tutorial, warm-up at launch, the awareness moment) are not built on `next`, and the flow design still waits on Paul's approval (#113).
- [ ] **SumUp — offline payments opt-in for the WCPOS integration** (Paul). Through SumUp's contact form to the Integrations team, accepting the offline terms (`https://developer.sumup.com/terminal-payments/sdks/offline-transactions`). SumUp then enables offline per merchant account. Unlocks offline on a Solo or Solo Lite over Bluetooth (Europe via Worldpay, Visa and Mastercard). Code is merged (sumup-terminal#55, monorepo#2495); the device run on #427 waits on this. Unknown: lead time, and whether each merchant must also ask SumUp.
- [ ] **Windcave — certification and VendorId** (Paul). Request a development account, run Windcave's HIT test scripts, receive the Certification Report, agree the VendorId and PosName (`https://www.windcave.com/merchant-attended-developer-hit`). Unlocks production for every Windcave merchant. Not started: the README says "pre-release — not certified", and the Vendor ID field is left empty "until Windcave issues one".

## Apple (iOS app)

- [ ] **Turn on the Tap to Pay capability for the production App ID `com.wcpos.main`** (Paul, 2FA) at `https://developer.apple.com/account/resources/identifiers`. It is on only for `com.wcpos.main.dev`; EAS cannot switch it on (Apple's API refuses the sync). Then a one-line code change: `app.config.ts` adds the entitlement to dev builds only.
- [ ] **App Store submission with the Tap to Pay declaration** (Paul): describe the use case, give App Review a test account, attach a checkout video, keep "Tap to Pay" out of the app name.
- [ ] **Any Tap to Pay announcement goes to Apple for approval before publishing** (Paul), Apple's toolkit assets only (`https://developer.apple.com/tap-to-pay/marketing-guidelines/`). Weeks of lead time.
- [ ] **Ask on the same case whether one entitlement covers several providers** (Session, by email on Case-ID 22668722). Stripe now, SumUp later; Apple's checklist names one provider per submission.

## Google Play (Android app)

- [ ] **Financial features declaration** (Session), Play Console → App content. Mandatory for every app and blocks updates until filed; whether a card-taking POS counts as "mobile payments" is a judgement to make on the form (`https://support.google.com/googleplay/android-developer/answer/13849271`).
- [ ] **Data safety form refresh** (Session) for location, Bluetooth and payment data now that the card SDKs are in the app.
- No Play policy specific to Tap to Pay or NFC; each provider's SDK checks the phone itself (Android 13+, GMS-certified, unrooted, developer options off for Stripe).

## Stripe

- WCPOS needs **no** Connect or platform registration: each merchant pastes their own secret key and the extension registers its POS webhook on save (`Pos_Webhook::ensure`).
- [ ] Docs check (Merchant): create a Terminal **Location** in the Dashboard and pick it in the gateway settings, one for test and one for live; without it Bluetooth and Tap to Pay fail with `stripe_location_missing`.
- [ ] Docs check (Merchant): buy readers at `https://dashboard.stripe.com/terminal/shop`; smart readers register with a code through the plugin.
- [ ] Docs check (Merchant): Tap to Pay on iPhone needs the merchant to link an Apple ID and accept Apple's terms in the app, once per Stripe account. Stripe has no separate enablement.
- Open question: whether WooPayments merchants (Stripe account under WooCommerce's platform) can use a third-party Terminal integration.

## SumUp

- [ ] **Decide: one WCPOS affiliate key, or each merchant's own** (Paul). SumUp's docs allow an integrator to own one key covering every merchant; the code as built asks each merchant for their own and `bootstrap()` refuses without one. If WCPOS owns the key: create it in the SumUp Dashboard (Settings → For Developers → Toolkit → Affiliate Keys) listing `com.wcpos.main` (`https://developer.sumup.com/tools/authorization/affiliate-keys`), then a code change to ship it. If merchants own theirs: the docs must tell them to add `com.wcpos.main` to the key (the 2.x docs on `main` have no affiliate-key guidance today).
- [ ] **Android Tap to Pay SDK credentials** (Paul, only if SumUp Tap to Pay is pursued after 2.0): "restricted pending review", requested through the Integrations team; its Maven repository needs credentials (`https://developer.sumup.com/terminal-payments/sdks/android-ttp`). Not in 2.0.
- [ ] Docs check (Merchant): Solo over the cloud needs an API key from the SumUp dashboard and a pairing code; no webhook to register (the result URL travels with each checkout).

## Square (cloud Terminal API only; Square's phone SDK is out of 2.0)

- [ ] **Keep WCPOS's two Square OAuth apps in order** (Paul, or Session with his login): production `sq0idp-zZjuiZ-…` and sandbox `sandbox-sq0idb-…` are hardcoded in `SquareOAuth.php`; the redirect URL `https://wcpos.com/api/square` must be registered on both and that endpoint must be live. Square describes no app review.
- [ ] Docs check (Merchant): optional webhook subscription in the merchant's own Square Developer app, signature key pasted into the gateway; polling works without it.
- [ ] Docs check (Merchant): pair the Terminal with a device code from the plugin; codes expire in five minutes; sandbox has no device codes.

## Mollie

- WCPOS needs nothing from Mollie: Connect onboarding applies to platforms only.
- [ ] Docs check (Merchant): enable the **Point of Sale** method on the Mollie profile and buy terminals in the Mollie Web App (NL, BE, DE, FR, UK); live API key only, since terminals exist only on live accounts; EUR only; no webhook setup. Open question: whether account verification must precede Point of Sale enabling.

## Mercado Pago

- WCPOS needs no partner or integrator ID.
- [ ] Docs check (Merchant): create an app under "Your integrations" and activate production credentials (industry, website, terms, reCAPTCHA); the extension asks for that app's access token.
- [ ] Docs check (Merchant): create a Store and a POS, link the Point terminal in the MP app and switch it to PDV mode (the plugin offers "Switch to PDV" but creates no store or POS).
- [ ] Docs check (Merchant): add the plugin's webhook URL under Webhooks with the "Order" event and paste the secret; unsigned calls get a 401.
- Status: never tested against a live account or a real terminal (README).

## Windcave

- [ ] Certification and VendorId: see the gating section above (Paul).
- [ ] Docs check (Merchant): HIT username and key (separate for test and production) and Station IDs, from Windcave sales.

## Payarc

- [ ] Docs check (Merchant): a Payarc account with Connect V3 access and five values Payarc supplies (MID, ClientSecret, SecretKey, a callback bearer token, a Payarc-confirmed terminal serial); the merchant may need to give Payarc the callback URL.
- Open questions: sandbox access, how terminals are provisioned, any ISV or partner terms, whether the callback URL is self-serve. Live behaviour was unverified in the design notes.

## WordPress.org

- Nothing to file. No extension is listed there; only `woocommerce-pos` is, and it is unaffected.

## Found on the way (engineering, not requests)

- `isInTapToPayProcess` is called nowhere in the app on `next`. Stripe's docs say `MainApplication` must return early on that check for Tap to Pay on Android, so Android Tap to Pay may not work as built (Inferred from the docs; needs a ticket and a device check).
- The Stripe extension's README on `next` still says Bluetooth and Tap to Pay are unsupported, while its device provider declares both.

## Not determined

Apple's re-review when a second provider joins the entitlement; SumUp's opt-in lead time and whether merchants must also ask; the Payarc questions above; Mollie account verification; Windcave's lead time; WooPayments compatibility with third-party Terminal; the right Play Financial features category.

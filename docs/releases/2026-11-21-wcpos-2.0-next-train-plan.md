## Should the app version move off 2.0.0? Yes, to 2.0.1

What the sidebar shows is `EXPO_PUBLIC_APP_VERSION`, which `app.config.ts` sets from `apps/main/package.json`. That file has read `2.0.0` at v2.0.0, at 33f23066 and at main. Every bundle since GA (v2.0.28–v2.0.34) and every desktop 2.0.1–2.0.4 therefore reports 2.0.0, and support cannot tell them apart.

A C1 bump makes v2.0.35 and desktop 2.0.5 report 2.0.1. It also creates the app tag that desktop's `.monorepo-ref` needs, which 2.0.4 lacked (it pinned a SHA).

2.0.1 follows the app line's own numbering. On 1.11, desktop 1.11.12 carried app 1.11.11, so the lines are not required to share a number within a patch lane. Matching the plugins' 2.0.5 would skip four app numbers that never shipped.

The bump does not move the mobile fingerprint: `fingerprint.config.js` skips app-config versions (verified with `@expo/fingerprint` 0.21.5, per the comment in the repo), so an OTA stays deliverable.

## A2b — patch-safe on 2.0 (0559ccbf content)

Verdict: **patch-safe: every line works with every other patch on 2.0**, judged against the 2.0.0 plugin.

- **#3706** feature-detects. The Cashier row is editable only when `useServerFeature('order_cashier_reassignment') && canReassignSales`. `useServerFeature` reads `capabilities` from `GET wcpos/v2/status` and returns false on any failure. Free's `Status_Controller` lists `order_cashier_reassignment` only from v2.0.5, so on 2.0.0–2.0.4 the Cashier row stays locked. The Store row needs only `canReassignSales` (`reassign_woocommerce_pos_sales`, in the Activator since v2.0.0). The store write is the meta push the cart's Order details already sends, and `persist_cashier_store_reassignment` with its filter exist since v2.0.0. No new request field, header or schema.
- **#3710** is client-side merge logic (`mergeProtectedOrderMeta` gains a `'read'` source). It reads `_pos_user` and `_pos_store` that every 2.0 plugin returns and sends nothing new.
- **Translations 2026.11.22**: 51 of 54 locales carry the five new `orders.*` keys. The other three show English for those strings.
- **#3711**: not judged here (Decision 0).

## Draft notes (per `woocommerce-pos/.ai/rules/release-notes.mdc`: no bold, PR numbers on GitHub)

### App v2.0.1 — GitHub release body (also the web bundle's notes)

> WCPOS 2.0.1 lets a manager change the cashier and store on any order from the Edit tab, and shows a change made elsewhere on the next sync.
>
> Upgrade and compatibility
> - Works with every 2.0.x plugin. Changing the cashier needs WCPOS 2.0.5 or later on the store; on older plugins the Cashier row stays locked and the Store row still works.
> - Changing either needs the reassign POS sales capability (administrators and shop managers by default).
>
> Added
> - Orders › Edit has Cashier and Store rows, each with its own Update button; a change the store refuses is rolled back, and every change is recorded on the order (#3706).
>
> Fixed
> - An order whose cashier or store was changed in WP Admin or on another device now shows the new values after the next sync, instead of keeping the old ones until local data was cleared (#3710).
>
> Developer and contract changes
> - The Cashier row reads `order_cashier_reassignment` from `GET wcpos/v2/status` capabilities; no new request field, header or schema (#3706).
>
> Maintenance
> - Translations 2026.11.22 (#3643); CI and test tooling (#3675, #3692, #3704, #3705).
>
> Web POS already received every earlier change since 2.0.0 in bundles v2.0.28–v2.0.34.
> Full diff: https://github.com/wcpos/monorepo/compare/v2.0.0...v2.0.1

### Desktop 2.0.5 — GitHub release body

> WCPOS Desktop 2.0.5 brings the app to 2.0.1: managers can change an order's cashier and store, and reports, register closing, checkout and the phone-sized layouts get the fixes web POS has had since 14 November.
>
> Added
> - Cashier and Store rows on Orders › Edit (#3706); a paid out larger than the drawer warns and asks again (#3617); reports show POS orders with no store under a "No store" scope (#3592).
>
> Fixed
> - Reports: money is grouped by currency, refunds of every store are kept, and orders paid in the window are included (#3588, #3593, #3595, #3600, #3601, #3602).
> - Register: a close is sent at once, and an interrupted close finishes at the next start (#3531, #3561, #3700).
> - Checkout and refunds: the store's default gateway is preselected, a refused tender raises attention, and a refund is a success only when the store created it (#3625, #3680, #3684, #3686, #3689).
> - Customer email and phone are masked in error reports (#3608, #3620, #3629); a changed cashier or store now syncs (#3710).
>
> Maintenance

## What broke: pnpm strict install vs @sentry/cli (the run's one real blocker)

`Publish Web Bundle` failed at `pnpm install`: `ERR_PNPM_IGNORED_BUILDS: @sentry/cli@2.58.6`.
Chain: electron #388 added `@sentry/webpack-plugin` → depends on `@sentry/cli` → the release PR's
`apps/electron` pin bump pulled it into the monorepo workspace → the **strict `allowBuilds` map**
(pnpm 11) fails the install for any ignored build script that is not explicitly listed. Deploy/E2E
runs passed on the same SHA because a plain install only *warns* — only the strict path fails
closed, so the breakage surfaced first in the release-critical workflow.

- Fix: monorepo #1749, one line — `"@sentry/cli": true` (true, not false: the postinstall downloads
  the binary the webpack plugin shells out to; `false` would pass installs while silently breaking
  sourcemap upload).
- **Pre-emptive twin fix:** electron's own `onlyBuiltDependencies` also lacked `@sentry/cli`, and
  its first Publish with #388 would have failed the same way mid-release. Added on the open #395
  branch — zero extra cycles. **Lesson: when a dep-allowlist failure hits one repo, grep the sibling
  repos' allowlists before their release workflows run.**
- Cost: one Merge Gate cycle (~35 min). Paul then waived the second E2E wait ("no need to wait for
  e2e tests") and the bundle was dispatched with `override_release_gate="I accept a red main"` —
  justified here because the app content was byte-identical to the already-E2E-green c5ca1636; the
  delta was one CI-config line.

## Translations folded mid-train (wcpos/translations#296)

Paul flagged the rolling Aide translation PR after the train had left. Not too late, and the right
move was to fold rather than defer:

- Every merge to translations `main` auto-cuts a date release (`release.yml`); #296 → `2026.9.3`
  within minutes of Paul merging it.
- The four repos consume it as a **one-line runtime pin** (`TRANSLATION_VERSION` in the plugins,
  `rxdb-backend.ts` in monorepo, `src/main/translations/index.ts` in electron). I pushed the pin
  onto all four **open release branches** directly and **closed the bot's four bump PRs** as
  superseded (monorepo #1748 first and fastest — a bot auto-merge to main mid-release would have
  superseded the bundle gate's E2E verdict).
- Only cost: the monorepo Merge Gate restart, which overlapped the queue anyway.

## The OPFS worker is now machine-checked — and it changes the tag order

Free has `opfs-worker-drift.yml` ("🧵 OPFS worker matches the bundle") since #1791-era: it compares
`assets/js/opfs.worker.js` against `build/opfs.worker.js` at the **highest v{major}.{minor} tag** of
wcpos/web-bundle (what jsDelivr actually serves) — not bundle `main`. Fails closed. This retires the
"remember to re-vendor" memory item as a manual step, but adds an ordering constraint:

**If the worker changed, the bundle tag must exist before free's drift check can go green.**
This run's worker did change (storage-recovery round 2; blob `017095ac` → `51f90b8f`), so the order
was: bundle build → vendor new worker onto free's release branch → **tag v1.10.15** → drift check
green → merge free. Tagging before the plugin merge is safe: the fleet always rolls ahead of
installed plugins, so bundle-vs-vendored-worker skew across one version must hold regardless.

Verification that matters: `git hash-object` of the vendored file vs the bundle blob SHA — matched
exactly, and again inside the shipped zip.

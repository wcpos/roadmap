## Release notes (app v1.10.16)

- **Search index repairs itself again.** When the app detected that its product search index had drifted from the product data, the rebuild silently did nothing, so stale or missing search results stayed that way until the app was reinstalled. The rebuild now runs.
- **Phone and tablet apps now update in place.** From this version on, fixes that only change the app's code reach iOS and Android without a trip through the app stores: the app checks on launch and applies the update the next time it starts.

## Mobile decision rule from here on (the new leg)

At the release SHA, compare against the runtime version **EAS recorded for the shipped build of
the same platform and profile** — `npx eas-cli build:view <build-id> --json` and read
`.runtime.version` from `apps/main`. Do NOT use a locally measured
`npx @expo/fingerprint fingerprint:generate` hash: an earlier version of this record did, and the
value it carried (`2d92b336…`) was both wrong and unreproducible on another machine.
**Runtime versions are per platform — there is no single production hash:**

| Shipped store build | Platform | EAS build id | Runtime version |
|---|---|---|---|
| 1.10.15 and earlier | both | — | no `expo-updates`; cannot receive updates at all |
| **1.10.16** | Android | `2c2a5601-5db5-44ea-abaa-aee8be4fe048` | `0aeafa6969b108dab0f4082f117bc8ee488238a5` |
| **1.10.16** | iOS | `98efef84-0804-4d91-ba9e-92b656b3302f` | `d02402d0a158a9b73e6c6666647eeef5e67a2887` |

To compare the working tree at the release SHA against those shipped builds, from `apps/main` — and
note the profile variable, without which the CLI evaluates the PRODUCTION config for every profile
(monorepo#2064):

```sh
EAS_BUILD_PROFILE=production npx eas-cli fingerprint:compare \
  --build-id 2c2a5601-5db5-44ea-abaa-aee8be4fe048   # Android
EAS_BUILD_PROFILE=production npx eas-cli fingerprint:compare \
  --build-id 98efef84-0804-4d91-ba9e-92b656b3302f   # iOS
```

Run it per platform and decide per platform; one platform can move while the other does not.

- Same hash → dispatch `publish-mobile-update.yml` (`monorepo_ref` = merge SHA, `channel=production`). No build, no store review; phones whose store binary carries the matching fingerprint pick it up on the next cold start after launch (a later store build with a new fingerprint starts a new cohort; older binaries keep the last update published for theirs).
- Different hash → `build.yml profile=production submit=true` as before, and record the new hash here.
- **CORRECTED 2026-09-16 — a `package.json` version bump DOES move the hash.** The claim that stood here
  ("identical at 1.10.15 and at a fake 1.10.99") was made with bare `@expo/fingerprint`, which is the
  wrong instrument. `eas fingerprint:compare` on the 1.10.17 train against both builds tabulated above
  reported a different runtime version on each platform, and the entire diff was the `version` line.
  So **these two binaries can never receive an update from this lane.** Fixed in monorepo#2087
  (`apps/main/fingerprint.config.js`, `sourceSkips: SourceSkips.ExpoConfigVersions`, scalar form);
  see `2026-09-15-wcpos-1.10.17-patch-run.md`. Codex raised exactly this as a P1 during #2056 review
  and was refuted on the strength of the wrong measurement; the reviewer was right.
- **The dev-client build broke on this train and was fixed in monorepo#2064** (merged `fb68e25f`).
  `eas build` computes the runtime version twice — once where it is invoked, once on the builder —
  and aborts when they differ. The CLI does not set `EAS_BUILD_PROFILE` locally, so `app.config.ts`,
  which has branched on it for bundle id, scheme, version and plugins since long before the OTA lane,
  resolved the PRODUCTION variant on the runner and the development one on the builder. Harmless
  before this train because there was no `runtimeVersion` to disagree about; `production` was
  unaffected because the config already defaults to `production` when the variable is unset.
  Fixed at the three callers (`e2e-native.yml`, both `build.yml` steps), NOT in `eas.json`: the whole
  of that file is a fingerprint source, so setting it there moves the production runtime version and
  would orphan the shipped 1.10.16 binaries from every future OTA update.
- `SENTRY_AUTH_TOKEN` reaches Actions as an organisation secret (`gh secret list` does not show org secrets, which misled this record at first; the web-bundle publish run 34957993473 read it and uploaded source maps), so OTA publishes will upload source maps too.
- Native E2E: `expo-updates` moved the dev-client fingerprint too; `e2e-native.yml` fails fast on the cache miss until a `build=true` dispatch rebuilds the dev client (Paul's call under the build cap).

# WCPOS Release Run Reference — 2026-07-24 (1.9.12 plugin-only patch)

A **plugin-only patch** of the free and Pro PHP plugins (no monorepo / web-bundle / electron /
mobile this cycle). Same-day follow-up to 1.9.11, shipping bug fixes to the Cloud Print feature
that 1.9.11 introduced plus a privacy-relevant behaviour correction. The notable event of this run
was **catching a missed Pro version marker at code review** — both Greptile and Codex independently
flagged that Pro's runtime `VERSION` constant hadn't been bumped, before anything shipped wrong.

## What shipped

All user-facing changes are free-plugin changes (already merged to free `main` since `v1.9.11`);
Pro carries them via the Composer bundle. This was a version-bump + curated-changelog release — no
new feature code was authored in the release branches.

- **Fixed cloud printing to Star TSP100 printers** — StarPRNT-native Star printers (the whole
  TSP100/TSP100IV line) rejected Cloud Print jobs with `510 Incompatible Media Type` and never
  printed, because WCPOS served them ESC/POS. WCPOS now serves native StarPRNT (new
  `Starprnt_Thermal_Emitter` + CloudPRNT media-type negotiation). First hit live at a customer's
  TSP100IV. Free [#1342](https://github.com/wcpos/woocommerce-pos/pull/1342). **Headline fix.**
- **Storefront receipt download is now opt-in** — the My Account → Orders Receipt button (shipped
  on-by-default in 1.9.11) is now off by default, with a UI toggle + template picker under
  General → Customers. A correction before the on-by-default behaviour spread. Free
  [#1338](https://github.com/wcpos/woocommerce-pos/pull/1338).
- **Cloud Print printer-name field no longer squeezed** by long/translated status labels — the
  status chip moved to its own row. Free [#1339](https://github.com/wcpos/woocommerce-pos/pull/1339).
- **Receipt template resolution fixes** — gallery templates resolve for customer receipt links;
  the storefront receipt uses the selected template; legacy metadata refreshed for template print
  jobs. Free [#1342](https://github.com/wcpos/woocommerce-pos/pull/1342).
- **Updated translations** — translation version `2026.7.7` in both plugins.

## The Pro dual-VERSION-marker catch (review gate earned its keep)

Pro has **two** independent version markers that both have to move every release, plus the free
Composer pin — the free plugin only has one:

1. `woocommerce-pos-pro.php` header `* Version:` (line 6)
2. `woocommerce-pos-pro.php` runtime `const VERSION` (line 30) — the `WCPOS\WooCommercePOSPro\VERSION`
   constant used for update checks, license metadata, REST/settings version reporting, asset
   cache-busting and DB-version bookkeeping
3. `package.json` `version`

The initial Pro bump commit moved the header + `package.json` but **missed `const VERSION`**, so a
1.9.12 install would have identified itself internally as 1.9.11 (repeated update prompts, stale
cached assets, skipped version-gated work). **Greptile and Codex both raised it as a P1** on Pro
[#389](https://github.com/wcpos/woocommerce-pos-pro/pull/389); every prior release (1.9.7→1.9.11)
had bumped this line, confirming the finding. Fixed in Pro `e9cbe37` before merge. CodeRabbit added
nothing this run — it hit its Fair-Usage rate limit and skipped review. **Free was unaffected** (it
has a single `VERSION` define, bumped correctly, and shipped clean).

## The Composer pin — repointed cleanly

Pro's release workflows pin free to an exact commit. Both `release.yml:72` and
`manual-release.yml:48` were repointed `dev-main#f386ba7c` (free 1.9.11) →
**`dev-main#895ca638`** (free's 1.9.12 `main` merge) as part of the Pro bump commit. Verified
post-publish: the shipped `woocommerce-pos-pro.zip` bundles `vendor/wcpos/woocommerce-pos` at
`Version: 1.9.12`.

**Follow-up still open:** drop the pin (let `dev-main` float) or derive it in-workflow from free's
`main` tip, so it can't silently rot.

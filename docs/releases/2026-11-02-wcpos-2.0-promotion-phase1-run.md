## What the plan got wrong

- **The Pro pin is `1.11.x-dev`, not `dev-1.11.x`.** Composer names a branch that looks like a version `<branch>-dev`; the first head of pro#749 carried `dev-1.11.x` and every PHP lane went red at `composer install`. Plan Phase 1.5 corrected in roadmap#498; memory `composer-pins-a-version-like-branch-as-branch-dev`.
- **Phase 5 said every 1.11 fix is merged `1.11.x` → `main`.** A branch merge would carry the patch line's version stamps, CI lists and the `1.11.x-dev` pin onto 2.0. Phase 5 now says what checklist F1 says: each fix that 2.0 also needs is re-applied to `main` through a PR of its own during the same run, and the run record lists them.
- **After 2.0 GA a 1.11 train must not move a public stable pointer** (GitHub `latest` for free, Pro and desktop; WordPress.org `trunk/` and `Stable tag`). The variant states the invariant; Phase 6 carries the mechanics (a `latest` input on Pro's `manual-release.yml`, a tags-only `wporg-deploy.yml`, electron `--latest=false`) before the first post-GA 1.11 train. Nothing of this applies during the beta, when the 2.0 beta is a prerelease.
- **Monorepo E2E on a `1.11.x` PR** was not in the plan: `deploy.yml`'s pull_request trigger has no branch filter, so a `1.11.x` PR would have run the web suite against dev-free/dev-pro on 2.0. #3190 skips both suites for base `1.11.x` and exempts it in both gates.
- Pro's `.github/scripts/test-tests-php-change-detection.sh` had been failing on every lane since the `translation_version_only` guard; nothing runs it in Pro CI. Fixed on `1.11.x` (#749) and `next` (#748).
- The `block-stacked-prs` guard (home hooks and the kilbot-guards mod) did not know `1.11.x` as a trunk; both now list it, with a test.

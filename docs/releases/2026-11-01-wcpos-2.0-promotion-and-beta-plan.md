# 2026-11-01 — WCPOS 2.0: promote `next` to `main`, keep 1.11.x alive, cut a public beta

**Status: plan, not a run record.** Written 2026-11-01 from the live state of every repo, the 1.10
promotion log (`2026-08-14-wcpos-1.10-lane-promotion.md`), the 2.0.0 renumber run and the patch
checklist. Nothing in it has been executed. The run record goes in a separate file when it runs.

Paul's ask: *"start the process of moving the next branch to main. We will still need to keep the
current main on a 1.11.x branch for a while, in case there are urgent bug fixes. After it has been
moved to main and I have tested on dev-free and dev-pro I want to release a beta for people to
start testing."*

## The shape in one paragraph

Four repos promote (`woocommerce-pos`, `woocommerce-pos-pro`, `monorepo`, `electron`); the seven
terminal-extension repos with a `next` branch (stripe, sumup, mollie, payarc, mercadopago, windcave,
square) do NOT promote yet (their `main` still serves 1.11 merchants through the
catalog, and their 2.0 betas already ship as prereleases from `next`). Before any promotion merges,
every repo gets a `1.11.x` branch at today's `main` tip, protected and wired into CI, so 1.11
patches keep a home. The promotion itself uses `promote/2.0` head branches, in the order bundle →
free → Pro → monorepo → electron, so dev-free and dev-pro never 404 and the main-lane E2E never
runs a 2.0 app against a 1.11 plugin. Paul tests on dev-free/dev-pro. The beta is then cut from
`main` as `2.0.0-beta.1`: GitHub **prereleases** for free, Pro and desktop (none of the three update
paths ever serve a prerelease), a `v2.0.x` web-bundle tag on the new `@2.0` lane (only a 2.0
plugin loads it), and store builds to TestFlight and the Play `beta` track. WordPress.org, the Pro
update server, desktop auto-update and the mobile `production` OTA channel all stay on 1.11 until GA.

Other facts the plan leans on, all verified today:

- Free `release.yml` already marks a draft **prerelease** when the header version contains `-beta`;
  Pro `manual-release.yml` already publishes a `-beta` version as a prerelease and never `--latest`;
  electron's `update.ts` skips update checks on any hyphenated version; `updates.wcpos.com` resolves
  Pro and desktop through GitHub `releases/latest`, which never returns a prerelease; WP.org deploy
  fires on the `released` event only, which a prerelease does not raise. The beta channel exists in
  the tooling already; nobody has used it on the core products (free last shipped a `-beta` at 1.0.0).
- The free plugin derives its web lane from its own version (`2.0.0-beta.1` → `@2.0`), and the 2.x
  loader asks `cdn.wcpos.com/manifest?ref=2.0` first, jsDelivr second. `publish-web-bundle.yml`
  runs the cdn job for a `bundle_branch=main` publish whenever the app major is ≥ 2, so the `2.0`
  lane on cdn.wcpos.com is created by the first 2.x publish to `main`. **That path has never run**
  for a released lane; the 1.11 plugin never used the manifest.
- `tag-web-bundle.sh` cuts `v2.0.0` on a new lane and, from then on, treats `1.11` as **frozen**:
  every later 1.11 bundle patch needs `allow_frozen_lane` on the publish and `--allow-frozen-lane`
  on the tag script. Deliberate, and the RxDB check still applies.
- The app's plugin floor (`MINIMUM_WCPOS_PLUGIN_VERSION = '2.0.0'`) compares with `semver.coerce`, so
  a `2.0.0-beta.1` plugin passes. **PHP does not agree:** `version_compare('2.0.0-beta.1', '2.0.0', '>=')`
  is false. Two places break on a beta Pro/free version and must be fixed before the beta is stamped
  (Phase 0, item 4).
- Pro's `release.yml` is still `disabled_manually` (left off since the 1.10 promotion), so merging the
  Pro promotion publishes nothing. Electron's push-to-main run builds Linux only and publishes nothing.
  Both safety switches from August still hold; no need to touch them.
- Merge gates in free, Pro and monorepo are promotion-aware (`promote/*` → `main` skips only the
  per-commit fix-bot discipline). "Protect next lane" deletion rulesets exist in all four repos
  (added after auto-delete ate `next` twice in August). Use `promote/2.0` heads anyway.
- The `requires_wcpos` updater gate (Pro #724, free #2490/#2495) **shipped today** in free 1.11.8 and
  Pro 1.11.10 (the 1.11.9 train record, A3). The extensions' 2.0 GA needs 1.11 sites to have taken
  that patch; the beta does not depend on it.

## Decisions taken in this plan (with the reasoning; say if any is wrong)

1. **Beta version string `2.0.0-beta.1`** on free, Pro and electron; the mobile app keeps the numeric
   `2.0.0` (App Store rejects a non-numeric short version; the beta there is the TestFlight/Play
   channel, not the number). Dotted `-beta.N` orders correctly in semver and PHP alike and matches
   electron's `-next.N` form; the extensions' `2.0.0-beta1` is re-stamped to the dotted form at their
   next beta cut. The alternative, stamping plain `2.0.0` and relying on "don't publish the draft",
   fails on day one: free's push run would create a non-prerelease `v2.0.0` draft that Paul publishes
   within a minute when he is watching, and Pro's `2.0.0` dispatch would mark `--latest`.
2. **Maintenance branch is `1.11.x`** in free, Pro, monorepo and electron, cut at each `main` tip
   immediately before that repo's promotion merges. Not `release/1.11`: the cut script creates
   `release/<ver>` branches per train and the name would collide in prose and hooks.
3. **The extensions do not promote now.** Their `main` is what the catalog serves to every 1.11 site;
   their 2.0 code is Pro-2.0-only and already reaches beta testers as prereleases. They promote at
   2.0 GA, after a 1.11 Pro patch carrying `requires_wcpos` has been out long enough.
4. **`next` is frozen from the promotion merge to GA.** Beta fixes land on `main`; a fix that also
   applies to 1.11 is cherry-picked to `1.11.x` (or lands there first and merges up). After GA,
   `next` is re-cut from `main` (the cycle Paul ruled on 2026-09-05).
5. **No OTA to `production` during the beta.** The 2.0 runtime fingerprint differs from the 1.11
   store builds (SDK 58 line), so the lane would most likely refuse it anyway; dispatching it is a
   production step with no beta upside.
6. **Bundle before plugin, plugin before app** (1.10 promotion + monorepo#2050): `@2.0` must resolve
   before dev-free loads it, and dev-free/dev-pro must run the 2.0 plugin before the main-lane E2E
   runs the 2.0 app against them.

## Phase 1 — the 1.11.x branch (per repo, immediately before its promotion merges)

3. **Workflows on `1.11.x`** (one PR to `1.11.x` per repo, the only non-patch change it will ever

4. **Free `release.yml` on `1.11.x`**: `git describe` gives `v1.11.8` on that branch, so the

8. **Repo docs**: each repo's `CLAUDE.md` "Branch lanes" section states three lanes for the beta

## Phase 4 — cut the beta (one session, ~half a day)

The order mirrors a patch train's D/E sections; every artifact is a prerelease and none of the
production switches (WP.org publish, Pro `--latest`, desktop latest, `production` OTA) is touched.

1. **App tag**: `gh release create v2.0.0-beta.1 --repo wcpos/monorepo --target <main SHA>
   --prerelease --title "WCPOS App 2.0.0 beta 1" --notes-file <B1 notes>` (no `--latest`). This is the
   tag electron's `.monorepo-ref` names.
2. **Web bundle**: if `main` moved since Phase 2.1, publish again from the beta SHA and let the
   script cut `v2.0.1` (bundle patch numbers are not merchant-visible; the four lines drift).
3. **Free**: the push-run draft `v2.0.0-beta.1` already exists; retarget check as in D6 (a draft reused
   across pushes keeps its first target — `release.yml` moves it on every push since #2003, verify
   anyway), download the zip, check header/VERSION/worker bytes/top-level folder (every zip is
   wrapped since WP 7.1.4), then **publish as a prerelease** — `gh release edit v2.0.0-beta.1
   --draft=false --prerelease` and nothing else. `wporg-deploy.yml` does not fire; WP.org stays 1.11.
4. **Pro**: `manual-release.yml --ref main -f releaseVersion=2.0.0-beta.1`; the workflow's own
   `-beta` branch publishes it as a prerelease without `--latest`. Verify `releases/latest` still
   answers v1.11.10 and that `updates.wcpos.com` offers nothing to a 1.11 site. The `CHANGELOG.md`
   top section is the beta's merchant-facing body; write it before the dispatch.
5. **Desktop**: one electron PR to `main` first, the C4 shape: `.monorepo-ref = v2.0.0-beta.1` (the
   tag from 4.1; a tag, never a SHA) and `package.json` `2.0.0-beta.1` if a beta-period fix moved it.
   Merge after the drift check reruns green against the tag, cancel the push Publish, then
   `tag-and-release.yml --ref main platform=all` → draft with 9 assets → publish with `--prerelease`,
   never latest. The prerelease build skips its own update checks and `updates.wcpos.com` never
   serves it. Strip the phone OTA paragraph the notes mirror copies.
6. **Mobile**: `build.yml platform=all profile=production submit=true` from the beta SHA (override
   phrase if the main Deploy is still running). iOS lands in App Store Connect as a build:
   internal TestFlight testers see it at once, external testers after Beta App Review; **do not
   submit the 2.0.0 version for App Store review**. Android lands on the `beta` track as a draft
   release (`eas.json`: `track: beta`, `releaseStatus: draft`); roll it out to the beta track in
   Play Console (the one step that needs Paul's console session or Codex computer use). Check both
   Apple agreement portals first (a train has 403'd on an expired one).
7. **Extensions**: no action; testers install the existing `2.0.0-beta1` prereleases by hand, which
   the Pro `wcpos_pro_requires` fix from Phase 0.4 lets start. Re-stamp to `-beta.2` dotted form at
   their next cut.
8. **Where testers get it**: one wiki/docs page ("Testing WCPOS 2.0 beta") linking the three
   GitHub prereleases, the TestFlight public link, the Play beta opt-in, the 2.x docs
   ("Upgrading to 2.0", "What's new"), the 1.11 → 2.0 requirements change (WooCommerce ≥ 9.0,

9. **Observability**: Sentry releases carry the version string, so `2.0.0-beta.1` events separate
   themselves; confirm the project's release filter shows it. PostHog likewise by app version.
10. **Run record** `docs/releases/<date>-wcpos-2.0.0-beta.1-run.md` with the patch checklist boxes

## Phase 5 — during the beta

- **Beta N+1** repeats Phase 4 from `main` with the next `-beta.N`; the free `release.yml` version
  check keys on `git describe`, so each stamp must actually change (a re-run on the same version
  skips the release).
- **1.11 patches** run the normal checklist from `1.11.x` with the frozen-lane flags from Phase 1.5,
  Pro dispatched with `--ref 1.11.x`, electron with `--ref 1.11.x`, OTA from a `1.11.x` SHA. Every
  such fix is also merged `1.11.x` → `main` in the same run (a fix that only lives on the patch
  line is lost at GA — the F1 lesson in the other direction).
- **The `requires_wcpos` gate is already in the field** (free 1.11.8 / Pro 1.11.10); the longer the
  beta runs, the more 1.11 sites have it when the extensions go GA.

## Phase 6 — GA (for the record; its own plan when the beta is done)

Re-stamp `2.0.0` on `main` (free's readme `Stable tag`, Pro `CHANGELOG.md` with free's notes, the
WP.org readme trimmed under 5,000 words), run the full train with every production switch on
(publish free → WP.org, Pro `--latest`, desktop latest, mobile submitted for store review, OTA
only if the fingerprint matches, which it will not for the first 2.0 store build), set
`requires_wcpos: "2.0.0"` on the extension catalog entries and promote the extensions, re-cut `next`
from `main` in every repo including translations (`git push origin main:next`), and re-enable
nothing: Pro `release.yml` stays disabled by design (Pro ships only by dispatch).

## Traps carried forward from the 1.10 promotion and the 2.0 numbering

- `promote/X.Y` heads, never `next` itself (auto-delete ate `next` twice).
- Pro's composer pin: flip to `dev-main` in the promote cut; and at the GA back-sync, flip it back
  to `dev-next` inside the sync merge commit (the lane check catches it only on the next push).
- A promotion PR re-litigates a cycle's worth of bot reviews; triage to issues and resolve the
  threads with links (rulesets require resolution), don't fix cycle-old code in the promotion diff.
- The main-lane E2E store selection is by `base_ref`; after promotion, `main` PRs test against
  dev-free/dev-pro on 2.0 — correct for 2.0, meaningless for a `1.11.x` PR (hence no dev site and
  local verification for the patch line).
- Pro's `dev-main` pin follows free's `main` wherever it points: every long-lived Pro branch needs
  its own free branch pin (`dev-next`, `dev-1.11.x`), or it silently vendors the wrong free.
- The monorepo bundle gate wants the **push** Deploy run for the exact SHA; `main` can move under
  you, so always pass the SHA, never `main`.
- WordPress.org propagation and a long-lived draft rotting its target are GA problems, not beta
  ones, but the free draft created at promotion will be weeks old by GA: delete it and let the GA
  push recreate it rather than retargeting.

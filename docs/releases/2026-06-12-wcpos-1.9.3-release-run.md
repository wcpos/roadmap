This document records the WCPOS `1.9.3` release train, run as a conducted session following the [2026-06-09 release run reference](2026-06-09-wcpos-release-run-reference.md) checklist. ## New Lessons (runbook corrections)

### jsDelivr semver-ref resolution caches independently of file purges

The plugin loads the app from `cdn.jsdelivr.net/gh/wcpos/web-bundle@1.9/build/…`. After tagging `v1.9.7` and purging `@1.9`, `@1.9.7`, and `@main`:

- `@main` and `@1.9.7` served the new bundle immediately.
- **`@1.9` kept resolving to `1.9.6`** — the semver→version *resolution* is cached separately from file content and lagged ~15 minutes despite repeated purges.

The 1.9.2 run only verified `@main` and the exact tag, so this gap went unnoticed. **Checklist correction: verify the exact ref style production uses (`@1.9`), looping on `x-jsd-version` until it reports the new version.** A re-purge + recheck loop every 2 minutes converged.

### Electron Publish on push builds Linux only

`tag-and-release.yml` triggers on push to `main`, but the macOS/Windows jobs are gated on `workflow_dispatch` inputs — a push run only attempts `build-expo` + `publish-linux`. For a full desktop release:

1. Merge the electron bump PR (after monorepo main is updated).
2. Cancel the redundant push-triggered run (it would only hit the Linux/Flatpak failure).
3. Dispatch Publish with `platform=all`.

The dispatched run published all macOS/Windows assets cleanly; the draft release created by Forge was published with notes after assets were verified.

### External-registry outages can paint release PRs red

Both plugin PRs failed their **Code Coverage** job because `pecl.php.net` returned "No releases available" for xdebug inside wp-env's Docker image build — twice, across retries, in both repos. The job is informational (not in the Merge Gate), so the PRs were merged with the red optional check after verifying the failure was external.

Fixed permanently afterwards: the coverage jobs now soften the env-start step and skip with a loud warning when wp-env+xdebug can't start ([woocommerce-pos#1145](https://github.com/wcpos/woocommerce-pos/pull/1145), [woocommerce-pos-pro#312](https://github.com/wcpos/woocommerce-pos-pro/pull/312)).

### Flatpak finally decoupled — Linux assets shipped

The Flatpak maker failure had blocked **all** Linux assets since v1.9.1 (one Forge invocation made deb+rpm+flatpak; one maker failure aborted everything before publish). Fixed in [electron#266](https://github.com/wcpos/electron/pull/266):

- `MakerFlatpak` is now opt-in via `WCPOS_FLATPAK=1`; default `publish-app` ships .deb/.rpm only.
- Flatpak is attempted as a non-blocking step chain (tooling install included — a Codex review catch: the apt install of flatpak packages also had to move out of the blocking step).
- On merge, the push-triggered run published `woocommerce-pos_1.9.4_amd64.deb` and the `.rpm` to the existing v1.9.4 release within 8 minutes.

Still open: the underlying `flatpak-builder` failure (the `DEBUG='electron-installer-flatpak*'` namespace didn't capture its stderr — try `DEBUG='@malept/flatpak-bundler'` or similar next run).

## Flathub Progress (post-release)

[electron#267](https://github.com/wcpos/electron/pull/267) finalized the Flathub submission assets against the real v1.9.4 `.deb` and added a `Flathub Validate` CI workflow that proved the full install path end-to-end (extra-data download → `apply_extra.sh` → binary in place). Findings worth remembering:

- **`apply_extra.sh` had a latent install-time bug**: it used `ar x`, but binutils is not in the Freedesktop *Platform* runtime where apply_extra executes (Sdk only). Rewritten with `bsdtar` (the com.google.Chrome pattern).
- **Runtime bumped 24.08 → 25.08** everywhere (manifest, `forge.config.ts`, publish workflow) — BaseApp `branch/25.08` verified to exist; 24.08 approaches EOL.
- **flatpak-builder-lint rules**: plain `--socket=x11` is rejected alongside `wayland`/`fallback-x11` (drop x11, keep fallback-x11); the app-id domain check (`appid-url-not-reachable`) fails because **wcpos.com returns 403 to `python-requests/*` user agents** (the linter's HTTP client) while serving browsers/curl normally — fix is removing that UA from the server's bot blocklist, or a Flathub linter exception at submission.
- **`StartupWMClass=WCPOS` was wrong** — measured under Xvfb in CI, the app's visible main window reports class `wcpos` (Electron derives it from the app name, not the productName). The validate workflow now asserts the `.desktop` value against the running app's visible window.
- **Validating flatpak-builder on GitHub runners** requires, in order: a D-Bus session (`dbus-run-session`), `sysctl kernel.apparmor_restrict_unprivileged_userns=0` (Ubuntu 24.04 AppArmor), and building to a local OSTree repo with the *install* done from the host (`flatpak-builder --install` runs apply_extra inside the Builder sandbox where nested namespaces are blocked).

**Submission must be made personally by the developer.** A first submission PR (flathub/flathub#8966) was opened by an AI agent with a custom description replacing the PR template; it was closed by a Flathub reviewer without review. Flathub's [Generative AI policy](https://docs.flathub.org/docs/for-app-authors/requirements#generative-ai-policy) explicitly bans AI tools from generating or opening submission PRs (repeat violations risk a permanent ban), and PRs that remove the template may be closed without review. The resubmission must: be opened by Paul from the browser (template auto-populates), keep and fill the checklist, use his own words, and follow a personal review of the `flathub/` files. Remaining besides that: resolve the wcpos.com 403, and verify the app via the wcpos.com domain or GitHub org after acceptance. `x-checker-data` is wired, so post-acceptance version bumps are automatic.

## Known Quirk To Watch

Every push to electron `main` re-runs `publish-linux` for the current `package.json` version. Once a version's deb/rpm assets exist on the release, a subsequent push-run's publisher may fail on duplicate assets. Harmless for the release itself, but it makes push-triggered Publish runs noisy — consider gating `publish-linux` on a version-changed check or tags instead of every push.

## B2 — plugin notes, two forms (identical bold leads)

### B2-short — `readme.txt` entry (free `release/1.10.26`; Pro `CHANGELOG.md` carries the same bullets)

= 1.10.26 - 2026/10/12 =

- **A sale through a gateway set to land on Pending payment or On hold now closes at the till.** The pay window no longer hangs on a checkmark with the order left in the cart; once the order reaches the status you stored for that gateway, the sale is done. Failed, cancelled and parked orders never close this way.
- **A bank-transfer, cheque or cash-on-delivery sale set to land on an unpaid status is no longer marked as paid.** Such an order was stamped with a paid date and counted as revenue in Analytics while nothing had been paid; it now stays unpaid until payment is recorded.
- **A server error quoted on the Logs screen keeps its comparison operators.** Only real HTML tags are stripped from the quoted text now.
- Updates the bundled Sentry PHP SDK to 4.33.2.

### B2-long — free GitHub body after Paul publishes (optional)

- **A sale through a gateway set to land on Pending payment or On hold now closes at the till.** A merchant who stores a gateway's POS Order Status as Pending payment (a pay-by-invoice workflow where the customer pays through the web pay link later) or On hold saw the pay window hang on a checkmark and the order stay in the cart until a forced reload; the received page only told the till "paid" when WooCommerce itself called the order paid. The stored per-gateway status is now the settled outcome: the received page emits for a POS order that has reached it, and the `payment-gateways` catalog exposes it as `settled_order_status` so the app applies the same rule to its fallback poll. Failed, cancelled, refunded and parked statuses are never a settled outcome whatever is stored; a web-checkout order keeps WooCommerce's own thank-you page; on a free-only site the stored status of a non-POS gateway is not acted on. On hold bank-transfer and cheque sales, which the 1.10.7 paid-only gate had left to the app's one-second poll, are emitted from the received page again. (woocommerce-pos#2164, monorepo#2461)
- **A bank-transfer, cheque or cash-on-delivery sale set to land on an unpaid status is no longer marked as paid.** The POS status filter also told WooCommerce's `maybe_set_date_paid` that the configured status was the paid one, so an order landing on Pending payment or On hold got a paid date and booked as revenue in Analytics with nothing taken. The date is now suppressed for that order when the stored status is not one WooCommerce calls paid; cash on delivery landing on Processing or Completed is stamped exactly as before. (woocommerce-pos#2163)
- **A server error quoted on the Logs screen keeps its comparison operators.** 1.10.28 began quoting the store's own error text, but dropped everything between a `<` and a `>`, so "Expected x < 5 and y > 2" read as "Expected x 2". Only real HTML tags (a known tag name followed by `name=value` attributes, comments, CDATA) are stripped now. (monorepo#2445, monorepo#2449)
- Updates the bundled Sentry PHP SDK to 4.33.2 (woocommerce-pos#2167); CI-only changes in woocommerce-pos#2160, #2166, #2168.

## Risk read

- **#2164 + #2461 (money path, both sides):** the new rule engages only when a merchant has explicitly stored a per-gateway POS Order Status; a gateway left at its default resolves to `''` server-side (the raw option is read, never the settings view that invents Completed) and the app rule reduces to the blocklist it always was. Failed / cancelled / refunded / parked are excluded on both sides and pinned by tests (mutation checks in both PR bodies: five cases fail without the exclusion). The app honours the stored status only for an order whose `payment_method` is that gateway, so a card gateway sitting `pending` cannot borrow a stored `pending`. Version skew is covered both ways (old app + new plugin: unchanged; new app + old plugin: field absent, unchanged). Evidence: free full suite 4,974 tests green at the merge, 27 new Received/contract cases red-before-green; app `payment-webview.test.tsx` 57/57. **Not verified live on a store** (dev-next serves `next`; the mechanism is a stored option + a received-page branch, both unit-covered). Codex and CodeRabbit were rate-limited on #2164, so its green checks there are not reviews; Greptile and an independent fresh-context pass were. Intentional side effect to watch: On hold bank-transfer/cheque sales now close from the received page instead of the one-second poll.
- **#2163 (every bacs/cheque/cod POS order landing on an unpaid status):** a `date_paid` suppression scoped to the order id, released on the order's own save with a `shutdown` backstop; paid statuses keep WooCommerce's stamping (COD → completed pinned). Behaviour change a merchant could notice: those orders stop appearing as revenue in Analytics on the day of the sale — which is the correct reading, and the reason for the fix.

- **`sentry/sentry` 4.33.2 (scoped vendor, runtime):** semver-minor SDK bump — rate-limit header parsing, a `data_collection` option that is opt-in (ignored unless set), request-body read limited to error events.

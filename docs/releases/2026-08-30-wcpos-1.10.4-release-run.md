## The new thing this run: `Require green main verification`

`Publish Web Bundle` now runs a pre-flight gate (`.github/actions/require-green-main`, review on
monorepo #1687) **before** it builds anything. It resolves the push `Deploy` run on `main` for the
release SHA and requires that run's `🎭 E2E Tests` job to have concluded `success`. There is an
override — typing `I accept a red main` into `RELEASE_OVERRIDE` — which was not used and should not
be, because tagging a bundle version rolls every 1.10.x install on next load.

This gate did not exist on the 1.10.3 run, so **the run order in the 1.10.3 doc is now wrong**:
"merge the monorepo PR, then dispatch the bundle" fails, because the Deploy run the merge triggers
has barely started. The bundle dispatch has to wait ~15 minutes for E2E.

**It refused twice, for two different reasons, and neither was a broken test.**

1. **First dispatch, ~10 seconds after the merge:** `main verification still in_progress`. Purely
   my own impatience.
2. **Second attempt:** `E2E verification was superseded by a newer main push`. The gate reads a
   *cancelled* run as failure and deliberately refuses to fall back to an older green verdict — the
   check comment says a PR or preview run of the same SHA verifies a preview, not the shipped
   artifact. Any push to `main` mid-release therefore costs a full E2E cycle.

## Two agents cut the same release two minutes apart

wcpos/monorepo#1703 (mine, `apps/main/package.json` 1.10.3 → 1.10.4) merged at 05:47. Paul's
wcpos/monorepo#1702, also titled for the 1.10.4 release, merged at 05:49 and touched
`apps/main/app.config.ts` + a new `app-config-version.test.js`.

They turned out to be **complementary, not conflicting** — #1702 bumped no version number; it made
`app.config.ts` derive the version from `packageJson.version` and froze `DEV_CLIENT_NATIVE_VERSION`
for the dev-client profile so a release-only bump does not churn the EAS fingerprint. `package.json`
stayed the single source of truth. But that was luck, not coordination, and the second merge
cancelled the first's Deploy run, costing the E2E cycle above.

**Lesson: confirm who owns the monorepo bump before opening a PR for it.**

## `raw.githubusercontent.com` is cached, and it lied

After the bundle built, `raw.githubusercontent.com/.../main/build/metadata.json` returned the
**old** entry hash (`entry-1b4a3052…`), identical to `v1.10.13`. Taken at face value that reads as
"the build produced nothing new" and would have led either to a pointless rebuild or to tagging
while believing the bundle was unchanged.

The commit was fine. Fetching the same path through the **contents API pinned to the commit SHA**
returned the real entry, `entry-ea724e67…`, and the commit diff showed 10 changed files including
`build/opfs.worker.js` — the #1697 storage fix landing.

**Rule: verify bundle contents via `repos/.../contents/...?ref=<full-sha>`, or with the commit SHA
in the raw path. Never via `raw.githubusercontent.com/.../main/...`.**

## Bundle tags are tags, not releases

The 1.10.3 doc and the standing note both say to publish the bundle with
`gh release create vX.Y.Z --repo wcpos/web-bundle …`. That is **not** what the repo actually
contains: `v1.10.0` is the newest 1.10.x *release object*, while `v1.10.1` … `v1.10.13` are all
lightweight commit tags with no release. jsDelivr only needs the tag.

`v1.10.14` was created to match, via `POST repos/wcpos/web-bundle/git/refs`.

## Run order that actually worked

1. Bump + changelog PRs on all four repos, opened together.
2. Merge free → merge Pro (Pro's `composer.json` resolves free's `main` tip at build time; no SHA pin).
3. Publish free's draft by hand → fires `wporg-deploy.yml`.
4. Dispatch Pro `manual-release.yml -f releaseVersion=1.10.4`.
5. Merge the monorepo bump → **wait for the push Deploy run's E2E to go green** → dispatch
   `Publish Web Bundle` → verify the built entry → tag → purge jsDelivr.
6. Merge electron → cancel the push-triggered `Publish` run → dispatch `tag-and-release.yml
   -f platform=all` → **write the release body while the draft is still building** → publish.
7. Create the monorepo release last, so its notes can name the real bundle tag.

## Traps that recurred exactly as documented

- **A push to electron's `main` does not publish.** The push run built the app and skipped all four
  `publish-*` jobs. Cancelled, then dispatched.
- **Electron's `release-notes` job mirrors the monorepo release with the same tag.** With desktop at
  1.10.5 and the app at 1.10.4 it would have written "Desktop build of WCPOS app 1.10.5". Pre-empted
  by writing the body by hand as soon as the first platform publish created the draft — the job
  skips a non-empty body, and it did.
- **Pro's `manual-release.yml` extracts the top `##` section of `CHANGELOG.md`** into the release
  body. Verified: the body matches the changelog entry exactly, no manual overwrite needed.
- **Pro's plain-text `CHANGELOG`** (no extension) ships inside the zip and was updated alongside
  `CHANGELOG.md`.

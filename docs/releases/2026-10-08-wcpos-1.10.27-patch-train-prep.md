## B2 — plugin notes, two forms (identical bold leads)

### B2-short — `readme.txt` entry (on free #2158 now; Pro #623 carries the same bullets)

= 1.10.25 - 2026/10/08 =

- **Saving or checking out a sale no longer fails with "Allowed memory size exhausted" on a store with a few thousand orders.** Since 1.9.0 every order save loaded the 200 most recent orders to guess which field holds VAT numbers; it now asks the database one small question instead.
- **A damaged row in the till's own bookkeeping no longer blocks the local database.** The till discards the row on the spot instead of refusing the read on every launch; sales, products and customers are never discarded this way.

### B2-long — free GitHub body after Paul publishes (optional)

- **Saving or checking out a sale no longer fails with "Allowed memory size exhausted" on a store with a few thousand orders.** Since 1.9.0 every order write that carried a `tax_ids` field (the till always sends one, usually empty) made the tax-ID detector load the 200 most recent orders with all their meta to guess which meta key holds VAT numbers, adding about 30 MB to a request that already sat near 115 MB on a plugin-heavy site with a 128 MB PHP limit. The detector now counts populated keys with one grouped query over the order meta table, and an empty `tax_ids` list no longer consults it at all. Reported 2026-10-08 on a store with 5,500 orders on legacy order storage. (woocommerce-pos#2157)
- **A damaged row in the till's own bookkeeping no longer blocks the local database.** When the till's storage finds a corrupt row in a collection it rebuilds on its own (its diagnostic log, health metrics, sync status and sync bookkeeping), it now discards that row on the spot instead of refusing the read on every launch. Sales, products, customers and the manifests the till audits itself against are never discarded this way. (monorepo#2429)

## Why a second plugin release in one day

Free 1.11.8 (published 14:32 UTC) carried #2505, which makes the store's `tax_based_on` mirror WooCommerce's "Calculate tax based on" setting. WooCommerce's default is the customer shipping address; a till sale almost never has one; and `Orders::get_tax_location()` copied the chosen address literally, so an empty one meant no country, no rates and 0.00 tax on every POS order saved server-side while the app still showed the tax. Seen first as the dev-free parity E2E going red on every `main` run after the 1.11.8 deploy (`line_items[0].total_tax` expected 2.50, received 0.00), including the merge-base run of an unrelated PR (monorepo#3184); dev-free's last passing POS order (10-31) carried `tax_based_on: base`, the failing ones `shipping`. The filter had carried the literal copy since the 1.10 line; #2505 made the branch reachable. `next` had the same code since the original #1953 (September) with no E2E lane to show it.

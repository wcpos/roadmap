## What the plan got wrong, corrected here

- **Pro's `db_upgrade()` has the same `'2.0.0' => update-2.0.0.php` loop as free's.** The plan said Pro's migrations key on an integer schema and are unaffected; they are not. pro#744 fixes both Pro sites (the extension gate and the update loop). Decision 7 / Phase 0.4 of the plan should read "three comparisons".
- **The pre-sync was not "free 2 behind, the rest 0".** The 1.11.9 train's F1 sync had already closed those; what was left was each repo's `2026.11.1` translation-pin commit (resolved to next's `'next'`) plus monorepo#3184 (Re-open refuses a paid order), which is the one real fix carried.
- **Translations `next` → `main` started no `pull_request` workflow on its first two heads** (#488 from `next`, then #489's first commit): on a 618-file PR GitHub fires the event before it has the merge commit, so Tests, Translation Quality and the required `dependency-review` never started while CodeQL and a `pull_request_target` workflow did. The `[skip ci]` on `next`'s bot tip was a red herring. A second commit pushed once mergeability was computed started them all. Written into the translations README (#490).
- **monorepo#3184 does not port to `next`.** Its ruling names `main` only; 2.0's ledger handles a re-opened paid order, and the port would refuse Re-open on part-paid 2.0 orders (`derive()` fills `transaction_id` at the first paid payment). The sync carries main's history and changes no file on `next`.
- **The bot's consumer pin PRs point at the 1.11 `main`s.** Closed with the reason; the `2026.11.2` pin goes into the promote cuts (Phase 2.0). The 1.11.x line stays on `2026.11.1`.

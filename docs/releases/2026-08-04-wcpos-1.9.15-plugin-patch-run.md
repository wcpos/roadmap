# WCPOS Release Run Reference — 2026-08-04 (1.9.15 plugin-only security patch)

A **plugin-only patch** of the free and Pro PHP plugins (no monorepo / web-bundle / electron /
mobile this cycle). Headline: **authenticated RCE via thermal receipt templates**. The fix was
already merged to free `main` (PR #1428) before this run — so this was a *release* run, not an
authoring run: version-bump both plugins, publish, verify.

## The vulnerability

`Receipt_Renderer_Factory` had no `case` for the `thermal` engine, so it fell through to the
default branch and returned `Legacy_Php_Renderer`, which writes the template content to a temp
file and `include`s it. Thermal template content is stored raw (kses-exempt via
`OFFLINE_CAPABLE_ENGINES`, because it is XML markup for receipt printers). That combination let a
user with `manage_woocommerce_pos` (eg: a shop manager) store raw PHP on a thermal template and
execute it by loading the receipt endpoint — **authenticated remote code execution**. Custom
receipt templates are a Pro feature, so Pro installs are the primary audience.

**Fix** (free commit `f90f3d59`, PR #1428): route the `thermal` engine to a new
`Thermal_Html_Renderer` that renders through the existing safe thermal pipeline
(`Thermal_Renderer::build_ast` + `Html_Thermal_Emitter`: Mustache → XML AST → HTML), mirroring the
already-safe `Template_Pdf_Service` path. The XML parser drops PHP processing instructions, so
embedded PHP can no longer execute; malformed markup fails closed. Follow-up commit `ae56c1cb`
(same PR) logs thermal render failures and constrains browser-printed HTML to the paper width.

## What shipped

- **Security: thermal receipt templates can no longer run PHP** — the RCE fix above
  ([free #1428](https://github.com/wcpos/woocommerce-pos/pull/1428), already on `main` at run start).
- **More reliable thermal receipt rendering** — render failures logged; browser HTML constrained

- **Dev-only:** phpcs-variable-analysis requirement bump (free #1425), also already on `main`.
- No translation bump this cycle (both stayed `2026.7.8`).

## Notes / catches this run

- **New Pro CI: `upgrade-notice-check.yml`** (added this cycle via pro #405). A `## Upgrade Notice`
  section in the release body is **optional**; when present, `updates.wcpos.com` extracts it and
  surfaces it as the in-dashboard update message to Pro installs. The check only **fails on
  near-miss headings** (eg: "Important Upgrade Notice") — the heading text must be exactly
  "Upgrade Notice" (any level, case-insensitive, emoji allowed). For this security release the Pro
  body carries an `## Upgrade Notice` prompting merchants to update. It re-runs on release edits;
  confirmed green after the body overwrite.
- **The two-step Pro pin worked cleanly again** (same as 1.9.14): placeholder = current free tip so
  CI runs, re-pin to the free release merge commit before merging Pro. Shipped Pro zip confirmed
  bundling free 1.9.15, not the stale 1.9.14 pin (`c4feb3ef`).
- **SSH to github.com still hangs on this machine.** Free clone is an SSH remote; fetch/push over
  explicit HTTPS URLs (`git fetch/push https://github.com/...`) worked. Pro clone is already HTTPS.
- **Baseline was clean** — no stale free draft releases; WP.org was on 1.9.14 before the run.

## Open follow-up — forward-port the RCE fix to `next`

the vulnerable factory fall-through. A separate PR should forward-port the thermal-renderer fix to

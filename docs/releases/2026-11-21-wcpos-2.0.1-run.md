## B1 — app v2.0.1 notes (GitHub release body; also the web bundle's notes)

> WCPOS 2.0.1 lets a cashier return an item inside a sale, lets a manager change the cashier and store on any order from the Edit tab, and shows a change made elsewhere on the next sync.
>
> Upgrade and compatibility
> - Works with every 2.0.x plugin. Changing the cashier needs WCPOS 2.0.5 or later on the store; on older plugins the Cashier row stays locked and the Store row still works.
> - Changing either needs the reassign POS sales capability (administrators and shop managers by default).
> - A returned item prints with its quantity and price on the store's receipt from WCPOS 2.0.5; older plugins print that line as 0 (the order total is right either way).
> - Known limit: on a reopened sale, moving a returned line to another product does not move its stock yet; the fix ships in the next free plugin patch.
>
> Added
> - A cashier can return an item inside a sale: the cart quantity keypad has a Return key that makes the line −1 (the minus key types it too). The sale must still total 0 or more; below 0, Checkout is refused and the cashier is pointed to Refund on the original order. A returned line takes no coupon discount, refunds nothing, and turns off Pick items in a split while it is in the sale; even and percent splits still work (#3652).
> - Orders › Edit has Cashier and Store rows, each with its own Update button; a change the store refuses is rolled back, and every change is recorded on the order (#3706).
>
> Fixed
> - An order whose cashier or store was changed in WP Admin or on another device now shows the new values after the next sync, instead of keeping the old ones until local data was cleared (#3710).
> - Orders changed elsewhere show on the Orders screen within a minute, and a manual sync re-reads the open order lists (#3711).

## Lessons

### Web bundles v2.0.28–v2.0.36 shipped app changes while the version users see stayed 2.0.0

Paul, 21 Nov 19:1x: *"previous web bundle builds should have been bumping the version, eg: in the sidebar"*.

What was verified on 21 Nov:

- **Where the displayed version comes from.** The sidebar footer (`packages/core/src/screens/main/components/drawer-content/version.tsx`: `v <appVersion>`, or `Version <appVersion>` on a phone, plus the App version row of the info panel) reads `useAppInfo().appVersion`, which is `AppInfo.version` from `@wcpos/utils/app-info`. On the web, `index.web.ts` takes it from `EXPO_PUBLIC_APP_VERSION`, which `apps/main/app.config.ts` sets to `apps/main/package.json`'s `version` at build time. On native, `index.ts` reads `Constants.expoConfig.version`, which comes from the same file. Nothing reads the web-bundle tag: the web-bundle repo's own `package.json` says 1.8.0.
- **What those bundles carried.** Bundles v2.0.28 to v2.0.36 were tagged between 10 and 21 Nov. Each `chore(release): build web bundle` commit names its monorepo SHA (`51e7c4351`, `17c283a69`, `44469e5d9`, `489d5e0b9`, `8fb27935a`, `1b372575d`, `33f23066d`; then on 21 Nov `7411220be` for v2.0.35 and `a5b8e2197` for v2.0.36, from Paul's publish dispatches 44917072494 and 44927085605 after he merged #3652 and #3718). `apps/main/package.json` reads `"version": "2.0.0"` at every one, and the live `updates.wcpos.com/web-bundle/2.0/bundle.json` for v2.0.36 (build `f631f79c`) says `"app_version":"2.0.0"`. The v2.0.34 entry chunk (`entry-51a31b57….js`) inlines `const t="2.0.0"` as `version`, `platformVersion`, `buildNumber` and the `WCPOS/2.0.0 (web; …)` User-Agent.
- **Effect.** A web POS on any of those bundles showed "v 2.0.0" in the sidebar, sent `WCPOS/2.0.0` to the store, and wrote App version 2.0.0 into log exports, the printer setup report and the order completion stamp (`stamp-completion.ts`). Nine bundles with different code were indistinguishable in support logs, receipts and screenshots. The first bump since 2.0.0 is this train's 2.0.1 (#3717), which ships as bundle v2.0.37.
- **Cost of a bump.** The 2.0.0 → 2.0.1 bump left both native fingerprints unchanged (A4 at `fc7fada39`: Android `b5747f6d`, iOS `ee732a81` match the 2.0.0 builds). So a version bump does not by itself force a store build or block an OTA.

**Proposed RELEASE-CHECKLIST follow-up (not made in this PR):** a web bundle publish on a released lane (`bundle_branch=main` or `<major>.<minor>.x`) is cut from a commit that bumps `apps/main/package.json` past the version of the last published bundle on that lane. D2 refuses a `monorepo_ref` whose app version equals that version, so the sidebar, User-Agent and logs always name a version that maps to exactly one bundle. Open question for Paul: should each bundle carry its own app patch (2.0.2, 2.0.3, … with a GitHub release each), or a build suffix that leaves the app release line alone?

## What rides

Thirteen merges on `main` since v1.10.16. Merchant-facing: #2070 (renderer memory leak — the
`*_flexsearch` destination retained up to 100 complete serialized index exports in RxDB's
change-event buffer; measured post-GC heap 46 → 404 MB in an hour before, 47 → 160 MB after),
#2057 (Logs screen freeze), #2065 (search terms in any order), `85ffed9f` (storage: single-instance
changelogs bounded, coverage rewrites reduced — **rebuilds `apps/main/public/opfs.worker.js`**),
#2072 (refresh snapshots with repeated records rejected rather than applied), #2074 (coverage history
bounded, oversized change buffers detected), #2071, #2067. CI/build only: #2064, #2068, #2063, #2062.

**The plugin legs were required, and scoping from memory would have missed them.** `85ffed9f` moved
the worker blob `5c46059e` → `4b78bf97`. The free plugin vendors `assets/js/opfs.worker.js` and the
web app loads the worker from the plugin, not the bundle — so web merchants receive the storage fix
only through a free release, and Pro follows because Pro vendors free. The first scoping pass of this
train tracked three merges and assumed a monorepo-only train; the tag diff (`compare/v1.10.16...main`)
is what caught it. Scope every line from its own tag diff, never from session memory.

## Ordering: a worker change inverts the tag order

Free's `opfs-worker-drift.yml` compares its vendored copy against `build/opfs.worker.js` at the
**highest `v1.10.x` tag** of web-bundle, and fails closed. So the order ran:

bundle build → vendor the new worker onto free's release branch → tag `v1.10.27` → drift green →
merge free. Tagging before the plugin merge is safe: the fleet always rolls ahead of installed plugins.

Verification was by **git blob SHA**, which is content-addressed and therefore identical across repos
for identical bytes: monorepo `4b78bf97` = bundle `4b78bf97` = free `4b78bf97` = the copy inside the
shipped Pro zip. The vendor script failed closed at three points (monorepo blob not as expected,
bundle blob not matching the monorepo, vendored result not matching the bundle). The worker is a
committed bundle that inlines patched rxdb-premium — **copy it, never rebuild it**.

## The mobile OTA lane cannot deliver — found here, not yet fixed

`eas fingerprint:compare` at the release SHA against BOTH shipped 1.10.16 builds:

| Platform | Shipped 1.10.16 runtime | Tree at 1.10.17 | Verdict |
|---|---|---|---|
| iOS (`98efef84-…`) | `d02402d0a158a9b73e6c6666647eeef5e67a2887` | `205413ba44f5c1e64d028f26c0d2d090711034ed` | DIFFERENT |
| Android (`2c2a5601-…`) | `0aeafa6969b108dab0f4082f117bc8ee488238a5` | `7d224673fb7e6f9a12af7a99a4c0d5bdbed4b36d` | DIFFERENT |

The **entire** reported diff on both platforms:

```
📝 Modified content: Expo app config
-  "version": "1.10.16",
+  "version": "1.10.17",
```

Every patch train bumps the app version, so as configured the lane stamps each update with a runtime
version **no shipped binary carries**. The update would publish successfully and reach nobody. Mobile
was therefore held rather than dispatched, and no store build was spent.

**This corrects the 1.10.16 run record.** That record states "A `package.json` version bump alone does
NOT move the hash (measured: identical at 1.10.15 and at a fake 1.10.99)". That measurement used bare
`@expo/fingerprint` and was the wrong instrument; the authoritative one is
`eas fingerprint:compare --build-id <shipped build of that platform and profile>`. Codex raised
exactly this as a P1 during #2056 review ("exclude version from the fingerprint") and it was refuted
on the strength of the wrong measurement. The reviewer was right.

**Fixed the same night in [monorepo#2087](https://github.com/wcpos/monorepo/pull/2087), merged
`e962c8b6` (2026-09-16 ~04:50 UTC).** `apps/main/fingerprint.config.js` sets
`sourceSkips: SourceSkips.ExpoConfigVersions`. It must be the **scalar**: `normalizeSourceSkips` in
`@expo/fingerprint` 0.20.8 silently drops non-string array entries, so the array form the spec asked
for would have normalised to `None` and shipped a no-op behind a green test — Codex (Astra) caught it.
Proof recorded in the PR: without the file a patch bump moved the runtime version on both platforms
(iOS `205413ba…` → `0a884f18…`, the same `205413ba…` this train's compare produced); with it, both
platforms held. The existing OTA contract test pins the skip by exact equality through the package's
own normaliser and goes red when the file is renamed aside.

**Consequence for the next store build:** the fix only applies to binaries built after `e962c8b6`. The
1.10.16 cohort can never receive an update. The first `build.yml profile=production submit=true` at or
after that SHA is the first OTA-capable cohort; record its per-platform `.runtime.version` in the
monorepo CLAUDE.md table when it ships. No store build was dispatched on this (1.10.17) train.
*Corrected 2026-09-16:* the 1.10.18 app release was cut at `e962c8b6` itself (the release commit was
already on `main` when #2087 merged), and its store build was dispatched from that SHA (`build.yml`
run 35059240821) — so the 1.10.18 store build **is** the first OTA-capable cohort, not a pre-fix one.
See `2026-09-16-wcpos-1.10.18-patch-run.md`.

### Notes worth keeping

- **Scope every line from its own tag diff.** This train was nearly run as monorepo-only because the
  session was tracking the three merges it had worked on rather than the thirteen on `main`.
- **A blob SHA is a cross-repo equality proof.** Vendoring was verified by comparing git blob hashes
  in four places rather than by waiting for the drift workflow, which is slower and no stronger.
- **Native E2E carried no verdict on this train.** It has reported `plan=rebuild` since the OTA lane
  landed — the dev-client fingerprint no longer matches any cached build, so the build job cancels
  rather than spend. A paid rebuild is the owner's call and was not taken.
- **A store submission remains the owner's call, not the train's** — reaffirmed here, where the
  honest answer was to ship nothing to phones rather than spend a build on a dead cohort.

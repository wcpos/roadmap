Partial train: app **1.11.5**, web bundle **v1.11.6**, desktop **1.11.5**. Free, Pro, mobile and the extensions do not move. Paul's go, 2026-10-22 ~18:14 UTC: *"ok, as you recommend"* to the recommendation below (an app patch rather than a quiet bundle-only tag).

## Why this train exists

One merchant-reported fix merged to monorepo `main` after the 1.11.4 train: [#2843](https://github.com/wcpos/monorepo/pull/2843), a keyboard-wedge scanner's trailing Enter re-pressed whichever button the cashier last clicked, so after a quantity change through the on-screen numpad the next scan reopened row 1's numpad and every later scan typed into it. The report was web **and Electron**. Paul asked whether to cut a patch or *"just quietly bump the web bundle"*. Recommended the patch because desktop embeds its own renderer from `.monorepo-ref` and does not follow the bundle: a bundle-only tag would have left the desktop merchants who reported it with the bug. Precedent: the 1.10.15 train (2026-09-15) was the same shape, one monorepo fix shipped as app + bundle + desktop, plugins skipped. A bundle built at the un-bumped tip would also have carried app version 1.11.4 under a v1.11.6 tag, which support could not have told apart.

## B1 — app notes (app 1.11.5 release body; desktop body = the same line + footer)

- **A barcode scan no longer reopens the cart quantity keypad on the wrong line (web and desktop).** After a quantity was changed with the on-screen keypad, the next scan reopened the keypad on the first cart line and every scan after that typed into it instead of adding the product. The scanner's closing Enter is now kept with the scan, so it never presses whichever button was last clicked. Scanning also works again with the barcode-scanner timing threshold set at or above 150 ms. (#2843)

## Notes worth keeping

- **A one-fix train runs in ~45 minutes of wall clock when nothing waits on a test**: go 18:14, bump merged 18:37 (the only wait was Codex's pass on the bump head, ~20 min; the merge-thread-walk hook holds the admin-merge until then), bundle dispatched and app release created 18:38, electron merged 18:39, web live 18:51, desktop published 18:58.
- **No jsDelivr 503s this run**: both the bundle publish's `@main` verify and the tag script's `@1.11` verify passed first time, so the 1.11.4 note ("read FAIL as re-probe now") was not needed; it still stands.
- **The merge hook treats a review-gate `success` on the head as Codex's pass**: the watcher that polled `pulls/<n>/reviews` for a Codex review never saw one (Codex posts through the gate's status, not as a PR review); watch `review-gate` on the head commit's combined status instead.
- **A Codex review stuck at "running" is unstuck by a NEW head plus a member-posted `@codex review`, never by re-requesting on the same head or by a fresh PR from it**: on #2855 the review sat at "running" for 90 minutes through one re-request, and #2857 (same branch and head) sat another 90. Pushing a new head (an API merge of the next `main` commit) made the gate's reason change from "Codex is reviewing (state: running); wait" to "a repository member must post `@codex review`" (an API merge commit does not trigger Codex's auto-review); the posted request completed in one minute. The gate reads Codex's state comment per head, so a stalled state on an old head holds every PR carrying that head. Don't hold the run record on it, and don't wait on it: refresh the head.
- **The 1.11.5 sync into `next` is not a version-only merge**: `next` had already changed `wedge-detector.ts` (#2846's `startedAtMs` de-dup timing), so main's stuck-latch re-arm and its three tests had to be merged by hand, and the ported tests assert the `onScan` payload with `expect.objectContaining` because next's payload carries one more field. See monorepo #2850's body.

## 3. Consistency rules the new collection must respect

- **Refund document versus summary:** embedded `refunds[]` remains the WC summary (`packages/database/src/collections/schemas/orders.ts:638–654`); detailed live refunds currently provide quantities/dates/actor (`orders/view/use-order-refunds.ts:9–31`). The collection is a third representation of the same refunds, not an additional amount to add to the summary.
- **Current parent write path:** refund POST does not locally patch `refunds`, `total`, `status`, or payments; it refreshes the parent (`packages/core/src/screens/main/orders/refund/use-refund-mutation.ts:100–132`). Pulled order payloads are stored through `packages/sync-engine/src/write-path/engine-order-repository.ts:85–139`; the server-side refund write implementation is **not found** here.
- **Payment allocation remains distinct:** `_wcpos_payments` parsing/writing is `packages/order-math/src/payments/ledger.ts:9,29–55`; per-payment refund entries have ID/amount/status/provider reference (`payments/types.ts:93–98,120–121`). Local payment constructors initialize zero refunds; terminal responses can replace ledger rows (`packages/core/src/screens/main/pos/checkout/payments/server/use-terminal-payments-service.ts:100–104,133`). A client function allocating WC refunds across payments is **not found**.
- **Different figures have different current authorities:** order net displays use embedded summaries; remaining refundable quantities use detailed live records; register expected/tender totals use payment allocations; fiscal refund receipts use server receipt data. Replacing a reader must not count both the replicated refund and its payment allocation.
- **Order total/status:** current consumers treat `order.total` as original total and subtract refunds separately. Refund-driven local writes to `status='refunded'` are **not found**. `packages/order-math/src/payments/derive.ts:30–34,60–70` derives payment status from captured/authorized amounts without subtracting refunds; it is not a refund-status calculator.
- **Session attribution:** current closure attribution follows payment-row `session_id`, and cashier breakdowns follow sale `_pos_user` (`packages/core/src/services/register-session/session-store.ts:200–208,300–313`). Refund occurrence session/actor are not read. The refund POST payload builder contains no register-session metadata (`orders/refund/use-refund-mutation.ts:37–60`).
- **Unsynced/local-first orders:** no persisted ID means the mutation throws `refund_requires_persisted_order` (`orders/refund/use-refund-mutation.ts:80–83`). Existing dirty/pending orders are protected from pull overwrite/deletion (`packages/sync-engine/src/write-path/engine-order-repository.ts:85–88,165–182`); adding refund replication must not silently bypass that separate parent protection.

## 4. Offline and sync edges

- **Today’s success path:** POST → forced targeted parent refresh → release handle → return POST data (`packages/core/src/screens/main/orders/refund/use-refund-mutation.ts:100–132`). Full refund response data is not persisted locally.
- **Refresh failure after success:** `use-refund-mutation.ts:116–127` logs but resolves, explicitly avoiding a retry that would mint another refund. Adding collection materialization must preserve this distinction between successful money movement and failed local refresh.
- **Offline:** the form has no explicit connectivity-disabled condition (`packages/core/src/screens/main/orders/refund/form.tsx:314,562,586`), but HTTP preflight blocks requests: `hooks/use-rest-http-client/index.ts:204–208` sets offline state and `packages/hooks/src/use-http-client/request-state-manager.ts:255–260` refuses it. An offline refund queue/local-first refund mutation is **not found**.
- **General journal:** refunds and orders are absent from `SUPPORTED_HYBRID_COLLECTIONS`; unknown rows are discarded while the cursor advances (`packages/sync-engine/src/change-signal/change-signal-source.ts:175–184,385–405`). Merely adding a schema cannot make refund journal events replicate.
- **Order checkpoint:** `packages/sync-core/src/customPullAdapter.ts:50–65` sends the order cursor to `/orders/pull`; `packages/sync-engine/src/scheduler/rx-scheduler-order-fetcher.ts:1210–1243` stores order documents and handles order deletes. This can refresh an embedded summary **if the server returns the changed parent**; whether refund creation advances that parent’s server journal entry is **unverified** here. It does not materialize a refund collection.
- **WP Admin deletion:** customer tombstones and coupon set-difference pruning exist (`packages/sync-core/src/applyReplicationActions.ts:368–374,507–518`); refund deletion handling is **not found**. Order `deletes` are parent-order IDs (`packages/sync-core/src/customPullAdapter.ts:40,97–105`), not a refund-deletion channel.

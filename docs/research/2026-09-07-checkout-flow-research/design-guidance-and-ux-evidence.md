# Cart → checkout transition: design-system guidance and UX evidence

Date: 2026-09-07

**Method.** Every claim was checked against the primary page cited next to it, fetched 2026-09-07. Apple's HIG and UIKit reference are client-rendered, so their text was taken from Apple's own JSON payloads (`developer.apple.com/tutorials/data/...`) behind the same URLs. Material 3's `m3.material.io` is an Angular app whose content could not be retrieved without a browser; Material is therefore cited from Google's server-rendered Android developer docs and the Material Components for Android docs, and anything remembered from the M3 spec is marked **UNVERIFIED**. Polaris has moved to shopify.dev; its Sheet and Modal pages were read from the Shopify/polaris repository source. Fluent 2's site is client-rendered; Drawer rules come from the Fluent UI React source. Wayback is blocked here. Candidates: **A** right-side sheet covering ~3/4 of the screen, **B** full-screen takeover, **C** centred modal dialog (current).

## 1. Platform design-system guidance

### 1.1 Apple Human Interface Guidelines

**Terms.** Modal surfaces are *sheets* (page/form sheet; iPhone sheets rest at *detents*), *full-screen* modal views, *popovers*, *alerts*. Side-by-side nonmodal content is a *split view* (two or three vertical panes on iPad) or a macOS *panel*. There is no side sheet in the HIG. https://developer.apple.com/design/human-interface-guidelines/modality · https://developer.apple.com/design/human-interface-guidelines/sheets · https://developer.apple.com/design/human-interface-guidelines/split-views

**Which to use.** A sheet is for "a simple task that they can complete before returning to the parent view." "For complex or prolonged user flows, consider alternatives to sheets. For example, iOS and iPadOS offer a full-screen style of modal view that can work well ... to help people perform multistep tasks." https://developer.apple.com/design/human-interface-guidelines/sheets — Modality: "Consider using a full-screen modal style for in-depth content or a complex task ... minimizes distractions"; but "Aim to keep modal tasks simple, short, and streamlined. If a modal task is too complicated, people can lose track of the task they suspended ... especially if the modal view obscures their previous context," and avoid "a modal experience that feels like an app within your app." https://developer.apple.com/design/human-interface-guidelines/modality — To keep the parent usable: "Use a nonmodal view when you want to present supplementary items that affect the main task in the parent view ... in iOS and iPadOS, you can use a nonmodal sheet." https://developer.apple.com/design/human-interface-guidelines/sheets

**iPad sizing.** "Prefer using the page or form sheet presentation styles in an iPadOS app. Each style uses a default size for the sheet, centering its content on top of a dimmed background view" (added 2024-03-29). https://developer.apple.com/design/human-interface-guidelines/sheets — UIKit: form sheet "displays the content centered in the screen. In a regular-width, regular-height size class, the system adds a layer with a Liquid Glass effect over the background content"; "The default content size is smaller than that of the page sheet style." Page sheet content "is roughly the size of a page, where the height is greater than the width." Both: "In a compact-width, regular-height size class, the system displays the view controller as a sheet with part of the background content visible near the top of the screen." Apple's sheets are centred or bottom-anchored, never side-anchored. https://developer.apple.com/documentation/uikit/uimodalpresentationstyle/formsheet · https://developer.apple.com/documentation/uikit/uimodalpresentationstyle/pagesheet

**Dismissal.** "Always give people an obvious way to dismiss a modal view ... a button in the top toolbar or swipe down." "Support swiping to dismiss a sheet ... If people have unsaved changes ... use an action sheet to let them confirm." Cancel leading, Done trailing; in multi-step sheets Back replaces Cancel and Done stays inactive until the last step (updated 2026-03-24). https://developer.apple.com/design/human-interface-guidelines/sheets · https://developer.apple.com/design/human-interface-guidelines/modality

**iPadOS windowing.** iPad windows are now freely resizable "similar to window behavior in macOS": "defer switching to a compact view for as long as possible ... prefer hiding tertiary columns such as inspectors as the view narrows." https://developer.apple.com/design/human-interface-guidelines/layout — The fetched HIG pages do not name iOS 26; the only Liquid Glass mention found is the UIKit form-sheet entry above.

### 1.2 Google Material Design 3

**Window size classes.** Compact `< 600dp` ("99.96% of phones in portrait"), medium `600–840dp` ("93.73% of tablets in portrait"), expanded `840–1200dp` ("97.22% of tablets in landscape"), large `1200–1600dp`, extra-large `≥ 1600dp`. https://developer.android.com/develop/ui/compose/layouts/adaptive/use-window-size-classes

**Canonical supporting-pane layout.** "The primary display area occupies the majority of the app window (typically about two thirds)"; "For medium width, split the display space equally ... For expanded width, give 70% of the space to the main content, 30% to the supporting content." "For compact-width displays, place the supporting content below the main content or inside a bottom sheet"; medium/compact may hide it "in a bottom or side sheet accessible by means of a control such as a menu or button." https://developer.android.com/develop/ui/compose/layouts/adaptive/canonical-layouts

**Side sheets** (Material Components for Android docs, linking to the M3 guidelines). "Surfaces containing supplementary content that are anchored to the side of the screen." *Standard*: "co-exist with the screen's main UI region and allow for simultaneously viewing and interacting with both regions." *Modal*: "present the sheet while blocking interaction with the rest of the screen"; they "render a scrim", dismiss on outside tap, "can be dragged horizontally and dismissed by sliding them off of the screen", and support predictive back. *Coplanar* (push) sheets "are not recommended for narrow screens." Sample width `256dp`. https://github.com/material-components/material-components-android/blob/master/docs/components/SideSheet.md — **UNVERIFIED** (M3 page unreachable): 256dp min / 400dp max width; modal side sheet becoming full-screen or a bottom sheet at compact width. https://m3.material.io/components/side-sheets/guidelines

**Bottom sheets, dialogs.** Modal bottom sheets "present a set of choices while blocking interaction with the rest of the screen"; default `maxWidth` 640dp. https://github.com/material-components/material-components-android/blob/master/docs/components/BottomSheet.md — "Basic dialogs interrupt users with urgent information, details, or actions." "Full-screen dialogs fill the entire screen, containing actions that require a series of tasks to complete." "Dialogs are purposefully interruptive, so they should be used sparingly." https://github.com/material-components/material-components-android/blob/master/docs/components/Dialog.md — **UNVERIFIED**: M3 dialog widths (280–560dp) and full-screen dialogs reverting to basic dialogs on large windows. https://m3.material.io/components/dialogs/guidelines

### 1.3 Shopify Polaris

**Sheet (deprecated), with the stated reason.** "A sheet is a large container that enters from the edge of the screen ... It doesn't interrupt their flow like a modal." Banner: "The sheet component encourages designers to create a new layer on top of the page instead of improving the existing user interface. It also blocks other parts of the UI, forces users to switch context, and adds complexity to otherwise simple interactions." Responsive: "At small screen sizes, the sheet component enters the page from the bottom of the screen. At larger screen sizes, the sheet component enters the page from the right side." Esc closes; focus moves in, "is kept in the sheet until it is dismissed", and returns to the launcher. "Best used in cases where the merchant needs to see elements behind it." https://github.com/Shopify/polaris/blob/main/polaris.shopify.com/content/components/deprecated/sheet.mdx

**Modal (now also deprecated for the App Bridge Modal API).** "Use modals for confirmations and conditional changes ... Don't use modals to display complex forms or large amounts of information." "Not have more than two buttons ... crowding on mobile screens." Sizes: small / default / large. No surviving "full page beats a modal" page; this is the closest rule. https://github.com/Shopify/polaris/blob/main/polaris.shopify.com/content/components/deprecated/modal.mdx · https://shopify.dev/docs/api/polaris

### 1.4 IBM Carbon

Dialogs: "Don't make modals full page. If a modal dialog needs more space than the large modal component allows then the content should be displayed on a page of its own ... A modal is not an alternative to page." "Don't use if additional information outside the modal needs to be consulted." "If a user needs to repeatedly perform a task, consider making the task do-able from the main page." Dismiss via primary action, Cancel, X, Esc. https://carbondesignsystem.com/patterns/dialog-pattern/ — Forms: "Use a dialog form when dealing with less than five inputs ... Use a side panel form when dealing with more than five inputs"; "dedicated-page forms can handle more complexity." https://carbondesignsystem.com/patterns/forms-pattern/ — Grid: "Slide-in side panels come into play when a user needs to reference the page along with the panel information to complete a task"; they push the content grid; sizes are IBM-internal. https://carbondesignsystem.com/elements/2x-grid/usage/

### 1.5 Microsoft Fluent 2 (Fluent UI React v9 Drawer)

"The Drawer gives users a quick entry point to configuration and information. It should be used when retaining context is beneficial to users." `OverlayDrawer` "blocks the screen and will require the user's full attention. Uses Dialog component under the hood" (inheriting Dialog's focus trap/Escape/backdrop rules); `InlineDrawer` "can be placed next to any content" and "does not take focus by default"; `Drawer` switches between them "for responsive design, so depending on the page viewport an inline drawer could become overlay." https://github.com/microsoft/fluentui/blob/master/packages/react-components/react-drawer/stories/src/Drawer/DrawerDescription.md · https://github.com/microsoft/fluentui/blob/master/packages/react-components/react-drawer/stories/src/Drawer/DrawerBestPractices.md — Sizes in source: small 320px, medium 592px, large 940px, full 100vw; `maxWidth: 100vw`; positions start/end/bottom. https://github.com/microsoft/fluentui/blob/master/packages/react-components/react-drawer/library/src/shared/useDrawerBaseStyles.styles.ts — Fluent 2 usage page itself: **UNVERIFIED** https://fluent2.microsoft.design/components/web/react/drawer/usage

### 1.6 Atlassian

"A drawer is a panel that slides in from the side of the screen." Banner: "We are planning on deprecating Drawer. Please use Modal instead." Remaining page content is client-rendered. https://atlassian.design/components/drawer/usage · https://atlassian.design/components/modal-dialog/usage

## 2. Implementation surface (React Native, Expo Router, React Navigation, web)

**Native stack `presentation`** (React Navigation): `card`, `modal`, `transparentModal` ("the previous screen will stay so that the content below can still be seen"), `containedModal`, `containedTransparentModal`, `fullScreenModal` ("can't be dismissed by gesture"), `formSheet` ("Uses `BottomSheetBehavior` on Android and `UIModalPresentationFormSheet` modal style on iOS"). "Only supported on Android and iOS." Sheet options: `sheetAllowedDetents` ("Android is limited to 3 detents"), `sheetLargestUndimmedDetentIndex`, `sheetGrabberVisible` (iOS), `sheetCornerRadius`. Android: "Nested stack navigators and `headerShown` are not currently supported inside form sheet screens." https://reactnavigation.org/docs/native-stack-navigator

**Native mapping** (react-native-screens): iOS `formSheet` → `UIModalPresentationFormSheet`, `transparentModal` → `OverFullScreen`, `containedTransparentModal` → `OverCurrentContext`; Android folds `modal`/`containedModal`/`fullScreenModal`/`pageSheet` into `MODAL`, `formSheet` into `FORM_SHEET`, both transparent styles into `TRANSPARENT_MODAL`. Mixing `contained*` with other modals "can result in a freeze or a crash." https://github.com/software-mansion/react-native-screens/blob/main/guides/GUIDE_FOR_LIBRARY_AUTHORS.md

**Consequence for a right-anchored sheet.** Every native sheet style is bottom-anchored on phones and, per Apple, centred on iPad (§1.1); Android's `formSheet` is a bottom sheet. Nothing in the stack exposes a side-anchored presentation, so candidate A must be a custom animated view inside a `transparentModal`/`containedTransparentModal` route (previous screen stays mounted and visible), or an in-screen layout change.

**Web.** react-native-screens gates native behaviour with `isNativePlatformSupported = ios || android || windows`; on web, screens are plain views. https://github.com/software-mansion/react-native-screens/blob/main/src/core.ts — Expo Router: "On web, screens with `presentation: 'modal'` or `presentation: 'formSheet'` render as regular stack routes." Recommended: `presentation: Platform.select({ web: 'transparentModal', default: 'modal' })`; "Expo Router keeps the previous route visible behind a transparent modal, so the route component only needs to render the backdrop and dialog", with `role="dialog"`, an Escape listener calling `router.back()`, and `unstable_settings = { anchor: 'index' }`. The old `EXPO_UNSTABLE_WEB_MODAL` implementation is removed. https://docs.expo.dev/router/advanced/web-modals/ · https://docs.expo.dev/router/advanced/modals/ — The JS `@react-navigation/stack` offers `card`/`modal`/`transparentModal` on web with `cardStyleInterpolator` and `gestureDirection`, but "Gestures are not supported on Web" and it "may not support ... form sheets". https://reactnavigation.org/docs/stack-navigator

## 3. UX evidence

**NN/g, modal vs nonmodal (Fessenden, 2017-04-23).** "Avoid modal dialogs that interrupt high-stake processes such as checkout flows." "Avoid modal dialogs for complex decision making that requires additional sources of information unavailable in the modal." "If it requires multiple steps to begin with, it probably justifies dedicating a full page to it." "A nonmodal window in Chrome on a desktop may become a modal one in Safari on an iPhone." https://www.nngroup.com/articles/modal-nonmodal-dialog/

**NN/g, overuse of overlays (Whitenton, 2015-05-25).** Benefit: "maintain the context of the current screen while providing some additional content or features." Costs: "anything more than a sentence or two creates complexity"; overlays "frequently break on mobile or on smaller browser windows"; Back "takes users not to the underlying screen, but to whatever page preceded that screen." https://www.nngroup.com/articles/overuse-of-overlays/

**NN/g, bottom sheets (Laubheimer, 2023-06-11).** Sheets "preserve substantial visibility of the underlying information" and help "when users are likely to need to refer to the main, background information", but "We strongly recommend not using a bottom sheet to replace typical page-to-page user flows"; a sheet "is meant to support quick interactions." Failures seen: "Lack of a clear way to dismiss", stacked sheets, swipe ambiguity; fix is a visible X plus Back. Mobile-only; no tablet or side-sheet findings. https://www.nngroup.com/articles/bottom-sheet/

**Baymard, checkout (Scott, 2023-09-27).** Across "multiple rounds of Baymard's checkout testing", participants "rely on order summary information to verify their data and selections", "sometimes finding critical errors", and in eye-tracking "routinely scanned the summaries of their prior steps throughout the checkout flow"; hiding them "adds friction" and "increases the risk of users eventually abandoning." Users also use Back to revisit steps. https://baymard.com/blog/accordion-checkout-usability — Mobile (Holst, 2013-10-01): the keyboard takes "close to 50% of the available screen space in portrait" and "70-80%" in landscape; the "extreme lack of page overview was observed to have severe implications." https://baymard.com/blog/mobile-checkout — No public Baymard article on tablet checkout or slide-in panels exists in its checkout collection. https://baymard.com/blog/collections/cart-and-checkout

**W3C ARIA APG, dialog (modal).** `role="dialog"`, `aria-modal="true"`, labelled by `aria-labelledby`/`aria-label`; "Windows under a modal dialog are inert"; Tab/Shift+Tab wrap inside; "Escape: Closes the dialog"; on open "focus is initially set on the first focusable element" (or the least-destructive action for irreversible steps); "When a dialog closes, focus returns to the element that invoked the dialog"; include a visible close button in the tab order. Mark modal only if code blocks outside interaction and styling obscures it. https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/ — A 3/4-width slide-over that traps focus is a modal dialog for assistive tech and must meet this.

**POS vendors.** Square's redesign post states goals only: "streamline the checkout process", "a consistent checkout experience across all of your POS devices", bottom tabs "to declutter your POS ... during busy business hours"; nothing on cart visibility during tender. https://squareup.com/us/en/the-bottom-line/inside-square/square-pos-redesign — The Square Design Blog index lists no POS/checkout article. https://design.squareup.com/us/en — No primary Toast design/engineering post on the order or tender screen was found: **UNVERIFIED**.

## 4. Small-screen adaptation rules

- Apple: form/page sheets in compact width become a bottom-anchored sheet "with part of the background content visible near the top of the screen"; in compact height, full screen. https://developer.apple.com/documentation/uikit/uimodalpresentationstyle/formsheet — "Avoid displaying popovers in compact views ... use all available screen space by presenting information in a full-screen modal view like a sheet instead." https://developer.apple.com/design/human-interface-guidelines/popovers — "Prefer using a split view in a regular — not a compact — environment." https://developer.apple.com/design/human-interface-guidelines/split-views
- Material: "For compact-width displays, place the supporting content below the main content or inside a bottom sheet." https://developer.android.com/develop/ui/compose/layouts/adaptive/canonical-layouts — Coplanar side sheets "are not recommended for narrow screens." https://github.com/material-components/material-components-android/blob/master/docs/components/SideSheet.md — **UNVERIFIED** (M3 spec): modal side sheet → full-screen or bottom sheet at compact width.
- Polaris: "At small screen sizes, the sheet component enters the page from the bottom of the screen." https://github.com/Shopify/polaris/blob/main/polaris.shopify.com/content/components/deprecated/sheet.mdx
- Fluent: drawers cap at `100vw`; `Drawer` exists so an inline drawer "could become overlay to save screen space" (§1.5).
- RN/Android: `formSheet` is a `BottomSheetBehavior` sheet, max 3 detents. https://reactnavigation.org/docs/native-stack-navigator

## 5. Synthesis

**A. Right-side sheet (~3/4 width), cart or summary visible.**
*For:* the only candidate consistent with Baymard's finding that shoppers "routinely scanned the summaries ... throughout the checkout flow" while still framing tender as a bounded task; NN/g's stated benefit of overlays; Fluent's "retaining context is beneficial"; Carbon's "reference the page along with the panel information" and "more than five inputs → side panel"; Material's supporting pane (70/30 expanded, 50/50 medium) is the nearest canonical layout, and Apple's "hide tertiary columns ... as the view narrows" says how it degrades.
*Against:* no platform offers a side-anchored native sheet (Apple: "Prefer using the page or form sheet presentation styles"), so A is a custom `transparentModal` view on every platform; Polaris deprecated exactly this component because it "blocks other parts of the UI, forces users to switch context, and adds complexity", and Atlassian is deprecating Drawer for Modal; at 3/4 width the visible cart is a strip, so it must be designed as a real summary; if it traps focus it is an APG modal dialog (Escape, focus return, inert background).
*Compact fallback:* Polaris and Material say bottom sheet or full screen; Apple says compact sheets are full width. A degrades to B on phones.

**B. Full-screen takeover.**
*For:* Apple's explicit recommendation for "multistep tasks" ("minimizes distractions"); Material's full-screen dialog is for "a series of tasks"; NN/g: multi-step flows justify "a full page"; Carbon: "A modal is not an alternative to page"; the only candidate with a native, platform-standard presentation everywhere and a plain route on web where browser Back works.
*Against:* it discards the context Baymard shows shoppers re-check, so the cart summary must be rebuilt inside it; Apple warns that obscuring "their previous context" makes people "lose track of the task they suspended"; iOS `fullScreenModal` "can't be dismissed by gesture", so Cancel/Back is mandatory.
*Compact fallback:* none needed.

**C. Centred modal dialog (current).**
*For:* Apple's default iPad presentation, zero custom code; the systems with explicit complexity thresholds reserve it for short, direct tasks or forms with fewer than five inputs.
*Against:* Polaris, Carbon, NN/g and Apple each steer growing or complex tasks away from a centred modal: Polaris "Don't use modals to display complex forms"; Carbon "If a modal dialog needs more space than the large modal component allows then the content should be displayed on a page of its own"; NN/g "Avoid modal dialogs that interrupt high-stake processes such as checkout flows"; Apple's form sheet is deliberately "smaller than that of the page sheet." "Too small" is the predicted failure, and enlarging the dialog to the screen is what Carbon forbids ("Don't make modals full page").
*Compact fallback:* UIKit already turns it into a bottom card sheet in compact width, so C collapses into a near-full-screen sheet on phones anyway.

**Net reading.** The systems split the decision on task length and on whether context must stay readable: short + no reference → C; long + reference needed → keep the context alongside the task; long + no reference → B. For WCPOS, the selected regular-width solution is an animated in-place column swap: keep the ledger in the existing right cart column and replace the left products column with tender. This preserves the referenced context without candidate A's custom side drawer or modal-dialog contract. At compact width, keep WCPOS's existing full-screen sheet with visible Back/Cancel and no swipe-to-dismiss.

## 2. Deciding a leak from noisy samples

Let `yᵢ` be a reading at time `tᵢ` (or at loop `i`), with the warm-up discarded.

- **Endpoint ratio** (used today): `R = y_end / y_baseline`, failing when `R > k`. It is simple and catches a step leak. It **fails** on one bad sample at either end, and its sensitivity shrinks with run length: a fixed `k` lets an 8-hour run hide a leak that a 12-minute run would expose. On an uncollected series it reads GC phase. `search-heap` found exactly this: window means and window minima both read collection timing (Observed, `search-heap.spec.ts` header).
- **Least-squares slope**: `b = Σ(tᵢ−t̄)(yᵢ−ȳ) / Σ(tᵢ−t̄)²`. Fail when `b` (MB/hour) exceeds a named constant. It **fails** in three ways:
  - The GC sawtooth is autocorrelated, so the textbook standard error is far too small. Never gate on its p-value (Inferred).
  - One outlier, such as a snapshot or a sync burst, levers the slope.
  - A step leak becomes a "slope".
- **Theil–Sen slope** ([Sen 1968](https://doi.org/10.1080/01621459.1968.10480934)): `b̃ = median over i<j of (yⱼ−yᵢ)/(tⱼ−tᵢ)`. It tolerates about 29% outliers. It gives a magnitude in the same units as OLS. It costs O(n²) pairs, which is trivial for n ≤ 1,000. **This is the slope to gate on.**
- **Mann–Kendall** ([Mann 1945](https://doi.org/10.2307/1907187)): `S = Σ_{i<j} sgn(yⱼ−yᵢ)` and `Var(S) = n(n−1)(2n+5)/18` (no ties), so `Z = (S−sgn(S))/√Var(S)`. A trend is present when `|Z| > 1.96`. It tests *whether* the series is monotone, not *how much*. Its failure modes:
  - With 960 samples a 1 MB/hour drift is "significant", so it must be paired with the Sen magnitude.
  - Autocorrelation inflates false positives unless the variance is corrected ([Hamed & Rao 1998](https://doi.org/10.1016/S0022-1694%2897%2900125-X)) or the series is thinned to one reading per GC cycle.
- **Sample choice under the sawtooth.** There are three options:
  - (a) A forced GC before each sample. It is clean but perturbs (see §1) and hides between-GC garbage.
  - (b) Troughs: the minimum per window. It **fails** when the window is shorter than the major-GC period. `search-heap` measured a period of about 10 cycles, so 5-cycle windows read a flank (Observed).
  - (c) Sparse forced-GC checkpoints plus an uncollected series that is gated only by a ceiling and a tail-over-plateau mean.
  - `tick-403-soak` already does (c) (Observed).
- **What memlab does:** a set difference, not statistics. It treats as leaked whatever was allocated during `action` and is still alive after `back`, after six forced GCs (Observed). This is exact for one reversible action, and blind to drift that the `back` step legitimately keeps (caches).
- **What Chromium does:**
  - Within a run, `memory.leak_detection` navigates `about:blank` → page → `about:blank`, then calls `Memory.prepareForLeakDetection` (which terminates workers, drops caches and runs GCs) and compares counters (Observed, [page_sets.py](https://github.com/chromium/chromium/blob/main/tools/perf/contrib/leak_detection/page_sets.py), browser_protocol).
  - Across builds, the perf dashboard does change-point detection: successive bisection with Mann–Whitney U and Kolmogorov–Smirnov tests, plus a Welch t-test per segment (Observed, [find_change_points.py](https://github.com/catapult-project/catapult/blob/main/dashboard/dashboard/find_change_points.py)).
  - Neither fits a slope inside a single run.

## 3. What the WCPOS soaks already do (Observed from file)

- **`playwright.soak.config.ts`:** two projects (`idle-soak`, `tick-403-soak`), 1 worker, no retries, Desktop Chrome, a list reporter, and a trace on failure. It passes no launch args, so there is no `--expose-gc`, no precise memory info and no Blink features.
- **`tick-403-soak.live.spec.ts`:**
  - It samples **every 30 s, not per minute**. Each sample reads `Performance.getMetrics` (`JSHeapUsedSize`, `Nodes`, `JSEventListeners`) plus a `longtask` observer count and sum.
  - It does **not** read `JSHeapTotalSize` or `Documents`.
  - Warm-up is 11 minutes and is discarded. At minute 11 it runs **one** `HeapProfiler.collectGarbage`, which is the post-GC "steady" baseline. It skips 2 re-warm samples, then takes uncollected plateau and tail windows of 4 samples each, followed by one final forced GC.
  - Gates: max heap ≤ 768 MB; tail mean / plateau mean ≤ 1.25; post-GC end / steady ≤ 1.25; nodes and listeners end / steady ≤ 1.5. It also requires the ticks to keep firing. It attaches a CSV.
  - It uses no slope, no Mann–Kendall, no snapshots and no LoAF.
- **`search-heap.spec.ts`:**
  - It samples per **cycle**, not per time. Each sample reads `JSHeapUsedSize`, `JSHeapTotalSize`, `Nodes`, `JSEventListeners` and long tasks.
  - There are 5 warm-up cycles, then a forced GC baseline, 2 re-warm cycles, and plateau and tail windows of 10 cycles each.
  - Gates: max ≤ 768 MB; post-GC / baseline ≤ 1.25; nodes end / plateau ≤ 1.5; long-task sum ≤ 2,000 ms with the harness GC's long-task time subtracted.
  - Its tail-over-plateau heap gate was **removed** because the 70–90 MB sawtooth made it read GC timing.
  - It is quarantined (G7).
- **`idle-backfill.live.spec.ts`:** it samples **no memory at all**. It asserts wire-traffic oracles (census probes, product trickle, variation prefetch) and logs counts every 15 s. #517's "Known" line says both live soaks sample heap and DOM; only `tick-403-soak` does.
- **The blind spot they share:**
  - RxDB storage runs in a dedicated module `Worker` (`packages/database/src/adapters/storage/index.web.ts:72`, Observed).
  - `JSHeapUsedSize` and the forced GC cover the page isolate only (Observed in source, consequence Inferred).
  - **So a leak in the storage worker is invisible to every WCPOS soak today**, though Chrome Task Manager's per-tab figure, the one the merchant read, includes it (Inferred).

## 4. Recommendation for the soak contract (#517)

**What to sample, smallest set (Inferred unless marked):**

1. **Every 30 s, uncollected:** `Performance.getMetrics` → `JSHeapUsedSize`, `JSHeapTotalSize`, `Nodes`, `JSEventListeners`, `Documents`. This keeps today's cadence and adds two fields that cost nothing. That is 960 rows over 8 hours, gated only by the absolute ceiling and by tail-over-plateau on means.
2. **At the end of every journey loop:** the LoAF sum (`blockingDuration`, count, and the top `scripts[].sourceURL`), Event Timing interaction durations (p50 and p95 per journey), and the long-task sum, kept for continuity with the 2,000 ms gate. Each row is keyed by journey name. This is the slow-mode signal: compare the p95 per journey in hour 1 with hour 8.
3. **Every 10 min:** `performance.measureUserAgentSpecificMemory()` in default mode, with `--enable-blink-features=UnrestrictedMeasureUserAgentSpecificMemory`. Record the page and `DedicatedWorkerGlobalScope` bytes separately. That gives 48 points, and it is the only cheap view of the storage worker. *Not evaluated:* that the flag is honoured by Playwright's bundled Chromium. Prove that first. If it is not, fall back to `worker.evaluate` with `--expose-gc`.
4. **Every 30 min, one checkpoint:** `HeapProfiler.collectGarbage` → the same reading as item 1, giving a post-GC series of about 16 points. Gate the **Theil–Sen slope of the post-GC series in MB/hour** against a named constant, and confirm it with Mann–Kendall on the same series. A short series has little autocorrelation, so the plain variance holds (Inferred). Gate the post-GC `Nodes` and `JSEventListeners` slope at about 0 per hour.
5. **Per-journey attribution:** after warm-up, run each journey **K times in a block**, bracketed by checkpoints, before the mixed day starts. The result is `(post-GC after K − post-GC before) / K`, in bytes per iteration, with nodes and listeners per iteration. That is memlab's `(STP \ SBP) ∩ SFP` idea measured as a number, without snapshots. The mixed, day-weighted loop then measures drift. Interleaved journeys cannot be told apart by slope alone.
6. **Electron:** add `app.getAppMetrics()` every 10 min through `electronApp.evaluate`, with per-process `workingSetSize` for the `Tab`, `GPU` and `Browser` processes. Everything else reuses the same CDP code via `electronApp.context().newCDPSession(window)`. *Not evaluated* on the WCPOS app.
7. **Artifacts:**
   - The CSV, as today.
   - **One** sampling heap profile (`HeapProfiler.startSampling` / `stopSampling`) over the last loop block.
   - Heap snapshots (`s1/s2/s3` plus `snap-seq.json` in memlab layout) only when a gate is red, or once at the end. memlab `findLeaks` reads them offline on a machine with about 8 GB free for Node.

**Leave out:**

- **A forced GC per sample.** It is up to 7 full GCs with footprint reduction each time. It hides the between-GC garbage that was the merchant's failure, distorts V8's own scheduling for the rest of the run, and adds harness long tasks to the main-thread numbers (Observed mechanism, Inferred effect).
- **Heap snapshots or `memlab run` on a cadence.** Each snapshot is a forced GC plus a seconds-long freeze plus a file several times the heap, and its analysis needs about 8 GB. `memlab run` brings its own Puppeteer and a single action/back model, not a cashier day.
- **`performance.memory` and `Memory.getDOMCounters`.** The first is bucketised and refreshed every 20 minutes without a flag, and it duplicates CDP with one. The second reads the same counters as `getMetrics`.
- **Mann–Kendall alone, or OLS p-values on the 30 s series.** On a sawtooth with hundreds of samples, significance is guaranteed and says nothing about size.

**Numbers #517 owns (Paul's thresholds; none are proposed here):** the post-GC slope limit in MB/hour, the per-journey bytes per iteration, the ceiling, K, and the length of the warm-up. A starting point that has actually been measured: the healthy `tick-403` hour went from 140 MB to 160 MB post-GC, about 20 MB/hour across minutes 10 to 60, and the leak went from 46 MB to 404 MB in steps (Observed, spec header). Any slope constant should sit between those two and be re-measured over 8 hours before it gates.

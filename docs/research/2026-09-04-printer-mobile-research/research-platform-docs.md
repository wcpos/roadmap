# Platform docs research — receipt printing from RN/Expo, Electron, browser
Date: 2026-09-04. Every claim below is either sourced or explicitly marked **UNVERIFIED**.
Note: `download4.epson.biz` and `support.epson.net` return HTTP 403 to this agent; where those pages are cited, the quote came back through the search index, and that is flagged inline.

## A. iOS local network

### A1. NSLocalNetworkUsageDescription / NSBonjourServices; what a denial looks like
- **Everything outbound to a local address needs the permission, not just multicast.** Apple's FAQ table: "Making an outgoing TCP connection — **Yes**; Sending a UDP unicast — **Yes**; Sending a UDP multicast — Yes; Sending a UDP broadcast — Yes… Receiving an incoming TCP connection — No; Receiving an incoming UDP unicast — No." Also: "All Bonjour operations require local network access: registering a service, browsing for services, and resolving a service," and resolving `.local` names. The checks "are done at the lowest levels of the system," so they cover NSURLSession and therefore RN `fetch`. → So **yes, plain unicast HTTP to `192.168.1.131` fires the prompt.** https://developer.apple.com/forums/thread/663874 (superseded by TN3179: https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy)
- **Browsing an unlisted Bonjour type is not a prompt and not a crash — it is a policy denial.** `NSNetServiceBrowser` reports error **-72008 = NSNetServicesMissingRequiredConfigurationError**; `NWBrowser` goes to `waiting(-65570: PolicyDenied)`; raw `dns_sd` returns 0 from the initial call and only surfaces `kDNSServiceErr_PolicyDenied (-65570)` in the callback — i.e. **it looks like "silent empty results" if you don't read the callback error.** The device console prints the exact missing string: `App Info.plist(NSBonjourServices) does not allow '_myprotocol._http._tcp.' for (My App)`. https://developer.apple.com/forums/thread/741503 and https://developer.apple.com/forums/thread/664264
- **Denied permission, as seen by URL loading:** Apple DTS (Quinn): "If a request is blocked by ATS you'll see some sort of TLS error, typically `NSURLErrorSecureConnectionFailed` (-1200). If a request is blocked by LNP you'll see some other type of transport error, **commonly `NSURLErrorNotConnectedToInternet`**" (-1009); at the socket layer a denial can surface as `EHOSTUNREACH`. Neither result uniquely identifies a denial: ordinary reachability failures can produce the same signature, so distinguish it only with a separate permission-state signal. https://developer.apple.com/forums/thread/788044
- **Broadcast/multicast additionally needs an entitlement.** "The general rule is that sending or receiving multicast or broadcast traffic requires the multicast entitlement (`com.apple.developer.networking.multicast`)… Sending a UDP unicast — no; Sending a UDP broadcast — yes… Browsing for advertised service types — yes." Enforcement was incomplete on iOS 14/15, "correctly enforced by iOS 16 and later." https://developer.apple.com/forums/thread/663875 — **this matters: Epson's own discovery is a UDP broadcast (see A3/C).**

### A2. ATS, IP literals, self-signed certs
- **ATS does not apply to IP literals.** Apple's archived ATS reference ("Availability of ATS for Remote and Local Connections") states ATS applies only to connections made to **public host names**; connections to IP addresses, unqualified names, or `.local` are outside ATS. Quinn confirmed empirically on iOS 10.1.1 that an app with no `NSAppTransportSecurity` dictionary loaded `http://192.168.x.x` successfully. https://developer.apple.com/forums/thread/66417
- **`NSAllowsLocalNetworking`** is "a Boolean value that indicates whether to allow local resources to load" — it exempts private IPs, unqualified hostnames (no dots) and `.local` from ATS while leaving ATS in force for public hosts. Quinn's current guidance: "If your app is expected to work with local devices — for example, you're building an app to configure an accessory — deploy `NSAllowsLocalNetworking`." https://developer.apple.com/documentation/bundleresources/information-property-list/nsapptransportsecurity/nsallowslocalnetworking and https://developer.apple.com/forums/thread/788044
- **Certificate trust is a separate gate and ATS keys cannot open it.** Quinn: if the server "presents a certificate that's not trusted by default (very likely given that it's hard to get a CA to issue a certificate for a 192.168/16 address), you must override HTTPS server trust evaluation" — i.e. a native `URLSession:didReceiveChallenge:` delegate. https://developer.apple.com/forums/thread/66417
- **RN `fetch` rejects self-signed on iOS with `NSURLErrorDomain` code **-1202** (`NSURLErrorServerCertificateUntrusted`, "The certificate for this server is invalid").** The cause is structural: React Native's `RCTHTTPRequestHandler.m` does not implement `URLSession:didReceiveChallenge:completionHandler:`, so "self-signed certificates are not included in HTTP calls" and there is no JS-level opt-out. Fix requires patching that file or adding an Obj-C category — a native module, not Info.plist. https://github.com/facebook/react-native/issues/22060 and https://github.com/react-native-webview/react-native-webview/issues/3673
- **There is no Info.plist-only way to trust a per-host self-signed cert on iOS.** (No such key exists in the ATS schema; ATS keys relax policy, they do not add trust anchors.) Sourced negatively from the above: Apple's own remedy is trust-evaluation override in code.
- **Expo:** `expo/fetch` is documented only as "a WinterCG-compliant Fetch API that works consistently across web and mobile environments" and is installed as the global `fetch` on Android/iOS — **no TLS/certificate/trust configuration surface is documented.** https://docs.expo.dev/versions/latest/sdk/expo/ `expo-network` "provides useful information about the device's network such as its IP address, MAC address, and airplane mode status" — **no discovery, no local-network permission handling.** https://docs.expo.dev/versions/latest/sdk/network/ Info.plist keys go through `ios.infoPlist` in app config (`NSLocalNetworkUsageDescription`, `NSBonjourServices`) and the multicast entitlement through `ios.entitlements`; https://docs.expo.dev/versions/latest/config/app/

## B. Android

### B4. Cleartext to a private IP
- "Starting with **Android 9 (API level 28), cleartext support is disabled by default**." The implicit `base-config` for apps targeting 28+ is `cleartextTrafficPermitted="false"` with `<certificates src="system"/>`. https://developer.android.com/privacy-and-security/security-config
- **The throw is `java.net.UnknownServiceException`, not a bare IOException** (UnknownServiceException extends IOException). OkHttp: `throw new RouteException(new UnknownServiceException("CLEARTEXT communication to " + host + " not permitted by network security policy"))` in `RealConnection.connect()`. https://github.com/square/okhttp/issues/6196
- **IP literals in a domain-config:** the docs give no example for a non-loopback IP, and `<domain>` matching is by exact string / subdomain — **there is no CIDR or range syntax**, so `192.168.0.0/16` cannot be expressed. The only IP-related statement is the Android 17 localhost rule: "A configuration is considered to be targeting localhost if the domain is: `localhost`, `ip6-localhost`, or a numerical IP address and `InetAddress.isLoopback()` is true (for example, `127.0.0.1` or `[::1]`)". So a literal `<domain>192.168.1.131</domain>` works only for that one address; for a merchant-configurable printer IP, the practical option is `cleartextTrafficPermitted="true"` in `base-config`. https://developer.android.com/privacy-and-security/security-config
- Expo: `usesCleartextTraffic` is exposed via `expo-build-properties` (`{"android": {"usesCleartextTraffic": true}}`); a custom `network_security_config.xml` needs a config plugin. https://docs.expo.dev/versions/latest/sdk/build-properties/

### B5. Self-signed HTTPS on Android
- Yes, rejected by default: "`javax.net.ssl.SSLHandshakeException: java.security.cert.CertPathValidatorException: **Trust anchor for certification path not found.**`" — Android lists "The server certificate wasn't signed by a CA, but was self signed" as one of the three causes, and the fix is "modify your application's Network Security Config to trust your self-signed certificates." It explicitly warns against a no-op TrustManager: "don't do this, even temporarily." https://developer.android.com/privacy-and-security/security-ssl
- A bundled trust anchor works and needs no user-installed CA: `<domain-config><domain includeSubdomains="true">example.com</domain><trust-anchors><certificates src="@raw/my_ca"/></trust-anchors></domain-config>`, with the PEM/DER at `res/raw/my_ca`. Caveat from the same page: "Certificate transparency verification isn't performed on connections that use custom trust anchors." https://developer.android.com/privacy-and-security/security-config
- **This does not work for a per-merchant printer.** The certificate must be baked into the APK at build time (`src` is a raw resource ID) and the config is keyed to a `<domain>`; a self-signed cert that differs per printer, on an IP that differs per store, cannot be enumerated at build time. (Inference from the API shape above — no source states this negatively.)

### B6. NSD / mDNS
- `NsdManager` multicast handling is version-sensitive. Before T Extension 7 (Android 12 and earlier, plus Android 13 without that extension update), even a foreground app must acquire a `WifiManager.MulticastLock`, which requires `CHANGE_WIFI_MULTICAST_STATE`. Starting with T Extension 7, the system manages multicast reception for foreground `NsdManager` operations; background work should still avoid holding a lock unless necessary. This is separate from Android 17's local-network access control below. https://developer.android.com/reference/android/net/nsd/NsdManager
- `react-native-zeroconf` (JmDNS/DNSSD path) asks for `INTERNET`, `ACCESS_NETWORK_STATE`, `ACCESS_WIFI_STATE`, `CHANGE_WIFI_MULTICAST_STATE`, and on iOS 14+ needs `NSBonjourServices` + `NSLocalNetworkUsageDescription`. https://github.com/balthazar/react-native-zeroconf/blob/master/README.md
- **New and load-bearing: Android is getting iOS-style local network permission.** "Starting in Android 17, local network protections are mandatory and enforced for apps targeting Android 17 or higher" via **`ACCESS_LOCAL_NETWORK`** (in the `NEARBY_DEVICES` group; Android 16 was opt-in and used `NEARBY_WIFI_DEVICES`). "Traffic to and from a local network address requires local network access permission… implemented deep in the networking stack… includes… networking libraries like Cronet and **OkHttp**." Denied: "TCP Connections will typically result in a **timeout error**… UDP errors and general permission denials will typically result in an **EPERM**." Escape hatch: `DiscoveryRequest.FLAG_SHOW_PICKER` + `registerServiceInfoCallback` — "Connections to IP addresses obtained this way don't require the `ACCESS_LOCAL_NETWORK` permission." https://developer.android.com/privacy-and-security/local-network-permission

### B7. Bluetooth on Android 12+
- Targeting API 31+: declare `BLUETOOTH_SCAN` for scanning and `BLUETOOTH_CONNECT` for talking to already-paired devices; set `android:maxSdkVersion="30"` on legacy `BLUETOOTH`/`BLUETOOTH_ADMIN`. Declare `BLUETOOTH_ADVERTISE` only if the app makes the handset discoverable to other devices; this printer scan/connect flow does not advertise. These are runtime permissions for their respective operations and produce a **Nearby devices** prompt. `android:usesPermissionFlags="neverForLocation"` on `BLUETOOTH_SCAN` lets you drop `ACCESS_FINE_LOCATION`, with the caveat "If you include `neverForLocation`… some BLE beacons are filtered from the scan results." https://developer.android.com/develop/connectivity/bluetooth/bt-permissions
- **What a missing grant throws: UNVERIFIED against a doc quote.** Best understanding: `java.lang.SecurityException` ("Need android.permission.BLUETOOTH_CONNECT permission") from `getBondedDevices()`, `createRfcommSocketToServiceRecord()`, `connectGatt()`, `startDiscovery()`/`startScan()`. The permissions page states the requirement but not the failure mode.

### B8. USB host
- Declare `<uses-feature android:name="android.hardware.usb.host" />`. Two ways in: an `USB_DEVICE_ATTACHED` intent-filter plus `<meta-data … android:resource="@xml/device_filter">` — "When users connect a device that matches your device filter, the system presents them with a dialog… If users accept, your application automatically has permission to access the device until the device is disconnected" — or `usbManager.requestPermission(device, permissionIntent)`, which "displays a dialog to the user asking for permission," answered via a broadcast carrying `EXTRA_PERMISSION_GRANTED`. Bulk write: `claimInterface(intf, forceClaim)` then `bulkTransfer(endpoint, bytes, bytes.size, TIMEOUT)` "in another thread." https://developer.android.com/develop/connectivity/usb/host
- **The device_filter is optional** — it only provides the attach-time launch/auto-grant; `requestPermission()` alone works for an already-connected printer, which is the usual RN/Expo path. Epson's own manual recommends taking it: "For a USB interface, we recommend obtaining access permission to USB devices in the application software… When [OK] is pressed in the dialog box for access permission acquisition, it takes about 10 seconds to open a port. When [Cancel] is pressed… the state of waiting for the timeout lasts for 30 seconds," with `res/xml/device_filter.xml` containing `<usb-device vendor-id="1208" />` (0x04B8 = Seiko Epson). Epson ePOS SDK for Android User's Manual Rev.P, Ch.6 "To connect via USB", p.452 (PDF as above).
- Class 7 (printer class) filtering is possible via `class="7"` in `device_filter.xml` (attributes are `vendor-id, product-id, class, subclass, protocol`), but note Epson filters by VID, not class. Same Android page.

## C. Epson mobile SDK

### C9. iOS Bluetooth = MFi ExternalAccessory
- Protocol string: **`com.epson.escpos`** — "Add `com.epson.escpos` in Supported External Accessory Protocol in your application info.plist." https://github.com/Shoptree/epsonPrintSDK/blob/master/README.md (verbatim mirror of Epson's SDK README). Community RN wrapper uses the same: `"UISupportedExternalAccessoryProtocols": ["com.epson.escpos"]`. https://github.com/MultiSafepay/react-native-epson-epos
- It is MFi/ExternalAccessory, not CoreBluetooth: Epson gates Bluetooth apps behind Apple's MFi review — "If you are developing an iOS App for an Epson MFi series POS printer with Bluetooth/USB, it must be approved by Apple before it is made available in Apple's App Store… this does not apply for iOS applications for printers with WiFi connectivity," with an Application Information Sheet → **MFI PPID** entered in the App Store review notes. https://epson.com/Support/wa00791 The iOS SDK README also lists **BLE** as a separate supported interface alongside Bluetooth, so both stacks exist (README v2.x, https://github.com/popina/EpsonSDK).
- **Pairing order: UNVERIFIED as an Epson doc quote.** Epson's user guide only says "pair the printer with your device using the Bluetooth function of your device" (TM-m30III Connecting Smart Devices page, https://download4.epson.biz/sec_pubs/bs/html/m001464/en/chap03_5.html — 403 to me; quote via search index). Best understanding: MFi accessories must be paired in iOS Settings → Bluetooth first; the app then enumerates them through ExternalAccessory, and an unpaired printer is invisible to the SDK.

### C10. TM-m30III Bluetooth on Android
- **SPP UUID `00001101-…`: UNVERIFIED.** No Epson document states it; the SDK abstracts the socket — you pass a target string `"BT:00:22:15:7D:70:9C"` to `connect()`, and `Discovery` has a `bondedDevices` flag that "Specifies the search target when searching for a device that can be connected via Bluetooth." Epson ePOS SDK for Android User's Manual Rev.P, Printer class / Discovery class. Best understanding: it is Bluetooth Classic RFCOMM/SPP under the hood, and the printer must be bonded in Android Settings first.
- Epson's manual (Rev.P) still documents only the pre-Android-12 set: `BLUETOOTH`, `BLUETOOTH_ADMIN`, plus `ACCESS_COARSE_LOCATION` ("required for Android 6.0 or later"). Current Epson reference adds by API level: ≤28 `ACCESS_COARSE_LOCATION`; 29–30 `ACCESS_FINE_LOCATION`; 31+ `ACCESS_FINE_LOCATION` only when acquiring physical location — i.e. you supply `BLUETOOTH_SCAN`/`BLUETOOTH_CONNECT` yourself per B7. (Discovery.start reference, download4.epson.biz — 403 to me, quote via search index.)

### C11. HTTPS / certificates / ports
- **Port table (Secure Printing enabled → disabled):** 80 HTTP "Cannot print · Can print"; 443 HTTPS "Can print (encrypted) · Can print (encrypted)"; 8008 ePOS SDK "Cannot print · Can print"; 8009 "Cannot print · Can print"; 8043 "Can print (encrypted)"; 8143 "Can print (encrypted)". Epson eRED guide for POS, https://download4.epson.biz/sec_pubs/bs/pdf/eRED_POS_revD.pdf (403 to me; quote via search index). Corroborated by Epson's Security Guidebook for POS Printers listing "communication using the TCP Port (8143/8043/TCPS) for ePOS-Device protected by TLS." https://support.epson.net/security/pdf/security_guidebook/en/NPD7629-00_EN.pdf (403; via index)
- **Epson's answer to the self-signed problem is a real hostname, not a trust override** — the "Automatic certificate update"/certified-domain feature: connect on port 8043 to a hostname built as "the product serial number hashed with SHA-256 and encoded with Base32, plus **`.omnilinkcert.epson.biz`**", generated by `connectHostName` in `printer_sample.html`; "only supported by some TM printers." ePOS SDK for JavaScript, `connect` method reference, https://download4.epson.biz/sec_pubs/pos/reference_en/epos_js/ref_epos_sdk_js_en_eposdeviceobject_connectmethod.html (403; via index)
- Native SDK equivalent: "To connect to the printer via SSL/TLS communication, specify TCPS in the connection type," and "If you specify TCPS in the connection to a printer that does not support SSL/TLS communication, ERR_PARAM is returned." Epson ePOS SDK for Android User's Manual Rev.P, Printer.connect. **Epson does not document app-side certificate pinning or trust overrides** — the SDK owns the TLS stack, so the RN-fetch self-signed problem (A2/B5) only bites if you speak ePOS-Print XML over `fetch` yourself instead of using the SDK.

### C12. USB from iOS
Epson *does* document it, for a short list that **excludes the TM-m30III**: "USB connection is only supported on the TM-m30II, TM-m30II-h, TM-m30II-NT and TM-m50 printers," via a Lightning-to-USB cable under MFi. https://epson.com/Support/wa00791 Epson's SDK landing page describes the family as "using Wi-Fi, Ethernet, Bluetooth, or **USB (Android only)** interface" (download4.epson.biz, 403; via index), while the iOS SDK README lists USB among supported interfaces — the two reconcile as "USB on iOS, MFi models only." ## D. Browser

### D13. WebUSB, Web Bluetooth, and Chrome's Local Network Access
- **WebUSB**: "This feature is available only in secure contexts (HTTPS)" and "**Transient user activation is required.** The user has to interact with the page or a UI element in order for this feature to work." Marked Experimental / "Limited availability… not Baseline because it does not work in some of the most widely-used browsers" (Chromium-only in practice). https://developer.mozilla.org/en-US/docs/Web/API/USB/requestDevice On Android, "after `requestDevice()`, Android will display a prompt asking whether to allow Chrome to access it." https://developer.chrome.com/docs/capabilities/build-for-webusb
- **Web Bluetooth**: secure context only; `SecurityError` DOMException "Thrown if this operation is not permitted in this context due to security concerns, such as being called from an insecure origin"; same Experimental / Limited-availability banners. The user-gesture requirement is Chromium behavior, not on the MDN page. https://developer.mozilla.org/en-US/docs/Web/API/Bluetooth/requestDevice
- **Private Network Access is dead; Local Network Access shipped.** "Chrome previously experimented with restricting access to local network devices with Private Network Access, which required CORS preflights… Local Network Access replaces that effort, after PNA was put on hold." LNA "restricts the ability of websites to send requests to servers on a user's local network (including servers running locally on the user's machine), requiring the user grant the site permission before such requests can be made"; requesting it is limited to secure contexts. Scope for the first milestone is "any request **from** the public network **to** a local network or loopback destination." Update 2025-09-29: "The Local Network Access permission prompt is launching in **Chrome 142**." https://developer.chrome.com/blog/local-network-access
- Enterprise levers exist and one has been withdrawn: `LocalNetworkAccessAllowedForUrls` allowlists origins; `LocalNetworkAccessRestrictionsTemporaryOptOut` is **removed in Chrome 146**; `LocalNetworkAccessIpAddressSpaceOverrides` (146+) re-labels address ranges. https://chromeenterprise.google/policies/local-network-access-allowed-for-urls/ and https://chromeenterprise.google/policies/local-network-access-restrictions-temporary-opt-out/
- Mixed-content behavior depends on LNA support. Chrome 142+ exempts a permission-gated request when it knows the destination is local before DNS resolution (a private IP literal, a `.local` name, or `fetch(..., { targetAddressSpace: "local" })`); after the user grants LNA, such an HTTPS page can reach an HTTP printer. Browsers without that LNA exemption still block the request as mixed content. https://developer.chrome.com/blog/local-network-access

## Implications for the app

1. Direct-to-printer over the LAN is now a *permissioned* operation on all three platforms — iOS 14+ (LNP), Android 17 (`ACCESS_LOCAL_NETWORK`), Chrome 142 (LNA). Budget for three prompts and recovery guidance. A denial can surface as iOS -1009/`EHOSTUNREACH` or Android timeout/`EPERM`, but unexplained connect failures remain ambiguous without a separate permission-state signal; offer both printer/network checks and OS-permission steps rather than labelling the printer offline or the permission denied.
2. With Secure Printing off, prefer acknowledged **HTTP/ePOS on port 8008 for Epson**. Reserve **raw ESC/POS over TCP on port 9100** for generic printers without an acknowledged vendor lane; raw 9100 remains quarantined on Epson. Self-signed TLS costs a native URLSession delegate on iOS (RN `fetch` gives you -1202 with no JS escape) and a build-time-bundled trust anchor on Android that cannot cover a per-merchant certificate. Pay `NSAllowsLocalNetworking` + `usesCleartextTraffic` for the cleartext HTTP lane instead.
3. If TLS is mandatory (for example, Secure Printing kills 80/8008/8009), browser/`fetch` clients may use `*.omnilinkcert.epson.biz:8043` for TLS-protected ePOS-Device communication only on Epson TM models that support the certified-domain hostname. Native mobile should retain the Epson SDK's acknowledged `TCPS:` lane; neither path requires a blanket trust override.
4. Use the Epson ePOS SDK rather than hand-rolled ePOS-Print XML over `fetch`: the SDK owns the TLS stack and sidesteps the whole self-signed problem, and it is the only supported route to MFi Bluetooth.
5. The Android Epson SDK documents UDP-broadcast discovery. The iOS SDK transport — and therefore whether it needs the Apple-approved `com.apple.developer.networking.multicast` entitlement — is **UNVERIFIED** until an iOS-specific document or packet trace confirms it. Keep manual IP entry as a fallback and start the entitlement application only if that evidence shows broadcast/multicast use.
6. Confirm the TM-m30III's actual mDNS types on hardware before writing `NSBonjourServices`; over-listing (`_printer._tcp.`, `_pdl-datastream._tcp.`, `_ipp._tcp.`, `_ipps._tcp.`, `_http._tcp.`) is free, under-listing fails silently with -72008/-65570 in a callback you must actually read.
7. Bluetooth is two different worlds: iOS = MFi ExternalAccessory with `com.epson.escpos`, paired in Settings first, plus an Epson→Apple MFI PPID review step before App Store release; Android = bonded RFCOMM with runtime `BLUETOOTH_SCAN`(`neverForLocation`)/`BLUETOOTH_CONNECT`. The MFi submission is a schedule risk, not a code risk.
8. USB is Android-and-desktop-capable for the m30III; no iOS USB accessory path exists for this model, and its USB-C to iOS is network tethering. WCPOS has verified generic USB and BLE only in Electron; generic native Android/iOS USB/BLE is unsupported, and the current native flow refuses the Netum NT-1809 rather than offering those lanes.
9. The browser build cannot be the primary printing surface: WebUSB/Web Bluetooth require compatible Chromium/device APIs and a user gesture. For LAN HTTP printing, Chrome 142+ can use the mixed-content exemption after an LNA grant when the destination is known to be local; older browsers without that exemption still block an HTTPS page from reaching the HTTP printer. Treat browser printing as degraded mode and route serious printing through Electron or native.
10. Two dated items to re-check before 1.11 ships: Android 17's `ACCESS_LOCAL_NETWORK` and Chrome 146's removal of the LNA temporary opt-out. `DiscoveryRequest.FLAG_SHOW_PICKER` avoids the Android permission only for host addresses returned through the picker callback; saved or manually entered printer IPs still need broad `ACCESS_LOCAL_NETWORK` access once the app targets SDK 37.

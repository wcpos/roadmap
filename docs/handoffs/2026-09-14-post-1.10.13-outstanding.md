## 1. `search.ts` teardown work — split out of #2020, needs its own PR

**Priority: the largest outstanding piece.** Originally finding 6 on #2020. Removing it from that PR was deliberate — a P2 retention leak was blocking a P1 correctness fix, and three consecutive review rounds found defects in the file.

`packages/database/src/plugins/search.ts` is currently at `origin/main` state; the 8 tests that covered this work were removed with it and must come back with the fix.

Four findings to address together:

1. **Retained maps survive locale eviction** (the original P2). `evictLRUIfNeeded` and `recreateSearch` tear down with `searchInstance.collection.destroy()` and never call `close()`, so the clearing code the churn patch installs on `close()` never runs. Retired instances stay reachable with their digest maps.
2. **`__wcposAppendIndex` back-reference survives eviction.** The patch links the pipeline destination to the index through this property. The destination collection stays registered in `database.collections`, so the back-reference strongly retains the entire FlexSearch index for every locale ever visited — defeating the three-locale bound eviction exists to enforce.
3. **Cleanup must run even when `pipeline.close()` rejects.** In the attempted fix, `await search.pipeline.close()` sat outside the `try`, so a rejecting close skipped the cleanup entirely and left the back-reference attached — while the caller had already dropped the instance from `_searchInstances`. Move the pipeline close inside the protected block.
4. **Teardown is not serialized against initialization.** `evictLRUIfNeeded` and `recreateSearch` delete the `_searchInstances` entry *before* awaiting close, and `initSearch` registers no barrier for its own creation work. An `initSearch` already in flight can still publish an instance that a concurrent recreation then replaces or destroys. The attempted fix added a locale-scoped teardown barrier but did **not** cover an init that had already passed the barrier check.

Findings 3 and 4 were raised on #2020 by CodeRabbit after the second attempt; both threads were replied to and resolved as *deferred*, with the reasoning recorded.

**This is a concurrency refactor of app lifecycle code.** It deserves a dedicated PR, tests that fail without each fix, and no release pressure. Do not attempt it as a rider on a release.

## 2. Accepted limitation in the append filter (monorepo#2020, shipped)

> **Corrected later on 2026-09-14** by the independent review of the shipped #2020 (see `2026-09-14-flexsearch-churn-followups.md`, item 1). The original text below said the append is lost "if the pipeline retries the batch". It does not retry. `RxPipeline` never re-invokes a throwing handler: it sets `pipeline.error`, halts, and leaves the checkpoint unadvanced, so the batch is re-read only by the **next process**, which starts with an empty map. The pre-write marking is therefore benign today, and load-bearing on that vendor behaviour. Nothing else in this section changes.

`wcposChangedSearchEntries` records persisted state **before** the upsert that writes the append has returned. If that upsert throws and the batch were ever re-run in the same process, the entry would be dropped as already-persisted and the append lost, so the replayed index would miss that document after the next restart.

Bounded and self-healing: `__wcposPersistedDigests` starts empty after a restart, so the affected document re-appends on its next write.

Fixing it properly means committing the digest only after the upsert resolves, which needs a **post-write anchor in the minified vendor dist**. The patch already carries five byte-exact anchors; a sixth is real added fragility. Independently identified by CodeRabbit, which agreed it matches the PR's own disclosure.

## 4. `release.yml` has no `workflow_dispatch` — no recovery path

**The highest-value small fix.** On the 1.10.13 run the zip built fine and then GitHub returned `HTTP 500` on the asset upload. Both re-run endpoints then 500'd, and once the API recovered the run answered `This workflow run cannot be retried`.

`release.yml` fires only on push to `main`, so the only recovery was another commit — and that is a trap: the version check compares `v$VERSION` against `git describe --tags`, so **once the release is published and the tag exists, a further push skips the build entirely**. The empty-commit re-trigger PR (#1978) became a no-op and was closed.

Add `workflow_dispatch` with a version input, mirroring `wporg-deploy.yml`, which already has one for exactly this reason.

## 8. Process changes proposed, none started

Ranked by leverage. Raised after this release ran two days and needed repeated intervention.

1. **Never decide release scope on the owner's behalf.** Present the tradeoff and ask. The single largest source of churn was pulling #2020 from the train — the one change the train existed for — then reversing.
2. **A release runbook as a repo file**, with a "what each workflow *consumes*" table: `wporg-deploy` builds from the tag and ignores release assets; `release.yml` version-checks against `git describe --tags`. Both caused real errors this run. The memory index itself records that the three release memory files are 9–11 KB each and cannot all be loaded in one session — procedural knowledge that provably does not fit in context belongs in the repo, greppable at the moment of use.
3. **`release.yml` `workflow_dispatch`** — item 4 above.
4. **Make the bundle → worker → plugin ordering mechanical.** Extend free's `OPFS Worker Drift` check to fail a release PR whose plugin version bumped while the vendored worker lags the newest `v1.10.x` bundle tag. That ordering is currently tribal knowledge and getting it wrong is what caused free to ship twice.
5. **One layer per release-blocking PR.** #2020 accreted #2028's ceiling *and* app-lifecycle changes; the split done at the end should have been its starting shape.

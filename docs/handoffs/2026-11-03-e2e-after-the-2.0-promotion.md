## The problems, one by one

Each entry: what failed, the evidence, what was done, what is left, and a pick.

### 1. `search-heap.spec.ts:84` — the long-task gate (free and pro)

- **Symptom.** "committed searches neither retain per keystroke nor block the main thread" fails its long-task budget (2 s of main-thread long tasks across 300 committed searches, a 1.11 number). Observed red on `main` runs 41459036466, 41463902314, 41472403746, 41509298153, 41519951463, 41528976512, 41548499724, 41565438333, 41580428195, every attempt, both projects.
- **Readings** (from #3216's body, Observed in its logs): run 41548499724 free 5,225 / 7,560 / 12,763 ms, pro 8,441 / 6,179 / 3,764 ms; run 41565438333 free 6,395 / 7,701 ms, pro 4,444 / 8,000 ms; run 41572770186 free 979 ms, pro 595 ms. So it passes on some runs with nothing between them but a theme PR.
- **Done.** Quarantined for the beta (#3216, with the gate kept).
- **Left.** Nobody has established whether this is a 2.0 main-thread regression in search (theme and font work landed in the same window), load from four or five Deploy runs sharing dev-free, or a gate that measured something different on 1.11. The variance between runs says load is at least part of it. Pick: own slice. Measure once on a quiet store with a local Metro + Playwright run (`local-web-taste-pass-recipe`), and separately with the gallery shoot running, before touching the budget.

### 2. `pos-cart.spec.ts:47` — the 300 ms cart-add gate, and the twenty-add burst (free and pro)

- **Symptom.** "should add a product to the cart and show checkout button" measures DOM add intent → quantity in the DOM against 300 ms (a 1.11 number). Observed red on every `main` Deploy run from the promotion to #3210, both projects. On the Phase 2 head the sample reported about 1e10 ms while a live probe added a product in under a second and the page clock was sane (Observed, promotion run record), so the first readings were a measurement fault, not a slow add.
- **Readings** on the 2.0 web build (#3210's body, Observed): quiet stores 313–518 ms free, 360–471 ms pro; with four or five Deploy runs sharing the stores 350–1,120 ms; never under 300. The twenty-add burst hit 11,157 ms against its 8,000 ms budget on the loaded run.
- **Done.** Both cases quarantined for the beta with the 300 ms target kept (#3210; Paul 2026-11-02).
- **Left.** Two separate questions: (a) the 1e10 ms reading means the timing harness can return garbage on some path (clock source, or a mark that never fires), which would also hide a real regression; (b) the 2.0 add is 15–70 % over the 1.11 target on a quiet store. Pick: own slice for (a) first, since every timing gate below depends on it.

### 10. The suite's own plumbing

- **Shard setup can fail before any test runs.** On #3215 (run 41586966583, shard 6) `node_modules/secp256k1 install` failed its node-gyp build against Node 22.22.2 (`v8-local-handle.h:269: static assertion failed`), the deployment health check then "failed after 30 attempts", and every spec in the shard was listed as skipped. A rerun of the failed jobs was green. Observed. Rule of thumb already in memory: zero tests ran means infra, rerun before reading specs.
- **Four or five Deploy runs share dev-free and dev-pro.** Every timing gate above (#1, #2, #5) read differently on a quiet run than on a loaded one (Observed in #3210 and #3216). The suite has no notion of "store busy", so a timing budget is as much a statement about the day's merge rate as about the app.
- **Probe data accumulates on the dev stores.** dev-free carried 3,990 probe coupons before #3212 swept them like probe products (Observed, #3212). Other fixture types may be accumulating the same way; #6's intermittency would fit.
- **dev-free's hostile edge strips `Authorization` and every `X-WCPOS-*` header** (its nginx tier). On the Phase 2 head the 2.0 app withheld its protocol twin on that path, every sync answered 426 and no E2E could load the POS; fixed in the cut (`customHeadersReachServer`), and #3203 made the hydration-echo fixtures carry the `X-WCPOS` marker the header verdict needs. Observed (promotion record). Any new fixture that fakes the echo endpoint must carry the marker or every spec dies in global setup.
- **The dev-box mu-plugin compared the plugin version with `version_compare`**, which sorts `2.0.0-beta.1` below `2.0.0`, attached the pre-2.0 auth hook name, and the 2.0 plugin's deprecation notice landed on the login page: every E2E died on the redirect in global setup until wcpos-wordpress#60. Observed (promotion record). A `-beta.N` or `-rc.N` stamp can re-break any compare someone adds.
- **The production-bundle cadence fallback** needed the ledger path's 60 s allowance (#3211, `21716e151`). Observed as a merged fix; the spec it governs was not red in the runs read here.
- **Quarantined cases still cost the full retry budget.** Shard 3 and shard 5 run their quarantined timing cases three times each per project; that is where a good part of the wall-clock goes.

## How to read the state again

- Per-shard outcome of recent `main` runs: `gh run list -R wcpos/monorepo --branch main --workflow Deploy --limit 7 --json databaseId` then `gh run view <id> --json jobs` and filter job names on `E2E Tests (`.
- Failing specs of a red run: `gh run view <id> -R wcpos/monorepo --log-failed | grep -oE "\[(free|pro)-authenticated\] › e2e/[a-z0-9-]+\.spec\.ts:[0-9]+:[0-9]+ › [^│]*" | sort | uniq -c | sort -rn`. A count of six is a case that failed every attempt in both projects; a count of one with a duration in brackets is usually a passed line that the failed-job log happens to list.
- The quarantine ledger: `apps/main/e2e/quarantine.json`, issue #2284, the `🧫 Quarantine report` job on each run.

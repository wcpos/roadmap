## 2. What the build is

Restyle the built screens to V2, step by step, keeping their behaviour, their tests' contracts and their
ledger lines. It is a visual change on existing screens, not new screens. The `new:` lines in
`changes.md` are the only places the component library grows, and each is a question before it is built
(§ 4).

Slices, one PR each, in this order (each is small enough to review and each is shot by the gallery or the
captures spec):

1. **AmountFigure `hero` inside a FieldBox** for every editable money amount (float, pay in, pay out,
   the count): the numerals, the 64 px frame, the `0.00` placeholder. One component change in
   `packages/components`, a gallery cell, then its four call sites.
2. **The register panel**: "In the drawer" as an unframed hero figure, "Session sales" as a muted line,
   the three verbs as `outline` buttons with the icon over the label (a `new:` line), the Expected ledger
   as a fold that can open.
3. **Pay in / Pay out** (`movement-sheet.tsx`): the figure leads, the keypad under it, reason chips in a
   fixed grid (a `new:` line: Chip at 44 px), the approval-limit line beside the button for Pay out over
   the limit ("Continue to approval", a `new:` line).
4. **The count** (`register-count.tsx`): the figure leads, the keypad collapses after entry (ruled),
   Expected + difference as one block whose lower half is the band (Short `--bad-bg`/`--bad`, Over
   `--ok-bg`/`--ok`, Exact `--muted`/`--muted-foreground` with a check), the footer's two buttons.
5. **Closure written** (`closure-written.tsx`): the variance leads as a hero figure with its eyebrow;
   Counted and Expected as two tiles; "Closure paper" fold open; Print and Done in one row.
6. **Reports › Closures**: the Stat strip and Tabs, the Difference column with its word badge, the phone's
   labelled caption line, the two-column phone filter grid with the date-range chip.

Not in scope: the picker and the gate card (ruled and built in October; V2 draws them as they are), any
behaviour change beyond the keypad ruling, any token value (V2 changes none).

## 3. How each slice is done

- Worktree from `origin/main`; PR to `main`; the brief's budget and the 600-line law apply per slice.
- Before the first slice: run `/mockup`'s diff discipline in reverse: open the built screen beside
  `variants/v2.html` at 1280 and 390 in light and dark, list every difference, and put that list in the
  slice's PR body as the contract. A difference not in the list is not in the PR.
- Component changes land in `packages/components` with a gallery cell, and the gallery baselines are
  refreshed in the same run. The recipe (monorepo, proven on #2919 and #3049): the `Gallery shoot (k/3)`
  job is one Playwright test per component, so a run names only the FIRST stale cell; do not hand-fix cells
  one per push. Commit the first stale cell's `actual` PNG from the shard's `gallery-report-k` artifact
  over its baseline (a PNG is a gallery input; a `.md` alone does not trigger the shoot), push, and add the
  `gallery:update-baselines` label: the bot commits every remaining baseline in ~20 min. The Merge Gate
  requires Gallery only where `test.yml` reported it.
- Before opening any slice's PR, search open PRs by symptom (`gh pr list -R wcpos/monorepo --search
  "<component or screen>"`): the MacBook and the mini have opened the same fix twice before.
- Tests: the screen's own suite (`--maxWorkers=2`), the components suite for any touched component, and
  `apps/main/e2e/register-captures.spec.ts` reshot so the captures carry the new look (that spec is the
  proof the states still render; the journey specs in `e2e/journeys/` are the proof the flow still runs).
- Reviews: `@codex review` on every push; read every thread; never `--auto`.
- Live check on `ui-polish-live` (Metro on :8081) is optional; the gallery and captures are the record.
